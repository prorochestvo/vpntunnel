# Task Breakdown

## Overview

Re-deploying an already-deployed version fails at the `scp` step with:

```
scp: dest open "/opt/vpntunnel/vpntunnel.v0.0.1": Failure
scp: failed to upload file ./build/vpntunnel to /opt/vpntunnel/vpntunnel.v0.0.1
```

Root cause: this is `ETXTBSY` ("text file busy"). On Linux a file that is
currently being executed cannot be opened for writing/truncation. The deploy
workflow scps the new binary **directly onto its versioned filename**
(`.github/workflows/release.yml:120-124`,
`$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}`). For a brand-new version that file
does not exist, so scp succeeds. But when the **same version is re-deployed**,
that versioned file is the live binary the running systemd service is executing
(it is the target of the `vpntunnel` symlink), so `scp`'s open-for-write of the
destination is rejected with `ETXTBSY` and the deploy aborts.

The symlink swap later in the workflow already avoids this class of problem by
writing to a temp name and renaming atomically (`release.yml:175-176`). The same
pattern must be applied to the binary upload: upload to a temp filename, then
`mv` it into the versioned name on the host. `rename(2)` replaces the directory
entry without opening or truncating the busy inode, so it succeeds even when the
target is the running binary — the running process keeps the old (now unlinked)
inode until the subsequent `systemctl restart` re-execs the new file.

The fix is confined to `.github/workflows/release.yml` (the `Copy binary to
host` and `Deploy on host` steps). No Go source changes. This deliberately does
not touch any file under `cmd/`, `internal/`, or `go.mod`, so it cannot collide
with the in-flight main-code refactor in the other session.

## Assumptions

- The host is Linux; `ETXTBSY` semantics apply (confirmed by the error string
  and the `ll` listing showing `vpntunnel -> vpntunnel.v0.0.1` with
  `vpntunnel.v0.0.1` as the running symlink target).
- `mv -Tf` (rename) over a running executable succeeds on the host filesystem
  (single-filesystem rename, same directory) — `ETXTBSY` only blocks
  open-for-write/truncate and `execve` of a file open for writing, not rename of
  the directory entry.
- `BINARY_SHA256` is computed on the runner from `./build/vpntunnel`
  (`release.yml:66`) and must match the uploaded artifact regardless of the
  destination filename, so the integrity check still holds when verifying a temp
  file.
- The deploy account can create and rename files in `$REMOTE_DIR` (the dir is
  `0777` per the `ll` output; the existing symlink `mv` already relies on this).
- Re-deploying the same tag is a legitimate, supported operation (operator did
  it intentionally to recreate the service). The goal is idempotent redeploys,
  not refusing them.

## Tasks

### Task 1: Upload the binary to a temporary filename, not the versioned name

- Description: In the `Copy binary to host` step (`release.yml:109-124`), change
  the `scp` destination from
  `"$SSH_USERNAME@$SSH_HOSTNAME:$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}"` to a
  temporary upload name in the same directory, e.g.
  `"...:$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}.upload"`. The temp name is never
  a symlink target and is never executed, so it can never be `ETXTBSY`. Update
  the step comment (`release.yml:110-112`) to describe the temp-upload +
  server-side atomic-rename design and to state the real reason (avoid `ETXTBSY`
  / truncating the running binary on same-version redeploys), not just
  "interrupted transfer".
- Acceptance Criteria:
  - `scp` writes to `$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}.upload`.
  - A redeploy of the currently-running version no longer fails at the copy step.
  - The step comment explains the temp-then-rename rationale.
- Pitfalls & edge cases: a stale `.upload` file from a previously failed run is
  harmless — `scp` overwrites it (it is not running). Keep the temp suffix
  distinct from `.tmp` (already used by the symlink swap at line 175) to avoid
  confusion; `.upload` is suggested.
- Complexity: Easy

### Task 2: Verify SHA256 on the temp file, then atomically rename into place

- Description: In the `Deploy on host` step heredoc (`release.yml:152-176`),
  operate on the temp file first:
  1. Point the `sha256sum` integrity check (`release.yml:156`) at
     `vpntunnel.${GITHUB_REF_NAME}.upload`. On mismatch, `rm -f` the `.upload`
     temp (not the live versioned file) and exit.
  2. `chmod +x` the `.upload` temp.
  3. Atomically promote it:
     `mv -Tf "$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}.upload" "$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}"`.
     This is the step that tolerates a running same-version target.
  4. Keep the existing `test -f` precondition (line 168) but point it at the
     final versioned name *after* the rename, as the guard before the symlink
     swap.
  5. Leave the symlink swap + restart (`release.yml:175-177`) unchanged.
- Acceptance Criteria:
  - SHA256 is validated against the uploaded artifact before it is promoted to
    the versioned name; corruption still aborts the deploy and removes the temp.
  - The versioned file is replaced via `mv`/rename, never via direct write, so
    the operation succeeds when that versioned file is the running binary.
  - After a same-version redeploy, `systemctl restart` runs the freshly uploaded
    binary (new inode), and `is-active` + the `/v1/admin/health` curl checks
    (`release.yml:181-214`) run unchanged.
- Pitfalls & edge cases:
  - Order matters: verify hash → chmod → rename → symlink swap → restart. Do not
    rename before the hash check, or a corrupted upload could replace a good
    running binary.
  - `mv -Tf` (treat dest as a normal file, force) is required so an existing
    versioned file is replaced rather than moved *into* a directory.
  - Rollback semantics: when redeploying the *same* version, `PREVIOUS_VERSION`
    (`release.yml:165`) equals the version being deployed, so "rollback" points
    at the same name — there is no separate old artifact for that version. Real
    rollback still relies on the retained *other* versions (`release.yml:251`,
    keep newest 3, active protected). Note this in Risks; do not try to preserve
    the pre-replace inode.
- Complexity: Medium

### Task 3 (optional refinement): Skip the rename when the upload is byte-identical to the running version

- Description: Before the `mv`, optionally compare the `.upload` hash to the hash
  of the existing `$REMOTE_DIR/vpntunnel.${GITHUB_REF_NAME}` (if present). If
  identical, skip the rename (the running binary is already correct) and proceed
  straight to the symlink swap + restart, then `rm -f` the temp. This makes a
  pure "restart the same build" redeploy do zero binary I/O.
- Acceptance Criteria:
  - Identical-redeploy path performs no `mv` and leaves the live inode untouched,
    but still restarts the service.
  - Non-identical redeploy (rebuilt same tag) still promotes the new binary.
- Pitfalls & edge cases: this is a nice-to-have; the Task 2 `mv` already works
  correctly for the identical case (it just replaces with an identical file). Only
  add this if the team wants to avoid swapping the inode of a running, healthy
  binary on a no-op redeploy. Keep it behind a simple `if` to avoid bloating the
  heredoc.
- Complexity: Easy

### Task 4: Document the behavior

- Description: Update the `Deployment` section of `CLAUDE.md` to state that the
  binary is uploaded to a `.upload` temp and atomically renamed into the
  versioned name on the host (so re-deploying an existing/running version is
  idempotent and `ETXTBSY`-safe). One or two sentences; mirror the existing
  description of the atomic symlink swap. (Defer the actual edit until the
  main-code session is done if `CLAUDE.md` is contended; the workflow change
  itself does not depend on it.)
- Acceptance Criteria:
  - `CLAUDE.md` Deployment section mentions the temp-upload + rename step.
- Pitfalls & edge cases: persisted docs stay in English (global rule).
- Complexity: Easy

## Execution Order

1. Task 1 — change the `scp` destination to the temp name.
2. Task 2 — verify-on-temp, chmod, atomic rename, then existing swap/restart.
3. Task 3 — optional skip-if-identical refinement (only if desired).
4. Task 4 — CLAUDE.md note (can land last; defer if CLAUDE.md is contended).

Tasks 1 and 2 are a single logical change and must ship together — Task 1 alone
(temp upload with no rename) would leave the versioned file missing.

## Risks

- **Rename over a busy executable assumption.** The whole fix hinges on
  `rename(2)` succeeding against the running binary. This is standard Linux
  behavior, but validate once on the host (e.g. `mv` a dummy over the running
  versioned name in a scratch test) before relying on it in production.
- **No same-version rollback artifact.** Replacing the running version's file
  means the previous bytes of *that version* are gone after restart. Real
  rollback still works via the other retained versions. Acceptable and inherent
  to redeploying the same tag; documented in Task 2.
- **Partial failure between rename and restart.** If the workflow dies after the
  `mv` but before/around `systemctl restart`, the versioned file is the new
  binary while the service still runs the old inode until the next restart. The
  existing diagnostics + health gate (`release.yml:181-214`) already surface a
  failed restart; the next deploy is still idempotent.
- **Temp-file cleanup.** A failed run can leave a `.upload` file behind. The
  retention cleanup (`release.yml:251`) globs `vpntunnel.v*`, which would also
  match `vpntunnel.vX.Y.Z.upload`; ensure the cleanup glob/logic does not treat a
  stray `.upload` as a deployable version. Prefer `rm -f` of the temp on every
  exit path (success and hash-mismatch), and confirm the retention `ls`/`grep`
  does not accidentally protect or count `.upload` files.

## Trade-offs

- **Temp-upload + atomic rename vs. stopping the service before scp.** Chosen the
  rename approach: it keeps the existing zero-extra-downtime shape (only the
  normal `systemctl restart` at the end) and mirrors the symlink-swap pattern
  already in the file. Stopping the unit before scp would add downtime and a new
  failure mode (service left stopped if the deploy aborts). Rejected.
- **Temp-upload + rename vs. refusing same-version redeploys.** Could detect that
  the versioned file already exists and fail fast with a clear message. Rejected:
  the operator legitimately wants same-version redeploys to work (service
  recreation), so making them succeed is the correct behavior, not blocking them.
- **Always rename vs. skip-if-identical (Task 3).** Always-rename is simplest and
  correct; skip-if-identical avoids swapping a healthy inode on a no-op redeploy
  but adds branching to the heredoc. Left optional.

## Appendix: immediate unblock (no workflow change required)

To get production moving right now, before this fix ships, the simplest path is
to **deploy a new tag** (e.g. `v0.0.2`) instead of re-running the `v0.0.1`
deploy. A new versioned filename does not collide with the running binary, so the
`scp` succeeds and the normal symlink swap + restart proceeds. (This sidesteps
`ETXTBSY` entirely without any host surgery.) Alternatively, on the host: stop
the unit, then the direct `scp` would succeed — but a new tag is cleaner and
needs no manual host steps.
