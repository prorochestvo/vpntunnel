# Task Breakdown

## Overview

Add optional Bearer-token authentication to the `httpproxy` forward proxy. The
proxy currently has no client auth (see the `client authentication disabled (v1)`
log line in `cmd/httpproxy/main.go` and the warning in `internal/config/config.go::warnNonLoopback`).
We will add RFC 7235 `Proxy-Authorization: Bearer <token>` checking on both
`HandleHTTP` and `HandleCONNECT` paths in `internal/service/proxy.go`. On
missing/invalid credentials the proxy responds with `407 Proxy Authentication
Required` plus a `Proxy-Authenticate: Bearer realm="httpproxy"` challenge —
**before** any CONNECT hijack happens, so the response still flows through the
normal `http.ResponseWriter`.

The token is configured under a new optional `auth` block in `proxy.json`,
either inline (`auth.token`) or via an out-of-tree file (`auth.token_file`,
path resolved relative to `proxy.json` exactly like `upstream.configs` already
is in `cmd/httpproxy/main.go::resolveActiveTunnel`). The two fields are
mutually exclusive. When the block is absent or both fields are empty, auth
stays disabled — full backwards compat with every existing `proxy.json`.

The token is treated as secret material on par with the WireGuard private key:
never logged, never echoed in errors, never on the 407 response body.
Constant-time comparison via `crypto/subtle.ConstantTimeCompare` prevents the
timing oracle that a naive `==` would create.

## Assumptions

- Single-token model is sufficient for v1. No multi-tenant, no per-client
  tokens, no rotation primitives, no JWT/expiry. If we ever want those, this
  plan's `auth.Verifier` interface gives us the seam — but YAGNI for now.
- The auth check fires **before** the existing `HandleHTTP` / `HandleCONNECT`
  body. For HTTP this means the URL absoluteness check (and everything else)
  is gated behind auth. For CONNECT it means the 407 is written via plain
  `http.Error` before any hijack — RFC 7231 §4.3.6 allows error responses to
  CONNECT before tunnel establishment.
- The `Proxy-Authorization` header is already stripped from the outbound
  request by `stripHopByHop` in `internal/service/proxy.go` (line 386), so we
  do not need to add that — but we MUST re-verify in tests that the header
  is not forwarded to upstream after auth succeeds.
- Token comparison is byte-for-byte (no Base64 decoding — Bearer tokens are
  opaque strings per RFC 6750 §2.1). Whitespace around the scheme/token is
  allowed per RFC 7235 grammar but at most a single space is what real
  clients send; we will tolerate one or more spaces between `Bearer` and the
  token via `strings.Fields`.
- Scheme matching is case-insensitive (RFC 7235 §2.1: "case-insensitive
  token"). Token comparison is case-sensitive.
- For v1, auth applies uniformly — there is no `/healthz`-style bypass on the
  proxy listener because the proxy listener does not serve `/healthz`. The
  admin listener (`internal/transport/adminserver/server.go`) is a separate
  port and is **out of scope** for this plan.

## Tasks

### Task 1: Add the `auth` block to the config schema

- **Description:** Extend `internal/config/config.go` with an `Auth` block in
  `Config`, a matching `rawAuth` JSON shape under `rawConfig`, and parsing
  + validation logic. Two mutually exclusive optional fields:
  - `auth.token`: inline string. Trimmed of surrounding whitespace.
  - `auth.token_file`: path to a file containing the token. Resolved
    relative to the directory of `proxy.json` (caller's responsibility —
    see Task 2; `config.Load` only carries the raw string).
  Add the `Auth` struct, the `rawAuth` shape, route it through `toConfig()`,
  and add validation cases in `validate()`. Update `internal/config/config_test.go`
  with the full validation matrix (subtests of one top-level test per the
  CLAUDE.md "one Test\* per method" rule — add cases to `TestLoad` or to a new
  `TestConfig_Validate`, whichever already exists; do NOT spawn
  `TestLoad_AuthBoth`, `TestLoad_AuthEmpty`, etc. as siblings).

- **Acceptance Criteria:**
   - [ ] `config.Config` has an `Auth` field of a new exported type `Auth`
         with exported fields `Token string` and `TokenFile string`.
   - [ ] `rawConfig` decodes `"auth": {"token": "...", "token_file": "..."}`
         from JSON without breaking existing config files.
   - [ ] A `proxy.json` with no `auth` block loads successfully and yields
         `cfg.Auth == Auth{}`. Existing tests in `internal/config/config_test.go`
         continue to pass unchanged.
   - [ ] Validation fails with a `*publicerror.Error` when **both**
         `auth.token` and `auth.token_file` are set. Message names the
         offending fields explicitly.
   - [ ] Validation passes when neither is set, or exactly one is set.
   - [ ] Validation does NOT read `token_file` from disk (that happens in
         Task 2, in `main.go`, because that is where path-relative-to-config
         resolution already lives).
   - [ ] Token value (when inline) is never present in any returned error
         message.
   - [ ] Tests cover: absent block, only `token`, only `token_file`, both set
         (error), empty strings on both treated as absent.

- **Pitfalls:**
   - The duration-pointer trick used for `Admin.ShutdownTimeout` is for the
     "absent vs explicit zero" distinction. Strings don't need that — empty
     string is "absent". Don't over-engineer.
   - Do **not** print the token in the "both fields set" validation error
     (someone could put a token in `auth.token` then realise they need a file
     and add `auth.token_file` too — the error must not echo the inline
     value).
   - The `Auth` block is logically a sibling of `Upstream`, `Admin`, `Health`.
     Slot the new field, JSON tag, defaults block, and validation block in
     the same positions in each list to match existing code structure.

- **Complexity:** Easy

- **Code Example:**
   ```go
   // Auth configures optional Bearer-token authentication for the proxy
   // listener. When both Token and TokenFile are empty, auth is disabled and
   // the proxy serves requests without challenge — matching pre-v1 behaviour.
   // Token and TokenFile are mutually exclusive; setting both fails validation.
   type Auth struct {
       // Token is the inline Bearer token. Empty means "use TokenFile or
       // disable auth". Treat as secret — never log this value.
       Token string
       // TokenFile is a path to a file whose contents are the Bearer token.
       // Resolved relative to the directory of proxy.json by the caller.
       // Trailing whitespace (including the newline that text editors add)
       // is trimmed when the file is read.
       TokenFile string
   }

   // in validate():
   if c.Auth.Token != "" && c.Auth.TokenFile != "" {
       return publicerror.New("config.auth: token and token_file are mutually exclusive; pick one")
   }
   ```

### Task 2: Resolve and load the token at startup

- **Description:** In `cmd/httpproxy/main.go::run`, after `config.Load` and
  before service construction, resolve the token to a single in-memory string:
  - If `cfg.Auth.Token != ""` → use it as-is (after `strings.TrimSpace`).
  - Else if `cfg.Auth.TokenFile != ""` → resolve relative to `configDir`
    (already computed on line 126 as `filepath.Dir(configPath)`), read the
    file, `strings.TrimSpace` the contents, fail-fast on any I/O error or
    empty-after-trim result.
  - Else → empty string, auth disabled.

  This sits in `main.go` (not `config.Load`) because `config.Load` does not
  know `configPath`'s directory — `cmd/httpproxy/main.go` already does the
  same dance for `upstream.configs` in `resolveActiveTunnel`. Mirror that
  pattern. Add a small helper `resolveAuthToken(cfg.Auth, configDir) (string, error)`
  next to `resolveActiveTunnel` and unit-test it in
  `cmd/httpproxy/main_test.go` (new file).

- **Acceptance Criteria:**
   - [ ] A new function `resolveAuthToken(auth config.Auth, configDir string) (string, error)`
         exists in `cmd/httpproxy/main.go`.
   - [ ] Returns `("", nil)` when both fields are empty.
   - [ ] Returns `(strings.TrimSpace(auth.Token), nil)` when only `auth.Token`
         is set.
   - [ ] Returns the trimmed file contents when only `auth.TokenFile` is set;
         path is resolved by `filepath.Join(configDir, auth.TokenFile)` if
         relative, used as-is if `filepath.IsAbs`.
   - [ ] Returns a wrapped error (NOT a `publicerror.Error` — this is operator-facing
         startup failure, not a user-facing proxy response) when the file is
         unreadable.
   - [ ] Returns an error when the file exists but contains only whitespace
         after trim — message: `auth.token_file %s: token is empty after trim`.
   - [ ] The error message never includes the file contents.
   - [ ] One startup log line emitted at `info`: `auth enabled` with
         `source=inline|file=<basename>` OR `auth disabled` (single line, no
         conditional spam). The token length MAY be included (`token_len=N`)
         — operators sometimes want to confirm "yes the right one is loaded"
         without seeing the value. The token value MUST NOT be included.
         The existing `client authentication disabled (v1)` log line on
         line 162 of `main.go` MUST be removed (it lies once auth ships).
   - [ ] If `resolveAuthToken` returns an error, `run` returns it wrapped with
         `fmt.Errorf("resolve auth token: %w", err)` — the existing pattern
         for `resolveActiveTunnel` failures.
   - [ ] Unit tests in `cmd/httpproxy/main_test.go` cover: both empty, inline
         only, file only (relative path), file only (absolute path), file
         unreadable, file whitespace-only, both set (this case is rejected
         in Task 1 validation but the helper should be defensively safe —
         document the precondition and assert it).

- **Pitfalls:**
   - `filepath.Dir(configPath)` was already computed once (line 126). Reuse it,
     do not recompute.
   - Token files often end with `\n` because editors add one. `strings.TrimSpace`
     handles `\n`, `\r\n`, and stray spaces in one shot. Operators will save
     a file via `echo "abc123" > token` and expect it to work — it must.
   - Do NOT log the token. Do NOT include token contents in the
     "empty after trim" error.
   - File-mode permission check (warn if not 0600) is **out of scope** for v1
     — the README will tell operators to chmod 0400. Adding a runtime warn is
     a separate plan if we want it.

- **Complexity:** Easy

- **Code Example:**
   ```go
   // resolveAuthToken returns the Bearer token to enforce. An empty string
   // means auth is disabled. Reads cfg.Auth.TokenFile from disk if set,
   // resolving relative paths against configDir like resolveActiveTunnel.
   // The token value is never returned in any error.
   func resolveAuthToken(auth config.Auth, configDir string) (string, error) {
       if auth.Token != "" {
           return strings.TrimSpace(auth.Token), nil
       }
       if auth.TokenFile == "" {
           return "", nil
       }
       path := auth.TokenFile
       if !filepath.IsAbs(path) {
           path = filepath.Join(configDir, path)
       }
       raw, err := os.ReadFile(path)
       if err != nil {
           return "", fmt.Errorf("read auth.token_file %s: %w", path, err)
       }
       tok := strings.TrimSpace(string(raw))
       if tok == "" {
           return "", fmt.Errorf("auth.token_file %s: token is empty after trim", path)
       }
       return tok, nil
   }
   ```

### Task 3: Add the `internal/auth` package

- **Description:** Create a new package `internal/auth` with two things:
  1. A `Verifier` interface — the minimum surface the service layer needs.
  2. A `BearerVerifier` concrete type built from a single token string,
     using `crypto/subtle.ConstantTimeCompare` for the check.
  3. A package-private helper that parses a `Proxy-Authorization` header
     value into `(scheme, token, ok)`.

  Placement: the service is currently the only consumer, which by CLAUDE.md's
  "package placement follows consumption" rule argues for putting auth code
  inside `internal/service`. We are putting it in `internal/auth` anyway,
  with explicit justification, because:
  - **Testability**: an external `auth` package is trivially unit-testable
    in isolation (parser logic + comparison logic) without spinning up a
    `ProxyService` and a mock dialer.
  - **Clarity of intent**: `internal/auth` is the right cognitive
    address for "where is auth implemented?" — a reviewer looking for the
    auth logic will not find it under `internal/service/proxy.go` next to
    hop-by-hop header handling. The principle "isolation + simplicity is the
    real quality bar" in CLAUDE.md cuts both ways: a 30-line auth concern
    buried in a 400-line file fails that bar.
  - **No abstraction tax**: the `Verifier` interface is one method,
    consumed at one site, and constructed once in `main.go`. The cost of
    "a new package and an interface" is two extra files; the benefit is that
    `internal/service/proxy.go` does not grow a new dependency on
    `crypto/subtle` and `strings.Fields`-style header munging.
  - **Forward door**: if we ever add a second verifier (multi-token, JWT,
    HMAC), the interface is already there. We are NOT pre-building the
    second verifier — that would be the speculative abstraction CLAUDE.md
    warns against. The interface exists because there is genuinely more than
    one possible token shape and the service should not care which.
  - **NOT a shared bootstrap layer**: this is a business-logic package, not
    a startup-wiring layer. CLAUDE.md prohibits the latter, not the former.

  If the orchestrating reviewer disagrees and wants auth inlined inside
  `internal/service`, fine — the trade-off is small either way. Default is
  the new package.

- **Acceptance Criteria:**
   - [ ] `internal/auth/auth.go` exists with:
         - `type Verifier interface { Verify(header string) bool }` where
           `header` is the raw `Proxy-Authorization` header value (one value;
           the caller is responsible for picking one if multiple are sent —
           per RFC 7235 only one is meaningful).
         - `func NewBearerVerifier(token string) *BearerVerifier` constructor.
           Panics on empty token (programmer error — the service-side wiring
           must check the "auth disabled?" branch before calling this).
         - `type BearerVerifier struct { ... }` with a single method
           `Verify(header string) bool`.
         - Package doc comment that names the contract: scheme is
           case-insensitive `Bearer`, token compared with
           `crypto/subtle.ConstantTimeCompare`, returns false on any malformed
           or wrong-scheme header.
         - Godoc on every exported identifier (CLAUDE.md "Godoc on exported
           identifiers").
   - [ ] `internal/auth/auth_test.go` exists, follows the one-Test-per-method
         + subtests rule. `TestBearerVerifier_Verify` covers:
         - valid token → true
         - missing header (empty string) → false
         - `Basic <creds>` → false
         - `bearer <token>` (lowercase scheme) → true
         - `BEARER <token>` (uppercase scheme) → true
         - `Bearer  <token>` (multiple spaces) → true
         - `Bearer<token>` (no space) → false
         - `Bearer ` (no token) → false
         - wrong token, same length → false
         - wrong token, different length → false
         - whitespace-only header → false
         - `Bearer foo bar` (extra token after the first) → false
   - [ ] Constant-time comparison is used. A reviewer reading the file MUST
         find `subtle.ConstantTimeCompare` and MUST NOT find a `==` comparison
         on token bytes.
   - [ ] The token value never appears in the error message of any returned
         error (the package returns no errors, just bool — so this is mostly
         a no-op rule, but be aware: do not introduce errors that include
         the token).
   - [ ] Compile-time interface check at top of the test file:
         `var _ auth.Verifier = (*auth.BearerVerifier)(nil)`.

- **Pitfalls:**
   - `subtle.ConstantTimeCompare` returns 0/1, not bool. Cast or compare
     explicitly: `subtle.ConstantTimeCompare(a, b) == 1`. It also returns 0
     for different-length inputs without leaking the length comparison —
     **but** the caller still leaks length via the early-exit check
     `len(provided) != len(expected)`. The trick is to NOT short-circuit on
     length: always call `ConstantTimeCompare`, which returns 0 for mismatched
     lengths anyway. The length is not itself secret (Bearer tokens have a
     fixed shape per issuer) but it costs nothing to keep this clean.
   - `strings.Fields` collapses multiple spaces and handles all unicode
     whitespace, which is right for the scheme/token split. `strings.SplitN`
     by `" "` would treat double-space as an empty token.
   - The scheme check must be case-insensitive. Use `strings.EqualFold`.
   - The check fails closed: any error path or unexpected shape returns
     false. There is no "fail open on malformed header" in this package.
   - DO NOT trim the token itself — only the surrounding header structure.
     If someone configures their token as `" foo "` they get what they
     asked for (and Task 2 already trims the configured value).

- **Complexity:** Easy

- **Code Example:**
   ```go
   // Package auth verifies Proxy-Authorization headers for the forward proxy.
   //
   // Only the Bearer scheme (RFC 6750) is supported. Scheme matching is
   // case-insensitive; token comparison is byte-exact and uses
   // crypto/subtle.ConstantTimeCompare so the runtime does not leak the
   // valid token via timing.
   package auth

   import (
       "crypto/subtle"
       "strings"
   )

   // Verifier checks a Proxy-Authorization header value. Returns true iff the
   // header carries valid credentials.
   type Verifier interface {
       Verify(header string) bool
   }

   // NewBearerVerifier returns a Verifier that accepts exactly the single
   // Bearer token. It panics if token is empty — empty-token auth is a config
   // bug, not a runtime branch. Callers must check the auth-disabled case
   // before constructing a Verifier.
   func NewBearerVerifier(token string) *BearerVerifier {
       if token == "" {
           panic("auth: NewBearerVerifier requires a non-empty token")
       }
       return &BearerVerifier{token: []byte(token)}
   }

   // BearerVerifier verifies a single-token Bearer credential.
   type BearerVerifier struct {
       token []byte
   }

   // Verify reports whether header is a valid `Bearer <token>` credential.
   // Returns false for any malformed header, wrong scheme, or wrong token.
   // Comparison is constant-time.
   func (v *BearerVerifier) Verify(header string) bool {
       parts := strings.Fields(header)
       if len(parts) != 2 {
           return false
       }
       if !strings.EqualFold(parts[0], "Bearer") {
           return false
       }
       return subtle.ConstantTimeCompare([]byte(parts[1]), v.token) == 1
   }
   ```

### Task 4: Wire the verifier into `ProxyService`

- **Description:** Extend `internal/service/proxy.go`:
  - Add `Verifier auth.Verifier` to `ProxyServiceOptions` (optional — nil =
    auth disabled).
  - Store it on `ProxyService` as `verifier auth.Verifier`.
  - Add a small private helper method `func (s *ProxyService) checkAuth(w http.ResponseWriter, r *http.Request) bool`
    that returns `true` if the request should proceed, `false` if a 407 was
    written.
  - Call `checkAuth` as the very first action in **both** `HandleHTTP` and
    `HandleCONNECT`. For CONNECT, this happens before the host:port parse,
    before `dial`, before `hijack`. The 407 response goes via `http.Error`
    on the still-valid `http.ResponseWriter`.
  - The 407 response sets `Proxy-Authenticate: Bearer realm="httpproxy"`
    and writes a generic body — `"Proxy authentication required."`. NOT
    the token. NOT details about what was wrong (no "missing", "invalid",
    "wrong scheme" — all the same surface to the client; the operational
    log gets the detail).
  - The 407 path emits one access-log record with `status_code=407` and the
    sanitised target (use the existing `logTarget` helper for HTTP; use
    `r.Host` for CONNECT — same as the rest of the file does).
  - Log an `Info` (NOT Warn — auth failures from misconfigured clients are
    routine, Warn floods on noisy networks) operational log line on the
    failure path: `auth failed` with `client_addr=...`, `method=...`,
    `target=...`, `reason=missing|wrong_scheme|wrong_token|malformed`. The
    reason is derived from the verifier's bool plus a cheap pre-check of
    "is the header even present". Token value MUST NOT be logged.
  - **NEVER LOG THE TOKEN**, even in the failure path. The
    `Proxy-Authorization` header value contains the *attempted* token —
    that is still secret material (attacker probes for valid tokens; logging
    them creates an offline-replay corpus). Log only the `reason` enum value.

- **Acceptance Criteria:**
   - [ ] `ProxyServiceOptions` has a new `Verifier auth.Verifier` field
         documented as "optional; nil disables auth".
   - [ ] `NewProxyService` does NOT panic on nil verifier (unlike `Dialer`).
   - [ ] `ProxyService` stores the verifier and a private `checkAuth` method
         exists.
   - [ ] When `s.verifier == nil`, `checkAuth` returns `true` immediately
         (zero allocations on the hot path).
   - [ ] When verifier is set and request lacks `Proxy-Authorization`, returns
         407 with the `Proxy-Authenticate: Bearer realm="httpproxy"` header
         and the body `"Proxy authentication required.\n"`.
   - [ ] When verifier is set and request has a wrong `Proxy-Authorization`,
         same 407 response — operationally distinguishable in the OP log
         (`reason` field) but not in the wire response.
   - [ ] When verifier is set and request has a valid `Proxy-Authorization`,
         the request proceeds and the `Proxy-Authorization` header is
         stripped before forwarding (the existing `stripHopByHop` already
         handles this — verify with a regression test).
   - [ ] CONNECT auth failure does NOT hijack the connection. Verify by
         reading the 407 response back through the normal HTTP client in
         tests (no raw socket needed for the auth path).
   - [ ] Access log records the 407 (with sanitised target, no
         `Proxy-Authorization` header bytes).
   - [ ] Operational log line on failure has `reason` field and NO `token` /
         `header` / `authorization` field anywhere.
   - [ ] All existing tests in `internal/service/proxy_test.go` still pass
         unchanged (they don't set a Verifier; nil = disabled = unchanged
         behaviour).

- **Pitfalls:**
   - `http.Error` adds `\n` to the body. The body assertion in tests must
     include the trailing newline (`"Proxy authentication required.\n"`).
     The existing tests in `proxy_test.go` already follow this convention
     (`"Upstream unreachable.\n"`); follow the same shape.
   - `http.Error` also sets `Content-Type: text/plain; charset=utf-8` and
     `X-Content-Type-Options: nosniff` automatically — fine, no extra work.
   - `w.Header().Set("Proxy-Authenticate", ...)` MUST be called BEFORE
     `http.Error` (which calls `w.WriteHeader`). Setting headers after
     `WriteHeader` is a silent no-op in `net/http`.
   - `r.Header.Get("Proxy-Authorization")` returns "" for missing header.
     This must NOT pass the verifier — the verifier already returns false
     for empty input, but defense in depth: the `checkAuth` helper checks
     `len(header) == 0` first to produce the `reason=missing` log enum
     before calling `Verify`.
   - The "auth disabled" path must be a true zero-cost no-op — do not even
     read the header. The hot path for the no-auth case must be one nil
     check.
   - Do not bypass auth for any method. CONNECT, GET, POST, all gated.
   - The `Proxy-Authorization` header is already in `hopByHopHeaders`
     (line 386) so it never leaks to upstream after auth passes. Add an
     explicit test for this regression.

- **Complexity:** Medium

- **Code Example:**
   ```go
   // in ProxyServiceOptions
   // Verifier authenticates incoming proxy requests via Proxy-Authorization.
   // Optional — when nil, auth is disabled and all requests pass through.
   Verifier auth.Verifier

   // private helper on *ProxyService
   func (s *ProxyService) checkAuth(w http.ResponseWriter, r *http.Request) bool {
       if s.verifier == nil {
           return true
       }
       header := r.Header.Get("Proxy-Authorization")
       reason := "wrong_token"
       switch {
       case header == "":
           reason = "missing"
       case !strings.HasPrefix(strings.ToLower(strings.TrimSpace(header)), "bearer "):
           reason = "wrong_scheme"
       }
       if header != "" && s.verifier.Verify(header) {
           return true
       }
       w.Header().Set("Proxy-Authenticate", `Bearer realm="httpproxy"`)
       http.Error(w, "Proxy authentication required.", http.StatusProxyAuthRequired)
       s.logger().Info("auth failed",
           slog.String("client_addr", r.RemoteAddr),
           slog.String("method", r.Method),
           slog.String("target", authLogTarget(r)),
           slog.String("reason", reason),
       )
       s.logAccess(domain.RequestSummary{
           Method:     r.Method,
           Target:     authLogTarget(r),
           ClientAddr: r.RemoteAddr,
           StatusCode: http.StatusProxyAuthRequired,
       })
       return false
   }

   // authLogTarget picks the right sanitised target for HTTP vs CONNECT.
   func authLogTarget(r *http.Request) string {
       if r.Method == http.MethodConnect {
           return r.Host
       }
       if r.URL != nil && r.URL.IsAbs() {
           return logTarget(r.URL)
       }
       return r.RequestURI
   }
   ```

## Risks

- **Risk: tokens accidentally logged.** Mitigation: explicit "never log
  the token" rules in Tasks 2/4/5, regression assertion in Task 6, new
  CLAUDE.md constraint in Task 7. Reviewer Lens B will (correctly) hunt
  for this.

- **Risk: timing attack via naive comparison.** Mitigation: Task 3's
  acceptance criterion explicitly requires `subtle.ConstantTimeCompare`
  and forbids `==` on token bytes; reviewer can grep for it.

- **Risk: CONNECT auth response written after hijack (would silently
  succeed but ship garbage to the client).** Mitigation: Task 4's acceptance
  criteria put `checkAuth` as the very first call in `HandleCONNECT`,
  before any dial or hijack. Task 6's CONNECT 407 tests use the normal
  HTTP client which would fail loudly if a hijack happened.

- **Risk: backwards compatibility breaks for existing operators.**
  Mitigation: Tasks 1, 4, 5 all encode "empty/missing auth = disabled =
  unchanged behaviour"; existing tests must pass unchanged (acceptance
  criteria for Tasks 1 and 4).

- **Risk: `token_file` resolution diverges from `upstream.configs`
  resolution.** Mitigation: Task 2 explicitly mirrors the existing
  `resolveActiveTunnel` pattern (same `configDir`, same `filepath.IsAbs`
  branch, same `filepath.Join`); shared code path argues against a separate
  helper, separate helper argues for clarity. We pick separate helper for
  clarity (single concern, single test).

- **Risk: scope creep into multi-token, JWT, rotation.** Mitigation:
  Assumptions section pins v1 to single-token; the `Verifier` interface
  is the seam for future work but we are NOT building a second
  implementation in this plan.

- **Risk: operator pastes the token into `config/proxy.json` and commits
  it.** Mitigation: README strongly recommends `token_file` over `token`
  for anything beyond local dev; `/config/auth/*` is gitignored. We
  cannot stop a determined operator from shooting themselves in the foot,
  but we can make the safe path the obvious one.

- **Risk: `Proxy-Authorization` leaks to upstream after auth passes.**
  Mitigation: the header is already in `hopByHopHeaders` (line 386 of
  `proxy.go`); Task 6 adds an explicit regression test.

## Trade-offs

- **Decision 1: separate `internal/auth` package vs inlined in `service`.**
  Chose separate package despite single-consumer rule. Reason: testability,
  cognitive clarity, and the `Verifier` interface is genuinely useful as a
  seam. Cost: two extra files (`auth.go` + `auth_test.go`). The CLAUDE.md
  rule says "lean toward the simpler placement unless you see a real
  reason otherwise" — the reasons above are the "otherwise". Reviewer
  Lens C may push back; if so, inlining is a 30-minute revert.

- **Decision 2: both `token` and `token_file` config shapes vs file-only.**
  Chose both, mutually exclusive. Reason: inline `token` is the obvious
  shape for a one-shot local test (`auth.token = "abc"` and you're done);
  forcing operators to create a file for a 30-second curl test is friction
  for no security gain (the JSON file is also on disk). For production,
  the README recommends `token_file` so the secret is at least in a file
  with restrictive permissions and a gitignored directory.

- **Decision 3: `Verify(header string) bool` vs `Verify(header string) error`.**
  Chose bool. Reason: the failure modes (missing, wrong scheme, wrong token,
  malformed) collapse to the same wire response — there is nothing the
  caller would do differently between them. The "why" of the failure is
  derived for logging by the caller (`checkAuth`), not returned from the
  verifier. An error-returning API would invite the caller to leak the
  reason into the response body, which is exactly what we DON'T want.

- **Decision 4: log auth-failure reason via a small enum derived in
  `checkAuth` vs returning the reason from the verifier.** Chose derive-
  in-caller. Reason: keeps `auth.Verifier` minimal (one method, one bool),
  and the reason enum is a transport/operational concern, not an auth
  concern. The Verifier should not know about logging.

- **Decision 5: fail-fast on `token_file` errors vs warn-and-disable.**
  Chose fail-fast. Reason: silent disable is the textbook auth-bypass
  vulnerability — operator thinks auth is on, file got renamed, proxy
  serves everyone. Crashing on startup makes the bug instantly visible.
  Same principle as the existing config validation (any invalid block →
  exit non-zero).

- **Decision 6: no rate-limiting or fail2ban-style lockout on bad tokens.**
  Out of scope. The proxy binds to loopback by default; the threat model
  is misconfigured clients, not attackers. If the proxy ever binds to a
  public IP, this becomes a separate concern that needs its own plan.
  Bearer tokens of even modest entropy (32 random bytes) survive online
  brute-force against a constant-time comparator without help.
