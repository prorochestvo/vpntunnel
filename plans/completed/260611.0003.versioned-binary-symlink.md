# Task Breakdown

## Overview

Replace the current single-slot `httpproxy.new` → `httpproxy.prev` deploy mechanism
with **versioned binaries plus a symlink swap**. The live `ExecStart` target
`/opt/httpproxy/httpproxy` becomes a symlink pointing at a versioned file
`/opt/httpproxy/httpproxy.${GITHUB_REF_NAME}` (e.g. `httpproxy.v6.0.4`). Atomic
swap is performed via `ln -sf newtarget tmp && mv -Tf tmp httpproxy` (the
single-step `ln -sfn` form is *not* atomic — it unlinks then re-creates).

The host retains the **3 latest** versioned binaries: the active one plus two
rollback candidates. The active version is **always** protected from cleanup,
regardless of its mtime — an operator may have rolled back to an older file,
and the running process must continue to have a working `ExecStart` target on
the next restart.

The systemd unit needs no changes: `execve` resolves the symlink at exec time;
the running process holds the inode independent of any later symlink change.

`make init` is updated to ship and bootstrap a `httpproxy.v0.0.0-init` binary
plus the initial symlink so first-time setup no longer requires a manual scp
of the binary.

## Assumptions

- Production host is Linux with GNU coreutils. `mv -Tf` (the `-T` flag) is
  GNU-only — BSD does not have it. This is a hard requirement of the host OS
  and is documented as such.
- The operator never `touch`es files in `/opt/httpproxy/` by hand. Manual
  `touch` would corrupt the mtime-based ordering used by retention. This is
  documented as a convention, not enforced.
- Cleanup runs at the end of a **successful** deploy only. Manual rollback by
  an operator is out-of-band (ssh + `ln -sfn` + restart) and does not invoke
  the workflow, so cleanup never runs during a rollback.
- The systemd unit's `ExecStart=/opt/httpproxy/httpproxy` is unchanged. The
  kernel resolves the symlink at `execve(2)` to an inode; the running process
  is unaffected by subsequent symlink changes.
- `GITHUB_REF_NAME` for tag pushes is the tag name (`v6.0.4`), which is
  already validated as semver upstream in the workflow.

## Tasks

### Task 1: Release workflow swap mechanics

- **Description:** Rework `.github/workflows/release.yml` to upload the binary
  under a versioned name, atomic-swap the live symlink, capture the previous
  symlink target for rollback diagnostics, and prune old versions while
  protecting the currently active one.

  Changes are confined to two steps:
  - **"Copy binary to host"** (lines 108-123): change the scp destination from
    `$REMOTE_DIR/httpproxy.new` to `$REMOTE_DIR/httpproxy.${GITHUB_REF_NAME}`.
    `GITHUB_REF_NAME` is exported by GitHub Actions; reference it as
    `${GITHUB_REF_NAME}` in the runner-side scp command (no escaping needed).
  - **"Deploy on host"** (lines 125-195): rewrite the heredoc body. New flow:

    1. sha256 verify operates on `$REMOTE_DIR/httpproxy.${GITHUB_REF_NAME}`.
       On mismatch: `rm -f "$REMOTE_DIR/httpproxy.${GITHUB_REF_NAME}"` and
       `exit 1`.
    2. Capture the current symlink target **before** the swap:
       `PREVIOUS_VERSION=\$(readlink "$REMOTE_DIR/httpproxy" 2>/dev/null || echo "none")`.
       Note the leading backslash on `\$(...)` and `\$PREVIOUS_VERSION` —
       these must evaluate **remote-side**, not on the runner.
    3. Atomic swap:
       ```bash
       chmod +x "$REMOTE_DIR/httpproxy.${GITHUB_REF_NAME}"
       ln -sf "httpproxy.${GITHUB_REF_NAME}" "$REMOTE_DIR/httpproxy.tmp"
       mv -Tf "$REMOTE_DIR/httpproxy.tmp" "$REMOTE_DIR/httpproxy"
       ```
       The `ln -sf ... tmp` then `mv -Tf tmp httpproxy` pair is atomic on
       Linux (same filesystem, single `rename(2)`). Using `ln -sfn` directly
       on the live symlink is NOT atomic (it is unlink + symlink, two syscalls).
    4. `sudo /bin/systemctl restart httpproxy`, then the existing
       `is-active` poll loop and `/healthz` poll loop run unchanged.
    5. `dump_diagnostics` now emits the captured `\$PREVIOUS_VERSION`:
       ```
       echo "INFO: previous version was \$PREVIOUS_VERSION"
       echo "  rollback: ssh $SSH_USERNAME@$SSH_HOSTNAME 'ln -sfn \$PREVIOUS_VERSION $REMOTE_DIR/httpproxy && sudo systemctl restart httpproxy'"
       ```
       The rollback hint command uses `ln -sfn`, which is fine for the
       rollback case: the operator is the only writer at that moment and
       can tolerate the millisecond-window between unlink and symlink.
    6. After a successful `/healthz`, run cleanup:
       ```bash
       ACTIVE=\$(readlink "$REMOTE_DIR/httpproxy" 2>/dev/null || echo "")
       cd "$REMOTE_DIR"
       ls -t httpproxy.v* 2>/dev/null | grep -vxF "\$ACTIVE" | tail -n +3 | xargs -r rm -f
       ```
       Logic: list `httpproxy.v*` files newest-first by mtime, drop the active
       symlink target with `grep -vxF` (exact line match, fixed string,
       inverted), keep the 2 newest of the remainder, delete the rest. The
       `-vxF` triple is load-bearing — `-x` prevents prefix collisions
       (e.g. `httpproxy.v1` matching `httpproxy.v1.0.0`), `-F` disables
       regex interpretation of dots, `-v` inverts. Total kept on disk =
       active + 2 = **3**.
    7. **Drop entirely:** the `cp "$REMOTE_DIR/httpproxy" "$REMOTE_DIR/httpproxy.prev"`
       line (line 158) and any `httpproxy.prev` reference in `dump_diagnostics`
       (lines 142-143). The previous version is now its own versioned file
       reachable via `$PREVIOUS_VERSION`; `.prev` is redundant.

  Heredoc-escaping rules (the heredoc on line 137 is unquoted, so runner-side
  variables substitute, remote-side ones must be escaped):
  - `$REMOTE_DIR`, `$BINARY_SHA256`, `$SSH_USERNAME`, `$SSH_HOSTNAME`,
    `${GITHUB_REF_NAME}` — runner-side, **not** escaped.
  - `$PREVIOUS_VERSION`, `$ACTIVE`, `\$(readlink ...)`, `\$(sha256sum ...)`,
    `\$actual`, `\$expected`, `\$i`, `\$body`, `\$healthz_ok` — remote-side,
    must be backslash-escaped.

- **Acceptance Criteria:**
   - [ ] scp step uploads to `$REMOTE_DIR/httpproxy.${GITHUB_REF_NAME}` (no
         `.new` suffix anywhere in the file).
   - [ ] sha256 verify operates on the versioned filename; on mismatch the
         versioned file is removed and the job exits non-zero.
   - [ ] `PREVIOUS_VERSION` is captured via `readlink` before the swap and
         used in `dump_diagnostics` to print a working rollback command.
   - [ ] Symlink swap uses `ln -sf … httpproxy.tmp` + `mv -Tf httpproxy.tmp
         httpproxy`. No `ln -sfn` directly against the live symlink.
   - [ ] The `cp … httpproxy.prev` line is gone. No `httpproxy.prev`
         appears anywhere in the workflow file after the change.
   - [ ] Cleanup runs only after the successful `/healthz` check, never on
         the failure path.
   - [ ] Cleanup pipeline is exactly `ls -t httpproxy.v* | grep -vxF "$ACTIVE"
         | tail -n +3 | xargs -r rm -f`. The `-xF` flags are present (without
         them, prefix or regex collisions can delete the wrong file). The
         `xargs -r` is present (no-op when the list is empty rather than
         calling `rm` with no args).
   - [ ] `make test` and `make lint` still pass (workflow files are not
         touched by these targets, but sanity-check no Go code regressed).
   - [ ] A manual dry-run reading of the rendered heredoc confirms
         `$PREVIOUS_VERSION` is set inside the remote shell, not on the
         runner.

- **Pitfalls:**
  - **`grep -vxF` is non-negotiable.** Without `-x` a value like
    `httpproxy.v1` would prefix-match `httpproxy.v1.0.0` and protect both
    files. Without `-F` the dots in the filename are regex metacharacters.
    Without `-v` the pipeline keeps only the active file and deletes
    everything else.
  - **Heredoc escaping is the most common foot-gun here.** A missed
    backslash on `$PREVIOUS_VERSION` causes it to expand to empty string on
    the runner (it doesn't exist there) and the remote command becomes
    syntactically valid but semantically wrong (rollback hint prints
    `previous version was`). Read the rendered command back from a dry-run
    log before merging.
  - **`mv -Tf` is GNU-only.** macOS/BSD `mv` does not accept `-T`. This is
    Linux-only on the production host by design — document the assumption
    in the plan but do not add a portability shim.
  - **`ls -t` falls back to alphabetical when mtimes match to the second.**
    Within a single deploy this is impossible (we only create one new file),
    but if an operator races a rollback and a deploy this could surprise.
    Acceptable; the alternative (ctime, or version-string sort) requires
    parsing semver and is overkill.
  - **Empty `ls` output must short-circuit.** `2>/dev/null` on the `ls` is
    important — without it, an empty directory prints `ls: cannot access
    'httpproxy.v*': No such file or directory` to stderr and `set -e`
    flips the deploy red after a successful health check.
  - **`grep -v` exits 1 when it filters out everything.** Under `set -e`
    this would abort the deploy. Currently safe because the pipeline ends
    in `xargs -r rm -f`, but if the pipeline is ever reordered, wrap with
    `|| true` at the end.

- **Complexity:** Medium

### Task 2: `make init` ships and bootstraps `httpproxy.v0.0.0-init`

- **Description:** Extend the `init` Makefile target so that first-time
  bootstrap places the initial versioned binary and creates the symlink,
  removing the manual "build first binary and scp it" step from the README's
  bootstrap path.

  Concretely, append to the existing `init` target body (current lines
  67-71):

  1. Build the bootstrap binary locally with the documented version suffix:
     ```make
     CGO_ENABLED=0 go build -o ./build/httpproxy.v0.0.0-init ./cmd/httpproxy/
     ```
  2. scp it to the host:
     ```make
     scp ./build/httpproxy.v0.0.0-init be-happy.kz:/opt/httpproxy/httpproxy.v0.0.0-init
     ```
  3. chmod and create the symlink:
     ```make
     ssh be-happy.kz 'chmod +x /opt/httpproxy/httpproxy.v0.0.0-init && \
                      ln -sfn httpproxy.v0.0.0-init /opt/httpproxy/httpproxy'
     ```
     `ln -sfn` is acceptable for **first-time bootstrap only**: there is no
     prior symlink, so there is no in-flight reader to race. The release
     workflow does NOT use `ln -sfn` — it uses the atomic
     `ln -sf … tmp && mv -Tf tmp httpproxy` form.

  Update the comment block above the `init` target (current lines 40-66)
  to describe the bootstrap binary, the versioned-binary + symlink layout,
  and the fact that the symlink it creates is what the release workflow
  swaps later. Keep the existing wording about `proxy.json`, the systemd
  unit, the bearer token, and ownership.

  Do not touch the existing scp lines for `proxy.json`, the `.conf` file,
  the systemd unit file at `/tmp/httpproxy.service`, or the token-generation
  block.

- **Acceptance Criteria:**
   - [ ] `make init` runs `go build` with `CGO_ENABLED=0` and writes to
         `./build/httpproxy.v0.0.0-init`. The output path stays under
         `./build/` per the repo's "no binaries in the project root" rule.
   - [ ] The build step uses the same `./cmd/httpproxy/` package as
         `make build`.
   - [ ] scp lands `httpproxy.v0.0.0-init` directly in `/opt/httpproxy/`,
         next to (not inside) `configs/`.
   - [ ] The final ssh command chmods the binary executable and creates a
         symlink `/opt/httpproxy/httpproxy → httpproxy.v0.0.0-init`. The
         symlink target is **relative** (`httpproxy.v0.0.0-init`), not
         absolute — relative targets keep the symlink valid regardless of
         where `/opt/httpproxy/` is bind-mounted.
   - [ ] The comment block above `init` mentions the bootstrap binary and
         the versioned-binary + symlink scheme in one short paragraph; it
         does not bloat the existing comment.
   - [ ] No existing scp line is modified or removed.
   - [ ] `make test` and `make lint` still pass.

- **Pitfalls:**
  - **`ln -sfn` versus the release workflow's atomic swap.** It is tempting
    to use the same form in both places "for consistency". Do not. The
    init path is single-shot, has no running daemon to race, and `ln -sfn`
    is the simplest form. The release workflow is the only place where the
    `ln -sf + mv -Tf` pair matters.
  - **Relative versus absolute symlink target.** `ln -sfn httpproxy.v0.0.0-init
    /opt/httpproxy/httpproxy` creates a relative target — correct, because
    the symlink and target are in the same directory. Writing the absolute
    `ln -sfn /opt/httpproxy/httpproxy.v0.0.0-init …` works but ties the
    layout to that specific path.
  - **The `init` target is run by humans, not CI.** `be-happy.kz` is the
    operator's known host alias. Do not parameterize unless asked — the
    target is intentionally not portable across operators.
  - **Stale `./build/` from a previous `make build`.** The new step writes
    a differently-named binary alongside the existing `httpproxy`. That is
    fine: `make clean` already wipes the whole `./build/` tree.

- **Complexity:** Easy

## Execution Order

1. **Task 1** (release workflow). Stands alone; can be tested by dry-running
   the rendered heredoc against a scratch directory locally before pushing
   a real tag.
2. **Task 2** (`make init`). Independent of Task 1 — `make init` writes
   `httpproxy.v0.0.0-init` and the symlink; the release workflow then
   atomic-swaps that symlink on the next deploy. Either order works.
3. **Task 3** (docs). **Must** run last. The docs describe behaviour
   delivered by Tasks 1 and 2 and would otherwise be out of sync.

Tasks 1 and 2 can be parallelized across two PRs / branches; Task 3 must
wait for both to be merged before it accurately reflects the system.

## Risks

- **`mv -Tf` is GNU-only.** Documented assumption. If the host is ever
  migrated to a BSD/macOS box, the deploy breaks. Acceptable — the
  production host is Linux by design and the systemd unit pins that
  assumption already.
- **Operator manually `touch`es a file in `/opt/httpproxy/`.** Breaks the
  mtime-based ordering used by retention. Documented convention: don't.
- **Race between deploy and manual rollback.** If an operator runs
  `ln -sfn` to roll back while the workflow is mid-deploy, the workflow's
  `PREVIOUS_VERSION` capture sees the rolled-back target and the cleanup
  protects the wrong "active". Acceptable — concurrent deploy + manual
  rollback is operator error; the `concurrency: deploy-production` group
  protects against two workflow runs racing each other.
- **Pre-release tags (`v6.0.4-rc1`) all land as separate files on disk.**
  Five `-rc` iterations leave five binaries; retention keeps the 3 newest.
  This is the intended behaviour but worth noting — pre-release churn can
  evict the last stable release from the retained set. If that becomes a
  problem, the cleanup logic could be tightened later to exclude
  pre-releases from eviction (out of scope here).
- **First deploy after this change has no `PREVIOUS_VERSION`.** Before
  the symlink exists, `readlink` exits 1 and prints nothing; the
  `2>/dev/null || echo "none"` fallback handles it. The rollback hint
  printed by `dump_diagnostics` will say "previous version was none",
  which is correct.

## Trade-offs

- **Symlink + `mv -Tf` over copy-with-version.** A `cp` of the new binary
  over the live `httpproxy` would also work and avoid the symlink layer
  entirely. Rejected because (a) the live filename then carries no version
  information — operators have to `sha256sum` to identify a binary; (b)
  rollback requires keeping a separate archive directory; (c) the symlink
  layer is one extra `lstat(2)` at exec time, which is free.
- **3-version retention over time-based retention.** "Last N days" would
  bias toward more retention for quiet weeks. Rejected: count-based
  retention has predictable disk usage and matches the operator's mental
  model ("two rollback candidates is enough; three is overkill").
- **Cleanup at end of deploy, not on a separate schedule.** Could be a
  cron / systemd timer on the host. Rejected for one-host-one-binary
  scope: end-of-deploy keeps it visible in workflow logs and avoids a new
  scheduled job to monitor.
- **`ln -sfn` permitted in `make init`, forbidden in release workflow.**
  Looks inconsistent at a glance but isn't: `init` runs once against a
  cold host with no running daemon; the release workflow runs against a
  live system where a non-atomic symlink update could be observed mid-swap
  by a concurrent restart. Same syscall pair, different threat model.
- **`PREVIOUS_VERSION` captured before swap, not derived from the file
  listing.** Could be reconstructed afterward via `ls -t httpproxy.v* |
  sed -n 2p`, but that depends on mtime ordering. `readlink` is
  authoritative — it tells us exactly what was active a moment ago,
  independent of any file-system race.
