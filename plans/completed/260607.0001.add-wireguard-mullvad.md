# Task Breakdown

## Overview

Ship v2 of `httpproxy`: a second `tunnel.Dialer` implementation backed by
userspace WireGuard (no root, no `wg-quick`, no system routing changes) plus a
one-shot CLI that turns a Mullvad account number into a ready-to-run config.

Two deliverables, one plan because they share two new internal packages and a
config schema change:

1. **WireGuard tunnel** — `internal/tunnel/wireguard/` exposes a
   `WireGuardDialer` that satisfies `tunnel.Dialer`. Under the hood it owns a
   `wireguard-go` userspace device with a gVisor-netstack TUN; `DialContext`
   becomes a thin wrapper around `tun.Net.DialContext`. All traffic — including
   DNS to `10.64.0.1` — egresses through the tunnel. Clients of `httpproxy`
   are unchanged: they still talk to it as a standard HTTP/CONNECT forward
   proxy.
2. **`bootstrap-mullvad` CLI** — `cmd/bootstrap-mullvad/` generates a WireGuard
   keypair, exchanges the operator's Mullvad account number for an access
   token, registers the public key as a device, picks a relay, and writes a
   complete `config/proxy.json` with `upstream.kind = "wireguard"`.

The `tunnel.Dialer` interface added in v1 is the integration seam. v1's
`SOCKS5Dialer` stays — it's the dev/test path. A small factory in
`internal/tunnel/` dispatches on `upstream.kind`. The config schema gets a
discriminator (`kind`) and a per-kind nested block; the v1 flat
`upstream_socks5` shape is **migrated** to `upstream.socks5`, not aliased
(pre-1.0, single operator, clean break is cheaper than dual-decoding).

No DB, no client auth, no health endpoint — same scope guards as v1.

## Assumptions

### Mullvad API contract (pinned from `mullvadvpn-app` source on GitHub)

All API calls go to `https://api.mullvad.net` over TLS. Base host is configurable
in the `mullvad.Client` constructor so tests can point it at `httptest.Server`.
The Mullvad app code uses a `hostname` field rather than a hardcoded constant —
we mirror that.

| Step | Method | Path | Auth | Request body | Response |
|------|--------|------|------|--------------|----------|
| Access token exchange | `POST` | `/auth/v1/token` | none | `{"account_number": "<digits>"}` | `200` + `{"access_token": "...", "expiry": "<RFC3339>"}` |
| Create device | `POST` | `/accounts/v1/devices` | `Authorization: Bearer <token>` | `{"pubkey": "<base64>", "hijack_dns": false}` | `201` + `{"id":"...","name":"...","pubkey":"...","ipv4_address":"10.x.x.x/32","ipv6_address":"fc00:.../128","hijack_dns":false,"created":"<RFC3339>"}` |
| List devices | `GET` | `/accounts/v1/devices` | bearer | — | `200` + array of device objects |
| Delete device | `DELETE` | `/accounts/v1/devices/{id}` | bearer | — | `204` |
| Relay list (WG section) | `GET` | `/app/v1/relays` | none | — | `200` + `{ "locations": {...}, "wireguard": { "ipv4_gateway": "10.64.0.1", "port_ranges": [[51820,51820],...], "relays": [ {"hostname":"se-sto-wg-001","ipv4_addr_in":"185.x.x.x","public_key":"<base64>","location":"se-sto","active":true,"owned":true, ...} ] }, ...}` |

Error mapping confirmed from source:
- Status `200/201/204` → success per endpoint.
- `401` on a bearer-authenticated request → invalid or expired token.
- For device creation, the daemon's error code `MAX_DEVICES_REACHED` (HTTP
  status `400` with a JSON `{"code":"MAX_DEVICES_REACHED", ...}` payload) is
  the documented "you have 5 devices already" path. The implementer should
  verify the exact JSON shape against current API responses during the
  device-create call (likely a `{"code":"...", "detail":"..."}` envelope —
  mirror the daemon's `rest::Error` shape).
- Any non-2xx the client doesn't recognise → return a plain `error` carrying
  status + truncated body for the operator's logs.

The pubkey wire format in JSON is **standard base64** (44 chars ending in `=`)
— same encoding `wgtypes.Key.String()` produces. Do NOT send hex here. UAPI
(IpcSet) is hex; the Mullvad API is base64. Two formats, one easy mix-up.

### WireGuard library surface (verified at pkg.go.dev)

- `golang.zx2c4.com/wireguard/device` — `device.NewDevice(tun.Device, conn.Bind, *device.Logger) *device.Device`. Configured via the UAPI `IpcSet(string) error` (key=value text, one pair per line).
- `golang.zx2c4.com/wireguard/conn` — `conn.NewDefaultBind()` for the UDP underlay.
- `golang.zx2c4.com/wireguard/tun/netstack` — `func CreateNetTUN(localAddresses, dnsServers []netip.Addr, mtu int) (tun.Device, *Net, error)`. `*netstack.Net` exposes `DialContext(ctx, network, address) (net.Conn, error)` and `LookupContextHost(ctx, host) ([]string, error)`.
- `golang.zx2c4.com/wireguard/wgctrl/wgtypes` — `GeneratePrivateKey() (Key, error)`, `ParseKey(string) (Key, error)`, `(Key).PublicKey() Key`, `(Key).String() string` (base64, 32 bytes).

### Locked decisions (from user spec, NOT revisited)

- SOCKS5 stays alongside WireGuard; factory dispatches on `kind`.
- DNS resolution inside the tunnel via `10.64.0.1` (passed to `CreateNetTUN`).
- `AllowedIPs` default = `["0.0.0.0/0", "::/0"]`.
- MTU default = `1420`; `PersistentKeepalive` default = `25s`.
- Endpoint hostnames resolved once at startup via system DNS (control-plane
  leak accepted; operator can hardcode IP).
- Handshake is lazy; failure surfaces as `502 Upstream unreachable.` on first
  request. No fail-fast, no health endpoint.
- No automatic key rotation; rotation = re-run bootstrap.

### Architect decisions (justified in Trade-offs)

- **bootstrap-mullvad is a separate binary** at `cmd/bootstrap-mullvad/`, not a
  subcommand of `httpproxy`. Lifecycles diverge (long-running daemon vs.
  one-shot CLI) and `cmd/<binary>/` per concern is the CLAUDE.md default.
- **Shared code splits two ways**: `internal/tunnel/wireguard/` owns the WG
  device + the dialer (no Mullvad coupling); `internal/mullvad/` owns the
  REST client (no WG coupling — it deals in strings/keys). The bootstrap
  binary glues them.
- **Config schema migrates cleanly** to `upstream: { kind, wireguard, socks5 }`.
  No deprecated alias. `config/proxy.json` is rewritten; v1's flat shape is no
  longer accepted. Pre-1.0; the only consumer is the operator.
- **`tunnel.Dialer` extends to a separate `tunnel.DialerCloser`** for impls
  that own resources. `SOCKS5Dialer` does not implement it; `WireGuardDialer`
  does. `main.go` type-asserts at shutdown.
- **`main.go` Ups the device via the constructor**, not separately. The
  constructor returns a fully-running dialer or an error. `Close()` tears it
  down. The handshake is still lazy because wireguard-go itself dials on
  first packet — the constructor only brings the device "up" administratively.

### Testing decisions

- **WireGuard unit tests**: cover constructor input validation, the UAPI
  IpcSet string we generate (golden-file comparison), and DNS field
  propagation. No real handshake. **No integration test in CI**. Justification:
  spinning up a second wireguard-go instance as the peer doubles the test
  binary's memory cost and tests `wireguard-go` more than our wrapper.
- **Mullvad client tests**: drive against `httptest.NewServer` with hand-rolled
  handlers that mimic the documented responses (and 4xx error shapes). Cover
  401, MAX_DEVICES_REACHED, 5xx with retry-once-then-fail.
- **Bootstrap tests**: introduce a `mullvadClient` interface in the bootstrap
  package; the integration tests use a fake that records calls and returns
  canned responses. The real `mullvad.Client` is exercised separately by its
  own package tests.
- **Manual smoke** (Task 8) is the only "real Mullvad" verification.

### Task 2: Migrate config schema — `upstream` discriminator with `kind`, `wireguard`, `socks5`

- **Description:**
  Restructure `internal/config/config.go` so `Config.UpstreamSOCKS5` (flat,
  v1-shaped) becomes `Config.Upstream` (a tagged union). The new shape:

  ```go
  // UpstreamKind enumerates the supported egress kinds.
  type UpstreamKind string
  const (
      UpstreamKindSOCKS5    UpstreamKind = "socks5"
      UpstreamKindWireGuard UpstreamKind = "wireguard"
  )

  type Upstream struct {
      Kind      UpstreamKind         // required, one of UpstreamKind*
      SOCKS5    UpstreamSOCKS5       // populated when Kind == "socks5"
      WireGuard UpstreamWireGuard    // populated when Kind == "wireguard"
  }

  type UpstreamSOCKS5 struct {
      Address  string // "host:port"
      Username string
      Password string // env override: HTTPPROXY_UPSTREAM_PASSWORD
  }

  type UpstreamWireGuard struct {
      PrivateKey                 string   // base64 (wgtypes format), required
      LocalAddress               string   // CIDR, e.g. "10.66.0.5/32", required
      PeerPublicKey              string   // base64, required
      PeerEndpoint               string   // "host:port", required (UDP)
      AllowedIPs                 []string // CIDR list; defaults to ["0.0.0.0/0", "::/0"]
      DNS                        []string // IP list; defaults to ["10.64.0.1"]
      MTU                        int      // defaults to 1420
      PersistentKeepaliveSeconds int      // defaults to 25
  }
  ```

  JSON shape on disk:
  ```json
  {
    "listen": "127.0.0.1:8080",
    "upstream": {
      "kind": "wireguard",
      "wireguard": {
        "private_key": "...",
        "local_address": "10.66.0.5/32",
        "peer_public_key": "...",
        "peer_endpoint": "185.x.x.x:51820",
        "allowed_ips": ["0.0.0.0/0", "::/0"],
        "dns": ["10.64.0.1"],
        "mtu": 1420,
        "persistent_keepalive_seconds": 25
      },
      "socks5": {
        "address": "127.0.0.1:1080",
        "username": "",
        "password": ""
      }
    },
    "dial_timeout": "10s", "idle_timeout": "90s", "shutdown_timeout": "15s",
    "max_concurrent_connect": 0,
    "access_log": { ... }, "operational": { ... }
  }
  ```
  Note: the `socks5` block sits alongside `wireguard` even when `kind` selects
  WG — it's just ignored. This makes "flip the discriminator" a one-key
  change for the operator and keeps both kinds documented in the file.

  Validation:
  - `Upstream.Kind` required and must be one of the two known values →
    `publicerror.New("config.upstream.kind: must be 'socks5' or 'wireguard'")`.
  - `kind = socks5`: existing v1 validation moves into the SOCKS5 branch.
  - `kind = wireguard`:
    - `private_key`: must parse via `wgtypes.ParseKey` →
      `publicerror.New("config.upstream.wireguard.private_key: invalid base64 WireGuard key")`.
      **Whether to call `ParseKey` in config validation or defer to the
      dialer**: prefer `config` because a bad key is operator-fixable and the
      message can be public; the dialer treats it as an impl invariant.
    - `local_address`: must parse via `netip.ParsePrefix`; the address part
      must be a single host (`/32` for IPv4, `/128` for IPv6 is OK, broader
      prefixes are rejected because netstack's TUN doesn't route them as a
      local source). Public error on failure.
    - `peer_public_key`: must parse via `wgtypes.ParseKey`. Public error.
    - `peer_endpoint`: must parse via `net.SplitHostPort` with a numeric port.
      Public error.
    - `allowed_ips`: each entry must parse via `netip.ParsePrefix`. If empty
      after applying defaults, public error "at least one allowed_ips
      required".
    - `dns`: each entry must parse via `netip.ParseAddr`. If empty after
      defaults, public error.
    - `mtu`: must be in `[576, 9000]` after defaults (576 is the IPv4 minimum
      MTU; 9000 covers jumbo). Public error.
    - `persistent_keepalive_seconds`: must be `>= 0` after defaults. 0
      disables; positive enables. Public error on negative.
  - Env override `HTTPPROXY_UPSTREAM_PASSWORD` still applies, but only when
    `kind == socks5`. When `kind == wireguard`, the variable is ignored
    (and a warn is emitted if set, to flag operator confusion).

  Update `config/proxy.json` in-place to the new shape — keep `kind: socks5`
  as the default so v1 tests + the existing dev workflow keep working with no
  user action. Operators who want WireGuard run `bootstrap-mullvad` to
  regenerate the file with `kind: wireguard`.

  Update `cmd/httpproxy/main.go`'s `domain.TunnelSpec` construction site: the
  field is now `cfg.Upstream.SOCKS5.Address` etc. (full update happens in
  Task 6.)

- **Acceptance Criteria:**
  - [ ] `internal/config/config.go` defines `Upstream`, `UpstreamKind`,
    `UpstreamSOCKS5`, `UpstreamWireGuard`. File declaration order respected:
    new exported `const`s (the `UpstreamKind*` values) at top after the
    existing defaults block; the `Upstream*` structs grouped together.
  - [ ] All `Config.UpstreamSOCKS5.X` references in the repo become
    `Config.Upstream.SOCKS5.X`. Compiler-driven sweep; no stragglers.
  - [ ] `config/proxy.json` updated to the new shape with `kind: "socks5"`.
  - [ ] `internal/config/config_test.go`:
    - Existing `TestLoad` subtests updated for the new path (no new top-level

    - New subtests inside `TestLoad`:
      - `t.Run("loads wireguard upstream and applies wg defaults", ...)` —

      - `t.Run("missing upstream.kind returns PublicError", ...)`.

      - `t.Run("wireguard local_address not /32 returns PublicError", ...)` —

  - [ ] `make test` passes with `-race`.
- **Pitfalls & edge cases:**
  - **Mutually exclusive blocks**: the loader MUST NOT require both `wireguard`
    and `socks5` to be populated. The unused block is allowed to be absent or
    empty; only the block matching `kind` is validated. Document this in the
    `Upstream` godoc explicitly.
  - The default for `AllowedIPs` is applied only when the JSON field is
    absent (nil slice), NOT when it's an explicit empty array `[]`. Empty
    array is a validation error ("at least one required"). Use a `*[]string`
    or sentinel to distinguish in the raw struct. Simpler: keep `[]string`
    raw and treat `nil` as "absent, apply default", `[]` as "explicitly
    empty, error".
  - `netip.ParsePrefix("10.66.0.5/32")` returns a prefix; check
    `prefix.Bits() == prefix.Addr().BitLen()` for the "single host" rule.
  - DO NOT add `omitempty` to JSON tags on the union blocks — we want
    `json.Marshal(cfg)` to round-trip predictably for bootstrap (Task 5).
  - When updating the default `config/proxy.json`, keep `kind: socks5` as
    default; the WG block can be present-but-empty (`"wireguard": {}`) — but
    if so, the loader must not validate it (kind selects which block runs).
    Cleaner: omit the `wireguard` block in the default file; bootstrap writes
    it when needed.

### Task 3: `internal/tunnel/` — factory function dispatching on `Upstream.Kind`

- **Description:**
  Add `internal/tunnel/factory.go`:
  ```go
  // DialerCloser is implemented by Dialers that own resources (a userspace
  // WireGuard device, an open file handle, etc.) and must be torn down
  // explicitly on shutdown. SOCKS5Dialer does not implement this; the
  // wireguard Dialer does.
  type DialerCloser interface {
      Dialer
      Close() error
  }

  // NewDialer builds the egress Dialer selected by cfg.Kind. It returns the
  // concrete type behind a Dialer interface; callers that need lifecycle
  // management should type-assert to DialerCloser at shutdown.
  func NewDialer(cfg config.Upstream, dialTimeout time.Duration, logger *slog.Logger) (Dialer, error) {
      switch cfg.Kind {
      case config.UpstreamKindSOCKS5:
          spec := domain.TunnelSpec{ Kind: domain.KindSOCKS5, Address: cfg.SOCKS5.Address, ... }
          return NewSOCKS5Dialer(spec, dialTimeout)
      case config.UpstreamKindWireGuard:
          return wireguard.NewDialer(wireguard.Options{
              PrivateKey: cfg.WireGuard.PrivateKey,
              ...
              Logger: logger,
          })
      default:
          return nil, fmt.Errorf("tunnel: unknown upstream kind %q", cfg.Kind)
      }
  }
  ```

  Wait — circular import alert. `internal/tunnel/` cannot import
  `internal/config/` if `internal/config/` ever needs to import
  `internal/tunnel/` (it doesn't today, but the layering rule is "tunnel
  doesn't depend on config"). Resolution: the factory accepts a
  `domain.TunnelSpec`-equivalent struct that's broader than v1's spec, OR
  lives in a separate package, OR `cmd/httpproxy/main.go` does the dispatch
  inline.

  **Decision: inline the switch in `cmd/httpproxy/main.go`.** Per CLAUDE.md
  Code Organization Principles, single-consumer wiring belongs next to its
  consumer. `httpproxy` is the only consumer of the dialer-build dispatch;
  no other binary needs it (`bootstrap-mullvad` never constructs a runtime
  dialer). The factory function is a 12-line switch — extracting it to
  `internal/tunnel/` would be a shared-bootstrap-layer smell.

  So this task instead extends the `tunnel.Dialer` contract with the
  optional `DialerCloser` interface, and Task 6 wires the switch in `main.go`.

  Concretely for this task:
  1. Add `internal/tunnel/dialer.go` → `DialerCloser` interface (just the two
     lines above; same file as `Dialer`).
  2. NO factory function; the switch is part of Task 6 (main.go work).

  Update the `Dialer` interface's godoc to mention `DialerCloser` as the
  optional extension.

- **Acceptance Criteria:**
  - [ ] `internal/tunnel/dialer.go` declares `DialerCloser` immediately after
    `Dialer`.
  - [ ] Godoc on `DialerCloser` names `WireGuardDialer` as a current
    implementer and `SOCKS5Dialer` as one that intentionally does not
    implement it.
  - [ ] `go vet` clean; existing tests pass unchanged.
  - [ ] No factory function added (per the rationale above). If the engineer
    disagrees during review, the rejection MUST be discussed before
    introducing one; a single switch in main.go is the bar to beat.
- **Pitfalls & edge cases:**
  - Resist adding a "registry" or "kind → constructor" map. The codebase has
    exactly two implementations; a `switch` is shorter and easier to read.
  - The optional-interface pattern (`if c, ok := d.(DialerCloser); ok { c.Close() }`)
    works only because `SOCKS5Dialer` has no resources to release. If a v3
    SOCKS5 impl adds connection pooling, it implements `DialerCloser` too.
- **Complexity:** Easy

### Task 4: `internal/tunnel/wireguard/` — `WireGuardDialer` implementation

- **Description:**
  New package. One main file (`dialer.go`) plus tests.

  Public surface:
  ```go
  // Package wireguard provides a tunnel.Dialer backed by a userspace WireGuard
  // device (wireguard-go) routed through a gVisor netstack TUN. The dialer
  // owns the device's lifecycle and must be Close()d on shutdown.
  package wireguard

  // Options configures a WireGuardDialer. All fields are required unless
  // documented otherwise.
  type Options struct {
      PrivateKey                 string         // base64 (wgtypes format)
      LocalAddresses             []netip.Addr   // tunnel-side addresses for our end
      DNSServers                 []netip.Addr   // for the netstack resolver, typically [10.64.0.1]
      MTU                        int
      PeerPublicKey              string         // base64
      PeerEndpoint               string         // "host:port"; hostname resolved once via system DNS
      AllowedIPs                 []netip.Prefix
      PersistentKeepaliveSeconds int            // 0 disables
      Logger                     *slog.Logger   // bridge to wireguard-go's logger; required (use slog.Default if you must)
  }

  // NewDialer builds the WireGuard device and brings it up (administratively).
  // It does NOT block waiting for a handshake — the handshake is lazy and
  // happens on the first packet sent via DialContext. If construction fails
  // (key parse error, netstack init failure, IpcSet rejection), the device
  // is torn down before NewDialer returns the error.
  func NewDialer(opts Options) (*WireGuardDialer, error)

  // WireGuardDialer implements tunnel.Dialer and tunnel.DialerCloser.
  type WireGuardDialer struct {
      device *device.Device
      tun    tun.Device
      tnet   *netstack.Net
  }

  func (d *WireGuardDialer) DialContext(ctx context.Context, network, address string) (net.Conn, error)
  func (d *WireGuardDialer) Close() error
  ```

  Construction sequence inside `NewDialer`:
  1. Parse `PrivateKey` and `PeerPublicKey` via `wgtypes.ParseKey`. Bubble
     parse errors as plain `error` (they came through config validation
     already; this is defense-in-depth).
  2. Resolve `PeerEndpoint` host via `net.DefaultResolver.LookupIPAddr` (system
     DNS, control-plane leak accepted per locked decision). Result is `ip:port`;
     wireguard-go's UAPI accepts a literal IP-and-port in `endpoint=`.
  3. `tunDev, tnet, err := netstack.CreateNetTUN(opts.LocalAddresses, opts.DNSServers, opts.MTU)`.
  4. `wgLogger := newDeviceLogger(opts.Logger)` — adapter type defined below.
  5. `dev := device.NewDevice(tunDev, conn.NewDefaultBind(), wgLogger)`.
  6. Build the IpcSet string (see "UAPI format" below).
  7. `err := dev.IpcSet(uapi)`; on error tear down (`dev.Close()`,
     `tunDev.Close()`) and return.
  8. `err := dev.Up()`; on error tear down and return.
  9. Return `&WireGuardDialer{...}`.

  UAPI format (exact strings — golden-test this):
  ```
  private_key=<hex(privKey)>
  public_key=<hex(peerPub)>
  endpoint=<ip>:<port>
  persistent_keepalive_interval=<seconds>
  allowed_ip=<prefix1>
  allowed_ip=<prefix2>
  ...
  ```
  Trailing newline after the last line. No `replace_peers=true` line on first
  setup (we're building the config from scratch). Hex encoding via
  `hex.EncodeToString(key[:])` on the `[32]byte` underlying the `wgtypes.Key`.

  `DialContext` delegates straight to `tnet.DialContext(ctx, network, address)`.
  Wrap the error with `fmt.Errorf("wireguard: dial %s: %w", address, err)` so
  the proxy's existing "Upstream unreachable." mapping (Task 7 in v1) still
  fires.

  `Close()` calls `device.Close()` (which internally closes the TUN device).
  Must be safe to call twice; use `sync.Once` to guard.

  `newDeviceLogger` adapter: wireguard-go's `device.Logger` is a struct with
  two function fields — `Verbosef func(format string, args ...any)` and
  `Errorf func(format string, args ...any)`. Bridge to slog at `Debug` and
  `Error` respectively. Map `Verbosef` to `Debug` (NOT `Info`) — the lib is
  extremely chatty at the Verbose level; default `Info` operational logger
  drops them, debug surfaces them when an operator turns the level down.

- **Acceptance Criteria:**
  - [ ] Files: `internal/tunnel/wireguard/dialer.go`,
    `internal/tunnel/wireguard/dialer_test.go`,
    `internal/tunnel/wireguard/uapi.go` (separate small file for the IpcSet
    string builder — easier to golden-test), `internal/tunnel/wireguard/uapi_test.go`.

  ```go
  // only what bootstrap-mullvad needs: access-token exchange, device CRUD,
  // and the WireGuard relay list. No retries beyond a single 5xx attempt.
  package mullvad

  // DefaultBaseURL is api.mullvad.net over HTTPS.
  const DefaultBaseURL = "https://api.mullvad.net"

  func (c *Client) DeleteDevice(ctx context.Context, token Token, id string) error

  // WireGuard relays plus the gateway DNS IP. The endpoint requires no auth.
  func (c *Client) ListWireGuardRelays(ctx context.Context) (RelayList, error)

  // Token is the opaque bearer token returned by AccessToken. Use only via
  // package methods.
  type Token struct {
      Value  string
      Expiry time.Time
  }

  type Device struct {

      Name        string    // human-friendly auto-generated name
      Pubkey      string    // base64
      IPv4Address string    // CIDR, e.g. "10.66.0.5/32"
      IPv6Address string    // CIDR

  }

      IPv4Gateway string  // typically "10.64.0.1" — Mullvad's DNS
      IPv6Gateway string

      Hostname  string  // e.g. "se-sto-wg-001"
      IPv4Addr  string  // exterior endpoint IP
      PublicKey string  // base64
      Country   string  // "se" — parsed from "location": "se-sto"

      Owned     bool

      ErrInvalidAccount    = errors.New("mullvad: invalid account number")
      ErrMaxDevicesReached = errors.New("mullvad: max devices reached (delete one or use -replace-device)")
      ErrTokenExpired      = errors.New("mullvad: access token expired")
  )
  ```

  HTTP behaviour:
  - Default `http.Client.Timeout = 30 * time.Second`. Each request also
    accepts a `ctx` from the caller; both bound the request.
  - `Content-Type: application/json` and `Accept: application/json` on every
    request with a body.
  - On `5xx`, retry **once** after a 500ms sleep. On second failure, return.
  - On `4xx`, do NOT retry. Parse the response body if it's
    `{"code":"<UPPER_SNAKE>", "detail":"..."}` (mirroring `mullvadvpn-app`
    daemon's `rest::Error`). Map known codes to sentinels:
    - `INVALID_ACCOUNT` → `ErrInvalidAccount`
    - `MAX_DEVICES_REACHED` → `ErrMaxDevicesReached`
    - `INVALID_ACCESS_TOKEN` → `ErrTokenExpired`
  - On `401` without a recognised error code, return `ErrTokenExpired`.
  - Other errors: return a plain `error` containing method + path + status +
    truncated body (`body[:min(256, len(body))]`). NEVER include the
    request body in the error string (that would leak account numbers and
    public keys to logs).

  Logging:
  - Log one INFO per request after it completes: method, path, status,
    duration. No body. No account number. No token.
  - On non-2xx, log WARN with the same fields plus the truncated body.
  - The account number argument to `AccessToken` is NEVER passed to any log
    call. Reviewer Lens B verifies.

## Risks

- **(a) Mullvad API contract drift.** Endpoints, JSON field names, or error
  codes may change without notice. We've pinned the contract from the
  current `mullvadvpn-app` source and put the base URL behind a config var
  (`-base-url` flag on bootstrap, no override on the runtime daemon since
  it doesn't talk to Mullvad's API). Mitigation: when smoke test fails after
  some months, first action is `curl -v https://api.mullvad.net/app/v1/relays`
  and diff against `testdata/relays.json`.

- **(b) wireguard-go upstream API churn.** zx2c4 has historically renamed
  packages and changed function signatures (e.g. `device.NewDevice`'s
  signature changed in 2022 when `conn.Bind` replaced the older bind
  interface). Mitigation: pin the exact commit/tag in `go.mod`; never
  use `latest`. When upgrading, expect a half-day of breakage-chasing.

- **(c) gVisor netstack memory footprint.** The `wireguard/tun/netstack`
  package pulls in `gvisor.dev/gvisor`, which adds ~20MB to the binary and
  ~10-50MB to runtime RSS depending on traffic patterns. For the user's
  single-host workload, this is fine. Document in CLAUDE.md so a future
  "why is the binary 30MB" question is answered.

- **(d) DNS through tunnel times out silently.** If `AllowedIPs` is
  misconfigured (e.g. someone trims `0.0.0.0/0` to a /24 that doesn't cover
  `10.64.0.1`), DNS lookups via the tunnel queue indefinitely and the
  symptom is "every request returns 502 after `DialTimeout`". Mitigation:
  on dialer startup, attempt a non-blocking `tnet.LookupContextHost(ctx,
  "am.i.mullvad.net")` with a 5-second timeout. If it fails, log a WARN
  with a clear "DNS via tunnel is not working — check AllowedIPs and
  PeerEndpoint" message but do NOT fail startup (locked decision: handshake
  is lazy, treat DNS health as lazy too).

- **(e) Mullvad device limit (5 per account).** Bootstrap MUST surface
  MAX_DEVICES_REACHED. Default (`-replace-device` unset) prints a hint with
  a link to https://mullvad.net/account/ and exits non-zero. With
  `-replace-device` set, list → prompt → delete → retry. Non-TTY refuses
  the prompt and returns a clear error rather than hanging.

- **(f) Account number leak via shell history / `ps`.** Passing
  `-account=4567894567894567` shows up in `ps -ef` and in shell history.
  Mitigation: prefer `MULLVAD_ACCOUNT_NUMBER` env var; warn at startup
  when `-account` is used (Task 6 acceptance criterion). NEVER log the
  value in any code path.

- **(g) Private key on disk in plaintext.** `config/proxy.json` contains
  `private_key` as base64. File mode `0600` mitigates per-user exposure;
  full-disk encryption is the operator's responsibility. Document in the
  CLAUDE.md security section: "treat `config/proxy.json` like an SSH
  private key".

- **(h) Endpoint hostname DNS resolution leak at startup.** Resolving
  `se-sto-wg-001.relays.mullvad.net` via system DNS reveals to the local
  resolver that the user is connecting to Mullvad. Locked decision: accept
  the leak; document that the paranoid operator can hardcode the IP in
  `peer_endpoint`. The bootstrap tool already writes the IP (not the
  hostname) since it picks from `RelayList.Relays[i].IPv4Addr`, so this
  risk applies only to operators who hand-edit the config to use a
  hostname.

## Trade-offs

- **(a) Config discriminator (`kind`) vs. parallel `upstream_socks5` /
  `upstream_wireguard` blocks.** Chose: `kind` with nested blocks.
  Why: clean migration is cheap (one operator, pre-1.0), and "which kind is
  active" being a single source of truth eliminates the "but I set both"
  ambiguity. The dual-key approach would mean either "first non-empty wins"
  (surprising) or "exactly one must be set" (more validation than `kind`).
  Rejected: dual-key. Cost: existing operators (one) must regenerate
  `config/proxy.json` — the v1 default file is updated in-place to the new
  shape with `kind: socks5`, so the dev workflow keeps working with zero
  effort.

- **(b) Separate `cmd/bootstrap-mullvad/` binary vs. `httpproxy
  bootstrap-mullvad` subcommand.** Chose: separate binary.
  Why: lifecycles diverge radically (one-shot CLI vs. long-running
  daemon); CLAUDE.md explicitly allows multiple `cmd/<binary>/` directories
  and the Code Organization Principles steer toward "code by concern, not
  by launcher". A subcommand would require argument parsing dispatch and
  would carry the `mullvad`/`wgctrl` deps in the daemon binary even when
  not used. Cost: a second build target in the Makefile. Worth it for
  cleaner separation.

- **(c) Lazy handshake vs. fail-fast at startup.** Chose: lazy
  (per locked user decision). Why: aligns with v1's "SOCKS5 doesn't have
  to be up when proxy starts"; the proxy can recover when the tunnel
  recovers without restart. Cost: the first request after startup pays
  the handshake latency (a few hundred ms over a transcontinental link)
  and a misconfigured tunnel only surfaces under load. Mitigation: the
  warn from Risk (d).

- **(d) Inside-tunnel DNS (slower, leak-free) vs. outside-tunnel DNS
  (faster, leaky).** Chose: inside-tunnel via Mullvad's `10.64.0.1`
  (per locked user decision). Why: a VPN that leaks DNS to your ISP
  defeats half its purpose. Cost: every CONNECT-target hostname lookup
  pays the tunnel round-trip latency (vs. local cached lookup); for
  forward-HTTP that's even less of a concern because the upstream
  `http.Client` reuses connections per host. Document in the WG package's
  godoc.

- **(e) gVisor netstack vs. leaner alternatives.** Chose: gVisor netstack.
  Why: it's the only production-grade userspace TCP/IP stack in Go that
  wireguard-go integrates with cleanly. Alternatives — raw TUN syscalls
  (needs root, defeats the "no system changes" goal), pure-Go reimpl
  (months of work, security disaster) — are off the table. Cost: 20MB
  binary bloat, transitive gvisor dep. Acceptable for a server-side tool.

- **(f) Inlined dispatch in `main.go` vs. `internal/tunnel.NewDialer`
  factory.** Chose: inline switch.
  Why: CLAUDE.md's Code Organization Principles say single-consumer code
  belongs next to the consumer. The dispatch has exactly one caller
  (`httpproxy` main); pulling it into `internal/tunnel/` for symmetry's
  sake would be the "shared bootstrap layer" anti-pattern the project
  explicitly rejects. Cost: ~15 lines in `main.go`. Worth it for honesty
  about who actually uses it.

- **(g) Single `mullvad.Client` with method-per-endpoint vs. separate
  resource types (`Devices`, `Relays`).** Chose: flat `Client` with methods.
  Why: 5 methods, all share the same bearer-token plumbing; splitting into
  resource types triples the file count for no readability win. Cost: the
  `Client` struct grows methods over time; if it ever passes 15 methods,
  revisit. v2 has 5.

- **(h) No retry beyond once on 5xx.** Chose: single retry, 500ms backoff.
  Why: bootstrap is interactive — the operator is watching. Aggressive
  retries would mask Mullvad outages and frustrate the operator. One retry
  catches transient blips; further failures bubble up immediately.
  Reviewer Lens C: if you want exponential backoff for resilience, propose
  it but expect the trade-off to be defended.

- **(i) Test the WG dialer against a dead UDP peer vs. a live wireguard-go
  partner.** Chose: dead peer.
  Why: spinning up a second wireguard-go in-process doubles the test
  binary's memory (each device + netstack = ~10MB), tests `wireguard-go`'s
  internals more than our wrapper, and the production failure mode we
  actually care about ("Mullvad is unreachable") is exactly what a dead
  peer simulates. Cost: we don't catch wrapper bugs that only manifest
  with a real handshake (e.g. a typo'd UAPI line that wireguard-go
  silently ignores). Mitigation: the manual smoke test exercises the
  real path before any release is tagged.
