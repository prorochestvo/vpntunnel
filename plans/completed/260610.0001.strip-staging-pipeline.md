# Task Breakdown

## Overview

Drop the staging environment entirely. After this change there are two CI/CD
shapes:

- **CI (push to `main` / PRs against `main`)** — run lint, tests, and a `go build`
  sanity check. Nothing else. No image build, no GHCR push, no deploy.
- **Release (tag push `v*`)** — unchanged: lint + tests + image build + deploy to
  the `PRIME` (production) host behind the manual-approval gate.

The staging host, the `STAGE` GH Environment, the `:edge` and `:main-<sha>`
tags, the staging deploy job, and the staging-rollback runbook are all removed
from code and docs. `build-image.yml` stays — it is still called by
`release.yml` — but its preamble loses the staging reference.

## Assumptions

- The user no longer wants a staging host. If staging is ever resurrected, it
  will get its own dedicated workflow file in a future change — we are not
  preserving the wiring "just in case".
- The `STAGE` GH Environment, `:edge`, and `:main-<sha>` tags can be deleted by
  the operator after this PR lands. The workflow change is enough to stop
  producing them; cleanup of historical GHCR tags and the GH Environment is a
  separate operator task documented elsewhere.
- The new CI workflow file is named `ci.main.yml` per the user's choice. It
  replaces `staging.yml` outright; `staging.yml` is deleted.
- No code changes are needed in the Go tree — the daemon does not know or care
  which workflow ships it.

## Tasks

### Task 1: Replace `staging.yml` with `ci.main.yml`

- Description: Create `.github/workflows/ci.main.yml` with a single
  `lint-and-test` job that runs `make lint`, `make test`, and `go build` for
  `./cmd/httpproxy/` as a sanity check. Trigger on `push` to `main` and
  `pull_request` against `main`. Delete `.github/workflows/staging.yml`.
- Acceptance Criteria:
  - `ci.main.yml` runs lint + test + go build on push to main and on PRs.
  - No `build` or `deploy` job exists in the file.
  - No reference to `STAGE` environment, `SSH_*` secrets, or GHCR remain in
    `ci.main.yml`.
  - `staging.yml` no longer exists.
  - `concurrency:` group exists so rapid PR pushes supersede each other.
- Pitfalls & edge cases:
  - `go build` must use `CGO_ENABLED=0` and write to `./build/` per
    CLAUDE.md's build constraints. A bare `go build ./...` works too as a
    smoke (no output), but doing the real build catches release-shape issues.
  - Keep `cache: true` on `setup-go` — drops cold-start by ~30s.
  - Do not name the workflow `ci` only; the user picked `ci.main.yml` to leave
    room for sibling CI workflows later.
- Complexity: Easy

### Task 2: Tidy `build-image.yml` header

- Description: The reusable workflow still references "Reusable image-build
  workflow — shared by staging.yml and release.yml" and shows `main-abc1234` /
  `edge` examples. Update the preamble to describe only the release-tag
  use case.
- Acceptance Criteria:
  - Header comment no longer names `staging.yml`.
  - Example tags in comments are semver (`1.2.3`, `latest`) only.
  - The workflow body is unchanged — it is still a generic reusable workflow.
- Pitfalls & edge cases:
  - Do not over-prune: the workflow is still genuinely reusable, just from one
    caller for now. Keep the `workflow_call` interface description intact.
- Complexity: Easy

### Task 3: Strip staging refs from `CLAUDE.md`

- Description: Update the `Project State` overview, the `Deployment` block, and
  the SSH-key constraint to reflect single-environment reality (production
  only, ships on `v*` tags).
- Acceptance Criteria:
  - "Two environments, two hosts" sentence rewritten to one environment.
  - `Deployment` block lists only the release/`v*` tags (`X.Y.Z`, `X.Y`,
    `latest`); `:main-<sha>` and `:edge` lines removed.
  - The SSH-key constraint drops the "different values in staging vs
    production" requirement and just says one ed25519 key, scoped to the
    `PRIME` environment.
  - Layer table, file ordering, agent pipeline, planning workflow, error
    handling — all untouched.
- Pitfalls & edge cases:
  - The CI workflow is now `ci.main.yml`, not `staging.yml`. Mention it in
    the deployment block under the same heading shape so future readers find
    it.
  - Do not delete the section about CI entirely — CI on push/PR is still real,
    just narrower.
- Complexity: Easy

### Task 4: Strip staging refs from `README.md`

- Description: Remove the staging sections of `README.md`: the staging deploy
  bullet in the deploy overview, the GHCR-visibility paragraph that says "this
  affects both `:edge` (first `staging.yml` run) and ...", the server
  prerequisites for the staging host, the `STAGE` GH Environment setup, the
  staging SSH key generation flow, the staging rollback section, and any
  miscellaneous mention of `:edge` / `staging.yml` / `STAGE`.
- Acceptance Criteria:
  - Grepping `README.md` for `staging`, `STAGE`, `:edge`, `staging.yml`,
    `main-<7-char-sha>` returns no hits.
  - The deploy section reads as one-environment: production tags drive
    `release.yml`, which builds + deploys to the `PRIME` host.
  - Rollback flow describes only the production path (re-run an older
    `release.yml` run from the GH Actions UI).
  - The single-key SSH section explains there is exactly one ed25519 key,
    stored as `SSH_PRIVATEKEY` in the `PRIME` environment, not two.
  - Server-prerequisite walkthrough lists exactly one host.
- Pitfalls & edge cases:
  - There is a legacy paragraph about migrating from `STAGING_HOST` /
    `STAGING_USER` / etc. style secrets. Delete that paragraph too — its
    purpose ended when staging died.
  - Watch for words like "edge" used as a generic English word — do not strip
    those.
- Complexity: Medium

### Task 5: Verify

- Description: Run `make lint` and `make test` locally to confirm no Go code
  was disturbed. Visually re-grep `staging`, `STAGE`, `:edge`, `staging.yml`
  across the repo to confirm clean.
- Acceptance Criteria:
  - `make lint` exits 0.
  - `make test` exits 0.
  - `git grep -ni 'staging\|STAGE\|:edge\|staging.yml'` returns only this plan
    file (and possibly historic plans under `plans/completed/`, which we do
    not edit).
- Pitfalls & edge cases:
  - Historical plans in `plans/completed/` reference staging — they are
    history, leave them alone.
- Complexity: Easy

## Execution Order

1. Task 1 (new CI workflow, delete staging.yml)
2. Task 2 (build-image.yml header tidy)
3. Task 3 (CLAUDE.md)
4. Task 4 (README.md)
5. Task 5 (verify)

## Risks

- **README divergence.** `README.md` is long and densely cross-referenced.
  Stripping staging without leaving a dangling cross-reference is the
  highest-effort part of this plan. Mitigation: do the strip in one pass,
  re-read the resulting deploy/runbook section end-to-end before moving on.
- **Operator surprise.** An operator who already configured the `STAGE` GH
  Environment and a staging host will not get a warning when they next push to
  `main`. After this change, `main` pushes silently stop deploying to the
  staging host. Mitigation: this is the user's explicit intent; no further
  action.

## Trade-offs

- **Keeping `staging.yml` vs replacing with `ci.main.yml`.** The user picked
  `ci.main.yml`. Trade-off accepted: the new name is clearer (it is just CI),
  at the cost of any external bookmarks to the old workflow path.
- **Leaving `build-image.yml` in place.** The reusable workflow is no longer
  shared (only `release.yml` calls it). We keep it anyway — collapsing it
  inline into `release.yml` is a separate refactor and not what was asked for.
