# Task Breakdown

## Overview

Make the `:8888` API listener (`internal/transport/apiserver`) **dual-mode**: plain
HTTP when no TLS cert dir is configured, HTTPS (TLS 1.3) when one is. The `:8080`
forward proxy is **untouched** — it stays plain HTTP always. The mode is fixed at
launch: a single running instance is EITHER HTTP OR HTTPS, never both.

**Motivation.** Locally, macOS system curl (LibreSSL) cannot complete a TLS 1.3
handshake against our self-signed Ed25519/ECDSA cert. Running the API as plain HTTP
locally removes TLS from the dev/test loop entirely. **Production runs HTTPS only.**

**Mode trigger.** The `-tls-cert-dir` flag is the discriminator: **empty/unset → HTTP,
set → HTTPS**. The carrier through the layers is `apiserver.Options.Cert`
(`*tls.Certificate`): **`Cert == nil` ⇒ HTTP**, non-nil ⇒ HTTPS. No new boolean field
is added; the existing field's nil-ness is the signal.

**Dependency on plan 004.** This plan is the **next plan after** the config-schema
work (plan 004) and **depends on plan 004's Wave 4** ("TLS settings → CLI flags").
Plan 004 Wave 4 introduces the flags `-tls-cert-dir` / `-tls-hostname` / `-tls-ip-sans`,
the unexported `tlsOptions{ CertDir string; Hostname string; IPSANs []net.IP }` struct
and `parseTLSOptions(certDir, hostname, ipSANsRaw string) (tlsOptions, error)`, threads
a required positional `tls tlsOptions` through `run(configPath, tls)` /
`runWithOpts(configPath, tls, opts...)`, and rewires the apitls call to
`apitls.LoadOrGenerate(tls.CertDir, tls.Hostname, tls.IPSANs, opLog)`.

**The one 004 assumption this plan overrides.** Plan 004 Wave 4 registers
`-tls-cert-dir` with a **default of `/opt/vpntunnel/tls/`**. This plan **flips that
default to `""`** (empty = HTTP mode). That is the only 004 decision this plan changes.
Because the default flips to empty, the **prod systemd unit must pass `-tls-cert-dir`
explicitly** so production keeps booting HTTPS — Wave 2 bundles that unit edit.

**Cert handling (locked).**
- No `-tls-cert-dir` at all → run HTTP + a LOUD startup `WARN`:
  `API running WITHOUT TLS — bearer tokens are sent in plaintext; intended for
  loopback/dev only`.
- `-tls-cert-dir` set but the cert is invalid/unloadable → **FAIL startup** (never
  silently fall back to HTTP).
- "Missing" vs "invalid" in an explicitly-chosen dir: **generate-if-missing stays**
  (today's `apitls.LoadOrGenerate` behaviour — it generates a self-signed cert when
  `cert.pem`/`key.pem` are absent). An **unreadable dir / wrong perms / an
  existing-but-unparseable cert → FAIL**. Two of these three FAIL today; the
  existing-but-unparseable FAIL is a behaviour change in `apitls` (see Risks) owned by
  a sibling apitls touch — this plan only wires the resulting error as fatal, which it
  already is.

**Orthogonality verdict (requirement 4) — AUDITED, ALREADY ORTHOGONAL.** The audit of
the on-demand proxy handler chain found **no listener-protocol leak**. The target
scheme in `/v1/proxy/{scheme}/{rest...}` is derived **exclusively** from the
`{scheme}` path segment via `r.PathValue("scheme")`:
- sync path: `proxy.go:126` reads the segment, `proxy.go:196`
  (`targetStr := scheme + "://" + rest`) builds the outbound URL;
- async path: `proxy.go:267-269` reconstructs identically from the path values.

Grep for `r.TLS` across `internal/` + `cmd/` non-test code returns **zero behavioral
hits**. The only two `.URL.Scheme` reads in prod (`proxy.go:248`,
`forwarder.go:262`) are **log-only `slog` fields on the OUTBOUND request** whose URL
was already built from the path segment — observational, no coupling. No absolute-URL
reconstruction from `r.TLS`, no scheme-based redirect (`CheckRedirect` returns
`http.ErrUseLastResponse` at `forwarder.go:71,110` — redirects are never followed), no
Host rewriting tied to the listener protocol. **Conclusion:** an HTTP-mode instance
and an HTTPS-mode instance both serve BOTH target schemes identically and the code
already guarantees it. Therefore requirement 4 is realised as **test-only waves** (a
comment pinning the invariant + a 2x2 `{server mode} x {target scheme}` matrix), **not
a fix wave**.

**Deliverables, by wave:**
1. one nil-tolerant branch in `apiserver.StartOn` + its unit tests (the only transport
   source change);
2. flip 004's flag default to empty + systemd `ExecStart` edit;
3. branch `runWithOpts` startup into HTTP vs HTTPS, emit the WARN, keep invalid-cert
   fatal;
4. an in-code comment pinning the orthogonality invariant (comment-only);
5. test-harness plain-HTTP path (`waitHTTP`, HTTP-mode integration daemon, TLS-upstream
   helper) + HTTP-mode smoke + bad-cert FAIL test;
6. the 2x2 orthogonality matrix.

**No invented safety rails.** The only HTTP-mode guards are requirement 3's WARN (no
cert) and FAIL (invalid cert). No non-loopback refusal, no `-tls=off` boolean, nothing
else.

## Assumptions

- **Plan 004 has landed first**, specifically its **Wave 4** ("TLS settings → CLI
  flags"). All of `-tls-cert-dir` / `-tls-hostname` / `-tls-ip-sans`, `tlsOptions`,
  `parseTLSOptions`, the threaded positional `tls tlsOptions` arg on
  `run`/`runWithOpts`, and the apitls rewire exist before this plan starts. **This plan
  overrides exactly one 004 assumption: the `-tls-cert-dir` default flips from
  `/opt/vpntunnel/tls/` to `""`.** Wave 1 (transport) is the sole exception — it does
  not depend on 004 because `apiserver.Options.Cert` already exists today; 004 and
  Wave 2/3 depend on Wave 1, not the reverse.
- **`Cert == nil` ⇒ HTTP, non-nil ⇒ HTTPS.** This nil-ness, fixed at construction, is
  the entire HTTP-vs-HTTPS signal threaded from the flag through `runWithOpts` into
  `apiserver.Options` and consumed in `StartOn`. No new `Plaintext bool` is introduced.
- **`apitls.LoadOrGenerate` keeps its signature**
  `(certDir, hostname string, ipSANs []net.IP, log *slog.Logger) (*tls.Certificate, string, error)`
  and its generate-if-missing behaviour. Making an existing-but-unparseable cert FAIL
  (rather than silently regenerate) is a separate apitls-area change (see Risks); this
  plan's negative test uses the wrong-perms path, which FAILs deterministically today.
- **Environment split:** **prod = HTTPS only** (systemd passes `-tls-cert-dir`);
  **local/dev = HTTP** (no flag). **HTTP mode exposes the three API bearer tokens
  (`X-Vpntunnel-Token`) in plaintext** on the wire — accepted because the API binds
  loopback (`127.0.0.1:8888`) for dev/testing and the WARN makes the exposure loud.
  The `:8080` forward proxy's own auth is unaffected (it is plain HTTP regardless and
  out of scope).
- **No new safety rails.** Only the WARN (no cert) and the FAIL (invalid cert) gate
  startup. No loopback check on `cfg.API.Listen` is added.

  - This wave compiles and passes **without plan 004** (the `Cert` field already
    exists) and imports no 004 symbol.
- **Complexity:** Medium — **dependsOn:** none (self-contained; the `Options.Cert`

### Wave 2: Flip `-tls-cert-dir` default to empty (HTTP-by-default) + systemd `ExecStart`

- **Title:** Make `-tls-cert-dir` default empty so unset ⇒ HTTP mode; pass it
  explicitly in the prod unit.
- **Goal (one line):** override plan 004 Wave 4's `/opt/vpntunnel/tls/` default to
  `""`; an empty cert dir is the HTTP-mode trigger; production keeps HTTPS via an
  explicit flag in the systemd unit.
- **Files touched (exact):**
  - `cmd/vpntunnel/main.go`
  - `configs/vpntunnel.service`
- **Change spec (exact):**
  - `main.go`: change the 004-Wave-4 flag registration
    `flag.StringVar(&tlsCertDir, "tls-cert-dir", "/opt/vpntunnel/tls/", "...")`
    to default `""`:
    `flag.StringVar(&tlsCertDir, "tls-cert-dir", "", "directory holding the API TLS`
    `cert/key; empty runs the API as plain HTTP (loopback/dev only). Relative resolves`
    `against CWD.")`. Only the default literal and the usage string change. The variable
    name `tlsCertDir` and the `parseTLSOptions(tlsCertDir, tlsHostname, tlsIPSANsRaw)`
    call site are unchanged.
  - `main.go`, `parseTLSOptions` (added by 004 Wave 4): **add an early empty-dir
    branch** so empty does NOT hit `filepath.Abs("")` (which returns the cwd and
    silently re-enables HTTPS).
    **SAN parsing — inline, do NOT reference a helper.** Plan 004 Wave 4 specifies
    `parseTLSOptions` as a single function (validate hostname → resolve `certDir` via
    `filepath.Abs` → parse IP SANs); it does **not** extract a reusable SAN-parsing
    sub-function. So the early branch must parse SANs **inline**, duplicating the same
    loop the non-empty path uses: split `ipSANsRaw` on comma, `strings.TrimSpace` each
    field, skip empties, `net.ParseIP` each, and return an error on a nil parse. That
    is ~5 trivial lines.
    ```go
    if certDir == "" {
        // empty cert dir is the HTTP-mode trigger: leave CertDir empty (do NOT
        // resolve it to an absolute path, which would yield the cwd and silently
        // re-enable HTTPS). Hostname stays required but its only use is the cert
        // SAN, so it is harmless when no cert is generated.
        var ipSANs []net.IP
        for _, raw := range strings.Split(ipSANsRaw, ",") {
            raw = strings.TrimSpace(raw)
            if raw == "" {
                continue
            }
            ip := net.ParseIP(raw)
            if ip == nil {
                return tlsOptions{}, fmt.Errorf("invalid -tls-ip-sans entry %q", raw)
            }
            ipSANs = append(ipSANs, ip)
        }
        return tlsOptions{CertDir: "", Hostname: hostname, IPSANs: ipSANs}, nil
    }
    ```
    Match 004 Wave 4's actual SAN-parse loop byte-for-byte (same split/trim/skip/parse
    behaviour and the same error wording style) so the two paths stay consistent. Do NOT
    fork hostname validation. Hostname stays required in HTTP mode (avoids a second
    behavioural fork; the value is simply unused).
    **Alternative (only if 004 is not yet frozen):** extract a package-private
    `parseSANs(raw string) ([]net.IP, error)` helper in 004 Wave 4 and call it from both
    the empty and non-empty branches. Pick ONE approach — inline duplication (default,
    self-contained in this plan) OR the 004 helper extraction (requires amending 004) —
    and apply it consistently; do not leave a dangling reference to a helper that 004
    never created.
  - `configs/vpntunnel.service`, `ExecStart` (line 20): **before**
    `ExecStart=/opt/vpntunnel/vpntunnel -config /opt/vpntunnel/configs/proxy.json`
    **after**
    `ExecStart=/opt/vpntunnel/vpntunnel -config /opt/vpntunnel/configs/proxy.json -tls-cert-dir /opt/vpntunnel/tls/`.
    Add a one-line comment directly above ExecStart:
    `# -tls-cert-dir is REQUIRED in production: its absence runs the API as plain HTTP.`
- **Tests:**
  - `cmd/vpntunnel/main_test.go`, `TestParseTLSOptions` (added by 004 Wave 4): **add a
    subtest** `"empty cert dir yields HTTP-mode tlsOptions"` — call
    `parseTLSOptions("", "localhost", "127.0.0.1")`; assert `err == nil`,
    `got.CertDir == ""` (NOT the cwd, NOT `os.Getwd()`), `got.Hostname == "localhost"`,
    `len(got.IPSANs) == 1`. This is THE regression guard against the `filepath.Abs("")`
    footgun. No new top-level test function (subtest of the existing
    `TestParseTLSOptions`).
- **Acceptance criteria:**
  - [ ] `./build/vpntunnel -h` shows `-tls-cert-dir` defaulting to empty.
  - [ ] `parseTLSOptions("", "localhost", "127.0.0.1")` returns `CertDir == ""` (new
        subtest), not the cwd.
  - [ ] `configs/vpntunnel.service` ExecStart passes `-tls-cert-dir /opt/vpntunnel/tls/`
        and carries the REQUIRED-in-production comment.
  - [ ] `make test` green with `-race`.
- **Pitfalls & edge cases:**
  - **`filepath.Abs("")` returns the CWD, not `""`** — miss the empty branch and every
    dev run is silently HTTPS again and the whole feature is a no-op. THE trap.
  - **Inline-SAN branch adds no new imports.** `net`, `strings`, and `fmt` are already
    imported in `main.go` (the existing `resolveAuthToken` / inline IP-SANs loop use

    re-import. Match 004 Wave 4's SAN-parse loop and its `fmt.Errorf` wording so the two
    paths read identically; never discard the `ParseIP`-nil case (no-skipped-errors
    rule).
  - **Forgetting the systemd edit ships an HTTP API to prod** (plaintext bearer tokens

  - This wave alone does not branch the listener (Wave 3 does). It must **not** be

- **Complexity:** Easy — **dependsOn:** plan 004 Wave 4 (introduces the flag,

## Risks

- **`filepath.Abs("")` → cwd (Wave 2).** The single highest-risk line. If
  `parseTLSOptions` does not special-case empty, every dev run silently re-enables
  HTTPS and the feature is inert. Guarded by Wave 2's dedicated `TestParseTLSOptions`
  subtest. (004 created `parseTLSOptions` but never exercised empty input.)
- **Prod ships HTTP by accident (Wave 2).** Flipping the default to empty without the
  systemd `ExecStart` edit exposes the three API bearer tokens in plaintext on the host.
  Mitigation: Wave 2 bundles the unit edit; the deploy verify step already curls
  `https://127.0.0.1:8888/v1/admin/health` (CLAUDE.md → Deployment), so an accidental
  HTTP prod boot would FAIL that curl loudly. **Flag for the reviewer:** confirm the
  deploy smoke-check stays `https://` (it must — prod is HTTPS) so the existing health
  curl is the backstop.
- **"Invalid existing cert → FAIL" is NOT today's apitls behaviour (sibling change).**
  `apitls.LoadOrGenerate` (`apitls/apitls.go:67-83`) calls `loadAndVerify`, which
  returns a *sentinel* error on BOTH a `tls.LoadX509KeyPair` parse failure
  (`apitls.go:137`) AND a regen condition (`apitls.go:154`). `LoadOrGenerate` swallows
  ALL of these (`apitls.go:77-80`) and falls through to `generate()`, which
  **overwrites** the files. So an explicitly-chosen dir with a corrupt `cert.pem` is
  silently regenerated, not failed. Making it FAIL requires an apitls change
  (distinguish "regenerate-because-stale/hostname" from "fail-because-unparseable") and
  is owned by a sibling apitls touch — **NOT this plan**. This plan's contract ("any
  error from `LoadOrGenerate` → fatal `load tls cert`") is already satisfied by Wave 3's
  `if err != nil { return … }`. The Wave 5 bad-cert subtest therefore uses the
  wrong-perms (`0777`) path — which FAILs deterministically TODAY via `ensureCertDir`'s
  `publicerror` (`apitls.go:121`) — and notes the unparseable-cert FAIL as gated on the
  sibling change. **Cross-reference:** the apitls area must add the
  FAIL-on-unparseable behaviour plus its own test; this plan only consumes the resulting
  fatal error.
- **Transport coupling (Waves 1 ↔ 3).** Wave 3 passes `Cert: nil`; if Wave 1 is not in
  the tree, `server.go:148` (`Certificates: []tls.Certificate{*s.opts.Cert}`)
  nil-derefs and panics on HTTP-mode boot. Mitigated by the Execution Order
  (Wave 1 first). The signal is the existing `Cert *tls.Certificate` field's nil-ness —
  no `Plaintext bool` is introduced, so there is nothing for the synthesizer to
  reconcile across areas.
- **Token plaintext in HTTP mode (accepted).** HTTP mode sends `X-Vpntunnel-Token` in
  the clear. Accepted: the API binds loopback for dev/testing, the WARN is loud, and
  prod runs HTTPS. No mitigation beyond the WARN — adding a non-loopback refusal would
  be an invented rail and is explicitly out of scope.
- **Async matrix wires through `ZoneRoutingForwarder` (pre-existing harness gap).** The
  legacy `TestProxyAsync*` tests inject a raw `asyncjob.Forwarder` directly into
  `asyncjob.NewPool` (`integration_test.go:189-197`), bypassing the
  `ZoneRoutingForwarder` that production interposes (`main.go:279-281`). Left as-is, the
  Wave 6 async cells would prove orthogonality on a path production never runs. This plan
  closes the gap **for the matrix only**: the async cells inject
  `handlers.NewZoneRoutingForwarder(fakeWorkingRouter{}, tlsTrustingRawForwarder{...})`
  so they exercise the production async wiring (header-strip + `X-Tunnel-Id` route +
  `RawForwarder`). The base type therefore satisfies `handlers.RawForwarder`
  (5-arg `ForwardRaw`), not a bare `asyncjob.Forwarder`. The legacy `TestProxyAsync*`
  tests are intentionally NOT re-wired — that is a separate cleanup, out of scope here.

## Trade-offs

- **Empty-flag trigger over an explicit `-tls=off` boolean.** Reusing
  `-tls-cert-dir`'s emptiness is the locked design and needs no new flag; the cost is
  the `filepath.Abs("")` footgun (guarded by a Wave 2 test). An explicit boolean would
  be self-documenting but adds a second flag and a redundant state (cert-dir-set +
  tls-off). Chose the locked single-trigger design.
- **`Cert == nil` as the mode signal over a new `Options` field.** The existing
  `*tls.Certificate` field already carries everything `StartOn` needs; its nil-ness is
  a zero-cost discriminator. Adding a `Plaintext bool` would introduce a redundant,
  desynchronisable second source of truth (cert non-nil + Plaintext true → ambiguous).
  Chose nil-ness.
- **Behavioural mode assertion over a logger seam.** Wave 5 asserts HTTP mode by
  reachability (plain HTTP works, TLS to the same port fails) rather than scraping the
  WARN string from `runWithOpts`, to avoid adding a `withOpLog` production seam purely
  for a test. The transport-level `tls=false` listening-log assertion (Wave 1) covers
  the log surface where a seam already exists. Cost: the exact WARN wording is not
  regression-tested at the composition-root level. Accepted — the wording is a one-line
  literal in Wave 3 and over-testing log strings is brittle.
- **Test-only orthogonality (matrix + comment) over a fix wave.** The audit found the
  proxy path already orthogonal (target scheme is path-only; zero behavioral `r.TLS`
  hits), so there is nothing to fix. Investing in a 2x2 matrix + an in-code invariant
  comment buys regression protection against a future leak at the cost of test
  surface — cheaper and safer than refactoring code that is already correct.
- **Hostname stays required in HTTP mode.** Avoids a second behavioural fork in
  `parseTLSOptions`; the value is simply unused when no cert is generated. Cost: an
  operator running HTTP mode must still pass (or accept the default) `-tls-hostname`.
  Negligible — `localhost` is the default.
