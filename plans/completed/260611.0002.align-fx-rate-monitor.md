# Task Breakdown

## Overview

Three small alignment tasks bringing `httpproxy` in line with the sibling
`fx_rate_monitor` deploy conventions, finishing the loose ends left by the
Docker-to-systemd cutover (`plans/completed/260611.0001.drop-docker-restore-bypass.md`):

1. Strip leftover Docker scaffolding from the `Makefile` — variables, targets,
   `.PHONY` entries, and the header comment paragraph all still reference a
   runtime and Dockerfile that no longer exist.
2. Extend `make init` so the operator-side seeding step also ships the systemd
   unit to `/tmp/httpproxy.service` on the host, mirroring `fx_rate_monitor`'s
   `deploy_environment` pattern. Final install (`mv` to `/etc/systemd/system/`,
   `daemon-reload`, `enable --now`) stays manual and operator-driven.
3. Add SHA256 integrity verification to `release.yml` between the binary scp
   and the on-host atomic swap, defending against corrupted transfers.

All three changes are config-only; no Go code is touched, no behaviour on the
hot path changes.

## Assumptions

- The systemd unit lives at `configs/httpproxy.service` in this repo (matches
  the README's `sudo cp /opt/httpproxy/configs/httpproxy.service` step — it is
  shipped today by other means and lives under `configs/`).
- The SSH user invoked by `make init` (the operator's interactive SSH session
  to `be-happy.kz`) has write access to `/tmp/` — the standard worldwide-writable
  scratch dir, no sudo needed for the scp step itself.
- `release.yml` runs on `ubuntu-latest`, which ships `sha256sum` and `coreutils`
  by default; no extra `apt-get install` needed.
- The deploy host runs `coreutils` (Debian/Ubuntu): `sha256sum -c` is present.
- `proxy.example.json` overwriting a customized production `proxy.json` during
  `make init` is a known, accepted risk already documented in the existing
  comment block above `init`; we extend that warning rather than rework the
  target's overwrite semantics.

### Task 3: SHA256 verification in `release.yml`

- **Description:** Add a checksum-and-verify pair around the existing scp +
  on-host swap in `.github/workflows/release.yml`. Mirrors `fx_rate_monitor`'s
  `stage.yml` lines 111–143 pattern, adapted for our single-binary deploy.
  Concrete edits:
  1. In the `Build binary` step (or a new step immediately after it), generate
     the SHA256 of `./build/httpproxy`. The output must already encode the
     remote-side filename `httpproxy.new` so the on-host `sha256sum -c` finds
     it directly. Two equivalent approaches; we pick approach #1 (file-based,
     mirrors `fx_rate_monitor`):
     ```yaml
     - name: Compute SHA256 of binary
       # Generate the sum file with the remote-side filename embedded so
       # `sha256sum -c` on the host matches against ./httpproxy.new directly,
       # not against the local ./build/httpproxy path that `sha256sum` would
       # write by default.
       run: |
         set -euo pipefail
         (cd ./build && sha256sum httpproxy | sed 's| httpproxy$|  httpproxy.new|') > ./build/httpproxy.new.sha256
         cat ./build/httpproxy.new.sha256
     ```
     Note: `sha256sum` writes `<hash>  <file>` (two spaces) on Linux. The
     `sed` substitution preserves that exact two-space separator.
  2. Extend the existing `Copy binary to host` step (or add a new one
     immediately after it) to scp the `.sha256` file as well:
     ```yaml
     - name: Copy SHA256 file to host
       env:
         REMOTE_DIR: ${{ vars.REMOTE_DIR }}
         SSH_HOSTNAME: ${{ vars.SSH_HOSTNAME }}
         SSH_HOSTPORT: ${{ vars.SSH_HOSTPORT }}
         SSH_USERNAME: ${{ vars.SSH_USERNAME }}
       run: |
         set -euo pipefail
         scp -i ~/.ssh/deploy_key \
           -o ConnectTimeout=30 \
           -P "$SSH_HOSTPORT" \
           ./build/httpproxy.new.sha256 \
           "$SSH_USERNAME@$SSH_HOSTNAME:$REMOTE_DIR/httpproxy.new.sha256"
     ```
  3. Add a new `Verify SHA256 on host` step between `Copy SHA256 file to host`
     and `Deploy on host`:
     ```yaml
     - name: Verify SHA256 on host
       # If the scp transfer was truncated/corrupted, sha256sum -c exits
       # non-zero and aborts the deploy BEFORE the atomic swap. The .sha256
       # file is removed in both branches so a stale checksum never confuses
       # a subsequent deploy.
       env:
         REMOTE_DIR: ${{ vars.REMOTE_DIR }}
         SSH_HOSTNAME: ${{ vars.SSH_HOSTNAME }}
         SSH_HOSTPORT: ${{ vars.SSH_HOSTPORT }}
         SSH_USERNAME: ${{ vars.SSH_USERNAME }}
       run: |
         set -euo pipefail
         timeout 30s ssh -i ~/.ssh/deploy_key \
           -o ConnectTimeout=30 \
           -p "$SSH_HOSTPORT" "$SSH_USERNAME@$SSH_HOSTNAME" bash -s <<EOF
         set -euo pipefail
         cd "$REMOTE_DIR"
         if ! sha256sum -c httpproxy.new.sha256; then
           echo "ERROR: SHA256 mismatch on httpproxy.new — aborting deploy"
           rm -f httpproxy.new httpproxy.new.sha256
           exit 1
         fi
         rm -f httpproxy.new.sha256
         EOF
     ```
  4. The existing `Deploy on host` step needs no change — it already operates
     on `httpproxy.new` after verification has cleaned up the `.sha256` file.
     Optional belt-and-suspenders: add `rm -f "$REMOTE_DIR/httpproxy.new.sha256"`
     to the failure path of `Deploy on host`'s `dump_diagnostics` function so
     a partial run never leaks the sum file; only do this if it is a one-line
     addition to the existing diagnostics block — do not redesign the block.
- **Acceptance Criteria:**
  - [ ] `grep -n -i 'sha256' .github/workflows/release.yml` returns at least
        three hits (compute, scp, verify; cleanup is inline in the verify
        step).
  - [ ] `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/release.yml'))"`
        exits 0.
  - [ ] Step order in the `deploy` job is: Validate tag → Checkout → setup-go
        → Build binary → Compute SHA256 → Assert env vars → Set up SSH client
        → Copy binary to host → Copy SHA256 file to host → Verify SHA256 on
        host → Deploy on host → Workflow summary → Notify success → Notify
        failure.
  - [ ] Simulated corrupted-binary scenario: if `httpproxy.new` is mutated on
        the host after the scp but before verification, the `Verify SHA256 on
        host` step exits non-zero, the workflow stops before `Deploy on host`,
        and `httpproxy.new` plus `httpproxy.new.sha256` are removed.
  - [ ] No change to the on-host atomic swap, `httpproxy.prev` rollback, or
        `/healthz` polling logic in `Deploy on host`.
- **Pitfalls:**
  - `sha256sum`'s output format is `<hash><space><space><filename>`. The
    `sed` rewrite MUST preserve both spaces — using a single space breaks
    `-c`. Document this in the comment above the compute step.
  - The verify step uses an UNQUOTED heredoc (`<<EOF`, not `<<'EOF'`) so that
    `$REMOTE_DIR` interpolates on the runner. Inside the heredoc, the `EOF`
    delimiter must sit at column 0 — same convention as the existing
    `Deploy on host` step. Do not indent the `EOF`.
  - `timeout 30s` on the ssh wrapper guards against a hung connection; copy
    the timeout idiom from `Deploy on host` (`timeout 3m ssh …`) but tighten
    it because verification is local (no curl polling, no systemd restart).
  - Do not fold this into the `Deploy on host` heredoc. Keeping verification
    in its own step means a corrupted-binary failure surfaces in the GH
    Actions UI as a distinct failed step, not as a generic "deploy script
    exited 1".
  - The `.sha256` file is non-sensitive; no need for `chmod 0600`.
  - If the runner picks a different `sha256sum` (e.g. BSD `shasum -a 256`
    on macOS runners), output format diverges. `runs-on: ubuntu-latest`
    pins GNU coreutils so this is fine; do not switch to macOS runners
    without revisiting the sed pattern.
- **Complexity:** Easy

## Execution Order

Tasks are independent — no task reads or writes state another task touches —
but execute and review them in the listed order for clarity:

1. **Task 1** first. Smallest change, narrowest blast radius, easy to verify.
2. **Task 2** second. Touches both `Makefile` and `README.md`; reviewers can
   see the `Makefile` change in isolation from Task 1's deletions.
3. **Task 3** last. Workflow change carries the highest deploy risk; landing
   it after the local-only changes keeps unrelated noise out of the deploy
   review.

All three may be batched into a single commit at the engineer's discretion,
since they share the theme "align with fx_rate_monitor". A single commit also
matches `260611.0001.drop-docker-restore-bypass.md`'s pattern.

## Risks

- **Workflow regression (Task 3).** A typo in the heredoc or sed pattern
  breaks every subsequent `v*` tag deploy. Mitigation: the engineer runs
  `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/release.yml'))"`
  locally before pushing; the first post-merge deploy is observed end-to-end.
- **README drift (Task 2).** The README references the manual unit-install
  step in two places (first-time-setup AND the v5→v6 cutover note). Updating
  only one leaves the other stale. Mitigation: explicit acceptance criterion
  lists both call sites.
- **Comment-churn temptation (Task 1).** While in `Makefile` it is easy to
  "improve" the `clean` comment or the `init` comment beyond the diff. Stay
  inside the budget — this is an alignment plan, not a comment refactor.
- **Operator confusion (Task 2).** Existing operators may already have a
  customised `/etc/systemd/system/httpproxy.service`. Running `make init`
  writes only to `/tmp/`, so existing installs are untouched until the
  operator chooses to `sudo mv`. The comment block must call this out so
  an operator doesn't worry their running unit was clobbered.

## Trade-offs

- **`sha256sum -c` file vs. inline `echo … | sha256sum -c -`.** Picked the
  file approach because it mirrors `fx_rate_monitor`'s working pattern. The
  inline approach is one fewer scp but requires more shell quoting inside the
  heredoc, which is fragile. File-based wins on robustness; the scp of a
  ~70-byte file is a negligible cost vs. the multi-MB binary.
- **`make init` ships the unit; the workflow does not.** Mirrors
  `fx_rate_monitor`. Rationale: unit-file changes are rare (`PATH`,
  `ReadWritePaths`, env-file location) and warrant the operator's eyes on a
  `daemon-reload`. Automating it would silently restart with a changed
  contract, e.g. a new `ReadWritePaths` entry the operator hasn't provisioned.
- **Belt-and-suspenders `rm -f` in `clean` dropped (Task 1).** The
  `bootstrap-mullvad` binary has been gone since v3; the `httpproxy` binary
  is built to `./build/` and `rm -rf ./build` covers it. Keeping the
  belt-and-suspenders line documents an obsolete failure mode and invites
  questions about why we are guarding paths the Makefile itself doesn't
  produce. Risk of regression is zero because the Makefile pins `-o
  ./build/<name>` on every `go build` invocation; if a future contributor
  drops the `-o` flag, the right fix is the lint check, not a `clean` rule.
- **Single commit vs. three commits.** Either is acceptable; the
  Docker-drop plan landed as a single commit and reviewers preferred that
  granularity. Engineer's discretion.
