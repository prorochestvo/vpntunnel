# Task Breakdown

## Overview

Add a `make generate-vpn-config` target backed by a new single-consumer launcher
`cmd/generatevpnconfig/` — an interactive operator CLI that (1) generates a
WireGuard keypair locally via `wgtypes.GeneratePrivateKey()` (zero new deps;
`golang.zx2c4.com/wireguard/wgctrl` is already in `go.mod`), (2) prints the public
key plus step-by-step Mullvad onboarding instructions, (3) prompts the operator
field-by-field over stdin for the remaining wg-quick fields, validating and
re-prompting on each, (4) assembles a wg-quick `.conf` and writes it atomically at
mode 0600 to `configs/tunnels/<name>.conf`, and (5) prints (does not mutate) the
snippet to add under `upstream.configs` in `configs/proxy.json`. The private key
and PSK must never be logged or printed except into the final `.conf` file. The
emitted `.conf` must round-trip cleanly through the existing
`internal/tunnel/wireguard/wgconf` parser. The tool refuses to run without a TTY so
it can never hang in CI/systemd.

Motivation: today an operator must obtain a full wg-quick `.conf` from the provider
and hand-edit it; key handling is error-prone and there is no guided, validated
local flow. This tool gives a guarded, validated path that keeps the private key on
the machine and produces a file the proxy already knows how to parse.

## Assumptions

- `wgtypes` (`golang.zx2c4.com/wireguard/wgctrl/wgtypes`) is reachable as a direct
  import; `wgctrl` is already a dependency, so this adds no new module. (Verified:
  `go.mod` lists `golang.zx2c4.com/wireguard/wgctrl v0.0.0-20241231184526-...`.)
- The wgconf parser contract is authoritative for field names and format
  (verified against `internal/tunnel/wireguard/wgconf/wgconf.go`):
  section headers are exactly `[Interface]` and `[Peer]`; keys are
  case-insensitive; required keys are `PrivateKey`, `Address` (in `[Interface]`)
  and `PublicKey`, `Endpoint` (in `[Peer]`); `DNS` and `AllowedIPs` are optional
  with defaults `10.64.0.1` and `0.0.0.0/0, ::/0`; inline `#` comments and
  surrounding whitespace are stripped by the parser.
- The module path is `vpntunnel` (verified in `go.mod`); the new package imports
  the parser as `vpntunnel/internal/tunnel/wireguard/wgconf` for the round-trip
  test.
- TTY detection is acceptable via `(os.Stat of the *os.File).Mode()&os.ModeCharDevice != 0`
  on the real stdin, threaded behind a seam so tests bypass it. No new dep
  (e.g. `golang.org/x/term`) is introduced.
- `configs/tunnels/` already exists in the repo (only `.gitkeep` tracked, dir
  gitignored). The tool will create it with mode 0700 if missing.
- `Address` is required and validated as a single-host prefix; the operator may
  enter `10.x.x.x/32` or a bare `10.x.x.x` (the tool normalizes a bare host to
  `/32` before writing, since the parser expects a CIDR via `netip.ParsePrefix`).
- The chosen conf name is restricted to a safe basename (no path separators, no
  `..`, no leading dot) to keep writes inside `configs/tunnels/`.

## Tasks

### Task 1: Create `cmd/generatevpnconfig/` package skeleton, flags, and a testable `run()` seam
- Description: Create `cmd/generatevpnconfig/main.go` with a thin `main()` that
  builds the real dependencies and calls a package-private
  `run(cfg runConfig) error`, exiting non-zero on error. `main()` owns: flag
  parsing (`-force` bool to allow overwrite; `-dir` string defaulting to
  `configs/tunnels` so tests can redirect; nothing else), wiring `os.Stdin` /
  `os.Stdout`, and the real TTY check. Define a `runConfig` struct carrying
  `in io.Reader`, `out io.Writer`, `dir string`, `force bool`, and an
  `isTTY func() bool` seam so `run()` never touches the real terminal in tests.
  The file gets a `// Command generatevpnconfig ...` doc comment (per CLAUDE.md,
  cmd entry points use Command, not Package). Follow File Declaration Order:
  exported/`main` first, then `run`, then the `runConfig` struct, then unexported
  helpers. No section-divider comments.
- Acceptance Criteria:
  - `go build ./cmd/generatevpnconfig/` (with `CGO_ENABLED=0`) succeeds; no binary
    is dropped in the repo root (build only via `-o ./build/...` if ever built —
    the Make target uses `go run`).
  - `run()` accepts injected `io.Reader`/`io.Writer` and `isTTY` so it can be
    driven entirely from a test with no real TTY.
  - When `isTTY()` returns false, `run()` returns a non-nil error whose message
    clearly states the tool is interactive and requires a terminal; it prompts for
    nothing and reads nothing from `in`.
  - `gofmt -l` clean and `go vet` clean.
- Pitfalls & edge cases: do not call `os.Exit` inside `run()` (untestable) — only
  in `main()`. Do not read from stdin before the TTY check passes, or a piped CI
  invocation could still consume input. Keep `runConfig` fields unexported-package
  but accessible within the package; it is not part of any public API.
- Complexity: Easy

### Task 2: Local keypair generation and operator instructions (no key leakage)
- Description: In `run()`, immediately after the TTY guard, generate a keypair with
  `key, err := wgtypes.GeneratePrivateKey()` and derive `pub := key.PublicKey()`.
  Write a clear, numbered instruction block to `out` containing only the public key
  (`pub.String()`): tell the operator to open mullvad.net/account, add this public
  key under WireGuard key management, pick a server, and note the assigned
  `Address`, the server `Peer PublicKey`, and the `Endpoint` (from
  mullvad.net/en/servers or the generated config). Keep `key` only in a local
  variable for later assembly. Never pass `key.String()` to any log/print call or
  `fmt` directive other than the final `.conf` assembly in Task 5.
- Acceptance Criteria:
  - The public key is printed exactly once, in base64 (`pub.String()`), with
    surrounding human instructions naming Mullvad account + server steps.
  - Grep of the printed output in tests confirms the private key string
    (`key.String()`) appears nowhere in `out`.
  - No `_`-discarded errors: `GeneratePrivateKey()`'s error is checked and
    returned.
- Pitfalls & edge cases: `wgtypes.Key` has a `String()` that base64-encodes both
  private and public forms — printing the wrong one leaks the secret. The private
  key variable must not be captured in any closure that also writes to `out`.
- Complexity: Easy

### Task 3: Field-by-field interactive prompt + validation with re-prompt
- Description: Implement an unexported helper that prompts a single field and loops
  until valid input or EOF. Read line-by-line with a `bufio.Scanner` over `in`.
  Prompt order and validation:
  1. conf name/label (e.g. `mullvad-se-sto-wg-001`) — required; validate as a safe
     basename: non-empty, matches `^[A-Za-z0-9._-]+$`, not `.`/`..`, no path
     separators. Re-prompt on violation.
  2. `Address` (assigned CIDR, e.g. `10.66.x.x/32`) — required; normalize a bare
     host to `/32`, validate via `netip.ParsePrefix`, and require it to be a
     single-host prefix (`prefix.Bits() == prefix.Addr().BitLen()`). Re-prompt on
     failure.
  3. `Peer PublicKey` (base64) — required; validate via `wgtypes.ParseKey`.
  4. `Endpoint` (`host:port`) — required; validate via `net.SplitHostPort` and that
     the port parses as a numeric `1..65535`.
  5. `DNS` — optional; empty accepts default `10.64.0.1`; otherwise validate via
     `netip.ParseAddr`.
  6. `AllowedIPs` — optional; empty accepts default `0.0.0.0/0, ::/0`; otherwise
     split on comma, trim, validate each via `netip.ParsePrefix`.
  On invalid input, print a one-line reason to `out` and re-prompt the same field
  (do not abort). On EOF/`scanner.Err()` for a required field, return an error.
- Acceptance Criteria:
  - Each validator rejects malformed input and the helper re-prompts (verified by a
    test feeding bad-then-good input and asserting the good value is captured).
  - Empty input for `DNS` yields `10.64.0.1`; empty `AllowedIPs` yields
    `0.0.0.0/0, ::/0`.
  - Empty input for a required field re-prompts; EOF on a required field returns a
    non-nil error rather than writing a partial file.
  - One `Test*` per validating/prompt method, scenarios as `t.Run` subtests
    (`t.Parallel()` where no shared state); `-race` clean.
- Pitfalls & edge cases: a bare IPv6 endpoint host must be bracketed for
  `net.SplitHostPort` — accept `[2001:db8::1]:51820` form; document that operators
  paste Mullvad's `host:port` verbatim. Trim trailing `\r` (operators may paste
  from Windows). Do not treat whitespace-only lines as valid for required fields.
  `netip.ParsePrefix` accepts a CIDR only, so the bare-host normalization for
  `Address` is mandatory or `/32` entry is forced on the operator.
- Complexity: Medium

### Task 4: Resolve target path, refuse unsafe/overwrite, ensure dir
- Description: Build the output path as `filepath.Join(cfg.dir, name+".conf")`.
  Ensure `cfg.dir` exists (`os.MkdirAll(cfg.dir, 0o700)`). If the target file
  already exists and `cfg.force` is false, return an error instructing the operator
  to pick another name or pass `-force`. The safe-basename validation from Task 3
  guarantees the join stays inside `cfg.dir`; additionally assert
  `filepath.Dir(path) == filepath.Clean(cfg.dir)` as a defense-in-depth check.
- Acceptance Criteria:
  - Existing file + no `-force` → non-nil error, no write, original file untouched
    (verified by test asserting byte-for-byte unchanged).
  - Existing file + `-force` → overwrite proceeds.
  - Missing `cfg.dir` is created at mode 0700.
- Pitfalls & edge cases: race between existence check and write is acceptable for a
  single-operator interactive tool, but the atomic write in Task 5 must still use
  `O_EXCL` semantics on the temp file. Do not follow symlinks blindly — a `.conf`
  that is a symlink and `-force` is set should overwrite the link target only if it
  resolves inside `cfg.dir`; if out of scope for a 150-line tool, document the
  decision in Trade-offs rather than silently following.
- Complexity: Easy

### Task 5: Assemble wg-quick `.conf`, atomic 0600 write, round-trip parse
- Description: Build the wg-quick body with exact section headers `[Interface]` and
  `[Peer]` and keys the parser recognizes: `PrivateKey`, `Address`, `DNS` under
  `[Interface]`; `PublicKey`, `AllowedIPs`, `Endpoint` under `[Peer]`. Write via
  atomic create: `os.CreateTemp(cfg.dir, name+".conf.*.tmp")`, chmod the temp to
  0600, write the body, `Sync()`, `Close()`, then `os.Rename(tmp, finalPath)`. On
  any error after temp creation, remove the temp (error from `Remove` may be logged
  but the original failure is returned). After the rename, re-open the final file
  through `wgconf.Parse(finalPath, opLog)` to confirm it round-trips; if Parse
  errors, return a non-nil error (the just-written file is malformed — surface it
  loudly).
- Acceptance Criteria:
  - The written file has mode 0600 (verified via `os.Stat`).
  - `wgconf.Parse` on the produced file returns no error and a `ParsedConfig` whose
    `Interface.PrivateKey`, first `Interface.Addresses` entry, `Peer.PublicKey`,
    `Peer.Endpoint`, `DNS`, and `AllowedIPs` match the inputs (round-trip test).
  - Write is atomic: no partial `.conf` is left if write fails mid-way (only a
    `.tmp` may remain, never a half-written final file).
  - Private key appears in the file but never in any value passed to a logger.
- Pitfalls & edge cases: `os.CreateTemp` creates at 0600 on most systems but not
  guaranteed across umask — explicitly `Chmod(0o600)` the temp before writing. The
  temp pattern must keep the file inside `cfg.dir` (same filesystem) so `os.Rename`
  is atomic; a `/tmp` temp + cross-device rename would not be atomic. Field order in
  the body should follow the canonical wg-quick layout for operator readability,
  but the parser is order-insensitive. Ensure exactly one space around `=` is fine;
  the parser trims, so formatting is forgiving — keep it human-readable.
- Complexity: Medium

### Task 6: Print proxy.json snippet + safe info logging
- Description: After a successful write, print to `out`: (a) a confirmation with the
  final path, (b) the exact JSON snippet to add under `upstream.configs` in
  `configs/proxy.json` — e.g. a one-line array-element string
  `"./tunnels/<name>.conf"` plus a short note that paths are resolved relative to
  the directory containing `proxy.json`. Do NOT read or mutate `proxy.json`.
  Separately, emit operational info (via the same `out`, or a plain `slog` to
  stdout consistent with the rest of the tool) limited to: the public key, the
  `.conf` basename, `peer_endpoint`, and `local_address`. Never the private key or
  PSK (this tool does not collect a PSK).
- Acceptance Criteria:
  - Output contains the relative `./tunnels/<name>.conf` snippet and a one-line
    explanation that it goes under `upstream.configs`.
  - `proxy.json` is never opened for writing (verified by test asserting the file
    — if present in the test dir — is unchanged, or simply that the tool makes no
    write to any path other than the target `.conf` and its temp).
  - Info output includes public key, basename, endpoint, local address; a test
    greps the full output and asserts the private key string is absent.
- Pitfalls & edge cases: the snippet must use the relative form the parser/config
  loader expects (`./tunnels/...`), not the absolute test-dir path, or the operator
  copies a path that only works on their laptop. Keep the snippet copy-pasteable
  (valid JSON fragment).
- Complexity: Easy

### Task 7: Add `generate-vpn-config` Makefile target
- Description: Add a `.PHONY` `generate-vpn-config` target that runs
  `CGO_ENABLED=0 go run ./cmd/generatevpnconfig`. Do not build a binary into
  `./build` (the tool is interactive and run on demand). Add the target name to the
  existing `.PHONY` line. Add a short comment block above it noting the tool is
  interactive, generates a keypair locally, writes to `configs/tunnels/`, and
  prints (does not edit) the proxy.json snippet.
- Acceptance Criteria:
  - `make generate-vpn-config` invokes the CLI interactively (it reaches the TTY
    guard and proceeds when run from a terminal; in CI/non-TTY it exits non-zero
    with the clear error from Task 1).
  - Target is listed in `.PHONY`.
  - No `./build` artifact is produced by this target.
- Pitfalls & edge cases: `go run` of an interactive program under `make` must keep
  stdin attached (it does by default). Do not chain it after `build`/`format` (no
  need to format before an interactive run, and it would slow startup).
- Complexity: Easy

## Execution Order

1. Task 1 — package skeleton, flags, TTY-guarded testable `run()` seam (foundation
   everything else attaches to).
2. Task 2 — keypair generation + instructions (depends on `run()` existing).
3. Task 3 — field prompts + validation (depends on `run()` and the `in`/`out`
   seam). Can be developed in parallel with Task 2 once Task 1 lands.
4. Task 4 — path resolution + overwrite guard (depends on the conf name from
   Task 3).
5. Task 5 — assemble + atomic write + round-trip parse (depends on Tasks 2–4 for
   all field values and the resolved path).
6. Task 6 — proxy.json snippet + safe logging (depends on Task 5's final path).
7. Task 7 — Makefile target (independent; can land any time after Task 1, but
   verify end-to-end after Task 6).

## Risks

- Key leakage: the single largest risk. A stray `fmt`/`slog` of `key.String()`
  leaks the private key into terminal scrollback or, worse, a log aggregator.
  Mitigation: tests grep all captured output for the private key string and fail if
  present; keep the private key in one local variable used only at assembly.
- Non-atomic write across filesystems: if the temp file is created outside
  `cfg.dir`, `os.Rename` can fall back to copy+unlink and break atomicity.
  Mitigation: `os.CreateTemp(cfg.dir, ...)` so temp and target share a filesystem.
- Parser drift: if `wgconf` field names/defaults change later, a hand-built body
  could silently stop round-tripping. Mitigation: the Task 5 round-trip parse check
  fails loudly at runtime, and the round-trip unit test pins the contract.
- TTY detection portability: the `os.ModeCharDevice` check behaves differently
  under unusual stdin redirections. Mitigation: the seam (`isTTY`) is injected, so
  tests don't depend on it, and the real check only gates interactive use.
- Operator pastes a bare IPv6 endpoint without brackets: `net.SplitHostPort` fails.
  Mitigation: clear re-prompt message documenting the `[v6]:port` form.

## Trade-offs

- New `cmd/generatevpnconfig/` binary vs. inlining elsewhere: chosen the dedicated
  cmd because it is a single-consumer launcher with its own entry point — the
  by-the-book CLAUDE.md placement (code with one consumer lives next to it; a
  launcher is a launcher). Note the tension: v3 deleted `cmd/bootstrap-mullvad`.
  That deletion was about not reimplementing Mullvad's REST API / account-number
  surface. This tool has none of that — it is a local keygen + `.conf` assembler
  with no network calls and no account handling — so the deletion rationale does
  not apply. Accepted: a second small binary in the tree.
- Pure-Go keygen via `wgtypes` vs. shelling out to `wg genkey`: chose `wgtypes`
  (already in `go.mod`, zero new deps, no external-tool dependency, works
  identically on the operator's laptop and any host). Rejected shelling out because
  it adds a runtime prerequisite and a place for the key to transit through another
  process.
- Print proxy.json snippet vs. auto-mutate `proxy.json`: chose print-only (locked
  decision). Auto-mutation would need to parse, merge, and rewrite operator-owned
  JSON (comments, ordering, the `active` field) and risks clobbering hand edits.
  Printing keeps the tool single-purpose and the operator in control.
- Field-by-field prompts vs. splicing a downloaded `.conf` (locked decision):
  prompts keep the private key local and force per-field validation, at the cost of
  more operator copy-paste. Accepted because key locality and validation outweigh
  the keystrokes.
- Symlink handling under `-force` (Task 4): for a ~150-line single-operator tool we
  do not implement symlink-target resolution; `-force` overwrites whatever the path
  names via atomic rename, which replaces a symlink with a regular file. Documented
  here rather than building link-following logic.
- TTY detection via `os.ModeCharDevice` vs. `golang.org/x/term`: chose the stdlib
  check to avoid a new dependency for a one-line need; the injected `isTTY` seam
  keeps it swappable if a more robust check is ever required.
