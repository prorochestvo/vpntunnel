# Task Breakdown

## Overview

Migrate the production deployment from the current "versioned binary file +
single `vpntunnel` symlink" model to the standard release layout: an immutable
per-version artifact store (`artifacts/<VERSION_ID>/`) plus a named channel
symlink (`bin/release`), a confined CI deploy user, a narrow sudoers grant, and
a de-rooted service.

Today the deploy scps a binary to `$REMOTE_DIR/vpntunnel.<tag>.upload`, verifies
its SHA256, promotes it to `vpntunnel.<tag>` via `mv -Tf`, atomic-swaps the
`$REMOTE_DIR/vpntunnel` symlink, restarts the unit (running as **root**), and
rewrites `$REMOTE_DIR/vpntunnel.env` from PRIME GitHub variables on every deploy.
Retention keeps the 3 newest `vpntunnel.v*` files.

Target layout (`REMOTE_DIR` = base dir = `/opt/vpntunnel`):

```
/opt/vpntunnel/                  root:root          0755   base dir, CI cannot create top-level entries
    vpntunnel.env                root:root          0600   read by systemd not the service; operator-managed (see Deviations)
    configs/                     github_aide        0755   service's own tree — daemon enforces owner==self (see Deviations)
        auth/                    github_aide        0700   *_token (0600, owner==self), tunnel-id.key (0600)
        tls/                     github_aide        0700   self-signed cert (service writes)
    state/                       github_aide        0750   async.db (service writes)
    logs/                        github_aide        0750   access.log (service writes)
    artifacts/                   github_aide        0755   immutable build store, by VERSION_ID
        20260629140000-r_6.0.4/  github_aide        0755
            vpntunnel            github_aide        0755   (+x)
    bin/                         github_aide        0755   channel symlinks only
        release -> ../artifacts/20260629140000-r_6.0.4
```

`VERSION_ID = <YYYYMMDDhhmmss UTC>-r_<version>`, where `<version>` is the git tag
with the leading `v` stripped (e.g. tag `v6.0.4` -> `r_6.0.4`).

## Assumptions

- `REMOTE_DIR` (PRIME GH var) is the service base dir `/opt/vpntunnel`.
- The CI deploy user is `github_aide`; `SSH_USERNAME` (PRIME GH var) is set to it.
- The service is **de-rooted to run as `github_aide`** — the same existing user
  that deploys. No new dedicated runtime user is created (operator's explicit
  choice). This collapses the skill's CI/SVC split: `github_aide` builds the
  artifact, executes it, and can read every service secret (WireGuard `.conf`,
  auth tokens, tunnel-id HMAC key). A leaked deploy key therefore = "read secrets
  + run code as github_aide" — never root. Recorded as a deliberate trade-off
  (see Trade-offs), strictly better than the current root model.
- Single channel `release` only (one env, one host). `stage`/`dev` are not
  scaffolded; adding one later is another symlink + another unit/env/port/DB.
- The on-host restructure is a one-time operator action; it cannot be done from
  CI and is delivered as a runbook (Task 6), not executed by this work.
- The HMAC tunnel-id key and TLS cert already exist on the migrated host (or are
  pre-generated), so the service needs no write to `configs/auth/` at runtime —
  only `state/`, `logs/`, `configs/tls/` are in `ReadWritePaths`.

## Tasks

### Task 1: Rewrite `.github/workflows/release.yml` deploy job

- Description:
  - Compute `VERSION_ID` on the runner: `version=${GITHUB_REF_NAME#v}`,
    `VID="$(date -u +%Y%m%d%H%M%S)-r_${version}"`; export to `GITHUB_ENV`.
  - "Copy binary to host": `ssh mkdir -p $REMOTE_DIR/artifacts/$VID`, then scp
    the binary to `$REMOTE_DIR/artifacts/$VID/vpntunnel`. The VID is unique per
    deploy (timestamp), so the target dir is never a live symlink target and
    never a running inode — no `.upload` temp, no ETXTBSY concern.
  - **Delete the "Sync runtime env file" step entirely.** The env file is now
    operator-managed and root-owned; CI cannot (and must not) write the base dir.
  - "Deploy on host":
    - verify SHA256 of `artifacts/$VID/vpntunnel` against `$BINARY_SHA256`; on
      mismatch `rm -rf artifacts/$VID` and exit 1 (never touches the live channel).
    - `chmod +x artifacts/$VID/vpntunnel`.
    - capture `PREV="$(readlink $REMOTE_DIR/bin/release || echo none)"`.
    - atomic channel flip with a **relative** target:
      `ln -sfn ../artifacts/$VID $REMOTE_DIR/bin/release.tmp` then
      `mv -Tf $REMOTE_DIR/bin/release.tmp $REMOTE_DIR/bin/release`.
    - `sudo systemctl restart vpntunnel`; poll `is-active` up to 10s.
    - on restart failure: flip `bin/release` back to `$PREV` (if not none),
      restart, dump diagnostics, exit 1.
  - "Post-deploy healthcheck": unchanged probe, but on failure **auto-rollback**
    — flip `bin/release` back to `$PREV`, restart, then dump journal and exit 1.
  - "Retention cleanup": channel-aware pruning of `artifacts/` — keep the newest
    3 version dirs, never delete the dir `bin/release` currently points at.
    Replace the `vpntunnel.v*` file logic.
  - Update the sudoers reference comment to name `github_aide`.
- Acceptance Criteria:
  - No step writes anywhere under `$REMOTE_DIR` except `artifacts/` and `bin/`.
  - The "Sync runtime env file" step is gone; `actionlint`/`yamllint` clean if
    available, otherwise `python -c yaml.safe_load` parses the file.
  - Channel flip target is relative (`../artifacts/...`).
  - Failed restart OR failed health check both roll the channel back to `$PREV`.
- Pitfalls & edge cases:
  - First deploy: `PREV=none` — guard rollback so it does not `ln -sfn none`.
  - Heredoc quoting: runner-side vars (`$REMOTE_DIR`, `$VID`, `$BINARY_SHA256`)
    expand before SSH; remote-side vars (`\$PREV`, `\$actual`) stay escaped.
  - Pruning must compare basenames and resolve `bin/release` via `readlink -f`
    (or basename of `readlink`) so the active VID is never swept.
  - `date -u` runs on the GH runner (UTC) — correct and timezone-stable.
- Complexity: Hard

### Task 2: Update `configs/vpntunnel.service`

- Description: switch `ExecStart` to the channel symlink
  `/opt/vpntunnel/bin/release/vpntunnel`; set `User=github_aide` /
  `Group=github_aide`; add cheap sandboxing: `NoNewPrivileges=true`,
  `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`,
  `ReadWritePaths=/opt/vpntunnel/state /opt/vpntunnel/logs /opt/vpntunnel/configs/tls`.
  Keep `EnvironmentFile=/opt/vpntunnel/vpntunnel.env`. Update the install header
  comment (env file is operator-managed, no longer deploy-rewritten).
- Acceptance Criteria:
  - `ExecStart` references `bin/release/vpntunnel`, never a concrete VERSION_ID.
  - `systemd-analyze verify` would pass (no typos; directives valid).
  - Header comment no longer claims the deploy rewrites the env file.
- Pitfalls & edge cases:
  - `ProtectSystem=strict` makes all of `/` read-only except `ReadWritePaths` —
    if the HMAC key or TLS cert must be generated on first start, `configs/auth/`
    / `configs/tls/` need write; cert dir is covered, the key must pre-exist
    (documented in the runbook).
  - Ports are loopback >1024 — no `AmbientCapabilities` needed.
- Complexity: Medium

### Task 3: Update `configs/vpntunnel.env.example`

- Description: rewrite the header comment — the file is operator-managed and
  **not** overwritten by the deploy anymore; values are stable across deploys
  because `ExecStart` points at the fixed `bin/release` path. Keep the three
  `VPNTUNNEL_*` keys. Note it must be readable by `github_aide`.
- Acceptance Criteria: comment no longer says the release workflow overwrites it.
- Pitfalls & edge cases: none beyond keeping the keys intact.
- Complexity: Easy

### Task 4: Add sudoers reference file

- Description: add `configs/vpntunnel.sudoers` — a narrow, install-once grant for
  `github_aide`: `NOPASSWD` for exactly `systemctl restart vpntunnel`,
  `systemctl is-active --quiet vpntunnel`, and the `journalctl -u vpntunnel
  --since * -n 200 --no-pager` invocation the workflow uses. Mode 0440, validated
  with `visudo -c`. Header documents install path `/etc/sudoers.d/vpntunnel-deploy`.
- Acceptance Criteria:
  - Commands listed match the workflow's `sudo` invocations verbatim.
  - No broad `systemctl *` or `NOPASSWD: ALL`.
- Pitfalls & edge cases: the `journalctl` glob must match the exact `--since`
  argument shape the workflow sends.
- Complexity: Easy

### Task 5: Update `CLAUDE.md` Deployment section

- Description: replace the "versioned file + symlink" description with the
  artifacts/bin layout, VERSION_ID convention, de-rooted `github_aide` service,
  confined-CI permission model, removal of the GH-vars env sync, and channel-aware
  pruning. Keep it descriptive (what it is / non-obvious gotchas), no rationale
  logs per the README discipline.
- Acceptance Criteria: section matches the implemented workflow + unit; no stale
  mention of `vpntunnel.${VERSION}`, `.upload`, or `mv -Tf` promotion of binaries;
  the env-sync removal is reflected.
- Pitfalls & edge cases: do not leave contradictory text elsewhere in CLAUDE.md
  (e.g. the "Project State" intro mentions `/opt/vpntunnel/`).
- Complexity: Medium

### Task 6: Write the host migration runbook

- Description: a one-time operator runbook at
  `configs/RUNBOOK-migrate-release-layout.md` (stable home next to the other
  host-install artifacts — it does not move when this plan is completed),
  covering: create `artifacts/` + `bin/` owned
  `github_aide`; move the current live binary into `artifacts/<initial VID>/`
  and point `bin/release` at it; re-own base dir + `vpntunnel.env` to root;
  ensure `state/` `logs/` `configs/tls/` are `github_aide`-writable and the HMAC
  key + cert pre-exist; install the new sudoers file and remove any prior broad
  grant; install the new unit, `daemon-reload`, restart, verify `/v1/admin/health`.
  Confirm `SSH_USERNAME` PRIME var = `github_aide`.
- Acceptance Criteria: the runbook, run top to bottom, leaves the host in the
  target layout with the service active and healthy; ordering avoids downtime
  (flip before restart; binary in place before flip).
- Pitfalls & edge cases:
  - The very first post-migration CI deploy must find `bin/release` already a
    valid symlink (created by the runbook) so `readlink` for `PREV` works.
  - If the deploy user is currently named something other than `github_aide`,
    the rename/realignment of the user is part of this runbook (out of repo scope).
- Complexity: Medium

## Execution Order

1. Task 1 (workflow) — the core behavior change.
2. Task 2 (unit) + Task 3 (env example) + Task 4 (sudoers) — host-side artifacts
   the workflow assumes.
3. Task 5 (CLAUDE.md) — docs follow the implemented behavior.
4. Task 6 (runbook) — last, references the final shapes of 1–4.

## Risks

- **Permission model collapse (CI = SVC).** Accepted per operator choice; a
  leaked deploy key reads service secrets and runs code as `github_aide`. Still
  never root. Mitigation: narrow sudoers, no escalation path via the env file
  (ExecStart `User=` is fixed in the unit, not in env).
- **First-start writes under `ProtectSystem=strict`.** If the HMAC key or cert is
  absent, the service cannot create it outside `ReadWritePaths`. Mitigation:
  runbook pre-creates them; cert dir is in `ReadWritePaths`.
- **Rollback correctness.** A failed restart or health check must leave the
  channel pointing at the last-good VID. Mitigation: capture `PREV` before the
  flip; rollback flips back and restarts; first-deploy `none` guarded.
- **Env-sync removal is a behavior change.** Changing a TLS hostname / config
  path now requires a manual host edit of `vpntunnel.env` (no daemon-reload, env
  re-read on restart). Documented in the unit/env comments and CLAUDE.md.

## Trade-offs

- **De-root to `github_aide` vs a dedicated SVC user.** The skill recommends
  SVC != CI so CI cannot read secrets. We deliberately run as `github_aide` to
  avoid creating/managing a new user; we lose the read-isolation of secrets but
  gain de-rooting with zero new-user operational overhead. Net: strictly better
  than the status-quo root service, weaker than the skill's ideal.
- **Single `release` channel.** No `stage`/`dev`. Cheapest correct setup for one
  host/one env; a future channel is additive (symlink + unit + env + port + DB),
  not a rework.
- **Keep `EnvironmentFile` vs bake flags into `ExecStart`.** Kept so the operator
  can change paths without editing the unit (no daemon-reload). Cost: one extra
  operator-managed file.
- **No `.upload` temp in the new flow.** The timestamped VID dir is always fresh,
  so the ETXTBSY-avoidance dance is unnecessary; the SHA256 check moves to the
  final path and cleans up `artifacts/$VID` on mismatch.

## Deviations discovered during implementation / review

- **Ownership model (correction to Assumptions).** The daemon ENFORCES at startup
  that auth `*_token` files are mode 0600 **and owned by the process UID**
  (`internal/transport/apiserver/authtokens.go`), `tunnel-id.key` is 0600
  (`cmd/vpntunnel/hmackey.go`), and the TLS cert dir is exactly 0700
  (`internal/transport/apiserver/apitls/apitls.go`). Because the service runs as
  `github_aide`, the **entire `configs/` tree must be `github_aide`-owned** — a
  root-owned token fails the owner==self check and the daemon refuses to start.
  Only the base dir, `vpntunnel.env`, and the unit stay root-owned. `vpntunnel.env`
  is `root:root 0600`: systemd (root) reads it before launching the process, so the
  service never reads it. The runbook, `CLAUDE.md`, `README.md`, and
  `vpntunnel.env.example` were corrected accordingly. This is the inherent
  consequence of CI == SVC and is documented as a blast-radius note in the runbook.
- **sudoers wildcard is invalid.** `visudo -c` rejects `--since *` ("wildcards are
  not allowed in command arguments"). The workflow's `journalctl` calls dropped
  `--since '5 minutes ago'` (the `-n 200` bound is sufficient), so the sudoers grant
  lists `journalctl -u vpntunnel -n 200 --no-pager` with no glob and parses cleanly.
- **Scope expanded to README + Makefile.** The `README.md` deployment guide and the
  `Makefile` `init` target both encoded the old root + versioned-file/symlink model.
  Both were migrated: the README sections rewritten to the new layout (and the false
  "automated rollback not implemented" claim removed — auto-rollback now exists), and
  `make init` fixed to the new model (no root chown of tokens, generates
  `tunnel-id.key`, installs the sudoers file, seeds `vpntunnel.env` via sudo). Per
  operator decision `make init` is kept (host `be-happy.kz` stays hardcoded).
- **Auto-rollback added.** Beyond the plan, the deploy now self-heals: a failed
  restart OR a failed health check flips `bin/release` back to the pre-deploy
  `VERSION_ID` and restarts (with explicit logging if the rollback itself fails).
