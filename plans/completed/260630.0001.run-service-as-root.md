# Task Breakdown

## Overview

Re-root the vpntunnel service so it runs as `root`, reversing the de-rooting
introduced in `260629.0001.migrate-release-layout.md`, and bring it in line with
the other services on the host (`hive_scout`, `beacon`), which already run as
`root`. Drive the change entirely through the existing deploy machinery: the
operator-run `make init` re-provisions the host tree and reinstalls the unit,
and the CI/CD pipeline (`release.yml`) ships binaries and restarts the unit as
it does today. No manual one-off `ssh` surgery on the box.

The security payoff of running as root is that the service's secret tree
(`configs/auth`, `configs/tls`, `configs/tunnels`, `state`, `logs`) can be owned
by `root` and made unreadable to the CI deploy user `github_aide`. Today, because
the run user and the deploy user are the same identity (`github_aide`, whose SSH
key lives in GitHub Actions secrets), that one identity both deploys and owns
every runtime secret — so a leaked CI key reads all of them. After this change,
`github_aide` owns only the deploy-staging tree (`artifacts/`, `bin/`) and has no
read access to any secret.

## Problem

Current state (post `260629.0001`):

- The unit runs as `User=github_aide` / `Group=github_aide`. It is the only
  service on the host not running as root (`hive_scout` and `beacon` run as
  root).
- `github_aide` is simultaneously the **CI deploy identity** (its private key is
  stored in GitHub Actions secrets and used by `release.yml`) and the
  **service run identity**. Because the daemon runs as `github_aide`, the secret
  tree is owned by `github_aide`:
  - `configs/auth/*` — proxy token, admin token, tunnel-id HMAC key
  - `configs/tls/*`  — self-signed TLS key/cert
  - `configs/tunnels/*.conf` — the WireGuard `.conf` files (provider private keys)
- Consequence: a leaked `github_aide` key reads every runtime secret directly.

Inconsistency: the fleet convention is root services; vpntunnel diverged. The
operator's mental model and the other two units assume root.

Context from the host audit (recorded here, mostly out of scope for this plan —
see Task 5):

- `github_aide` is a member of the `docker` and `sudo` groups, which makes a
  leaked key root-equivalent independent of this change (P0, host action).
- On a root service the binary executed by root lives in `bin/release` and is
  owned by `github_aide`, so the deploy user can reach root by swapping the
  binary and triggering a restart. Running vpntunnel as root extends this
  property to it as well (P1, pipeline rework — out of scope here).
- `deploy/` is `0777` on all three services; `configs/tunnels` is `0777` on
  vpntunnel (P2, hygiene).

## Goal

1. vpntunnel runs as `root`.
2. The secret tree moves to `root` ownership; `github_aide` loses read access.
3. The operator path (`make init`) and the CI path (`release.yml`) apply and
   restart the change automatically — no hand edits on the host.
4. Passwordless restart for CI is preserved by the existing narrow sudoers grant;
   no new NOPASSWD entry is introduced.

## Target ownership / permissions (after this plan)

> **Correction during implementation.** The base dir is `0755`, **not** `0750`.
> `github_aide` is not in the `root` group, and a `0750` base dir would deny it
> the `x` (traverse) bit it needs to reach its own `artifacts/` and `bin/` —
> breaking every deploy. Secret isolation does not depend on the base-dir mode:
> it comes entirely from the `0700` root-owned `configs/auth|tls|tunnels`,
> `state/`, and `logs/` subdirs, which `github_aide` cannot open even while it
> can traverse their `0755` parents. Base dir stays `0755`.

```
/opt/vpntunnel/            root:root      0755   base dir (CI must traverse to artifacts/, bin/)
  .env                     root:root      0600   read by systemd (EnvironmentFile), operator-managed
  artifacts/               github_aide    0755   CI-writable build store, by VERSION_ID
    <VERSION_ID>/vpntunnel github_aide    0755   executed by root (residual risk, see Task 5)
  bin/                     github_aide    0755   channel symlinks only (CI-writable)
    release -> ../artifacts/<VERSION_ID>
  configs/                 root:root      0755
    auth/                  root:root      0700   *_token, tunnel-id.key (each 0600)
    tls/                   root:root      0700   self-signed cert (root writes on cold start)
    tunnels/               root:root      0700   *.conf (each 0600) — WireGuard keys
    proxy.json             root:root      0644
  state/                   root:root      0750   async.db (root writes)
  logs/                    root:root      0750   access.log (root writes)
  deploy/                  root:root      0755   nginx vhost staging (was 0777)
```

`github_aide` (the CI key) ends up able to write **only** `artifacts/` and
`bin/`. Everything runtime/secret is `root`-owned. The root daemon reads the
secret tree regardless of ownership (root bypasses DAC); the daemon does not
enforce an `owner==self` check, so root-owned secrets are read fine.

## Assumptions

- The fleet decision is "services run as root"; the security trade-off of a root
  network daemon (a proxy RCE yields root) has been accepted by the operator.
- `make init` is run by the operator as `pi5_aide`, which has password-gated
  `sudo` (credentials in 1Password). The operator path may use interactive
  `sudo` freely.
- `release.yml` authenticates as `github_aide` with an SSH key only (no
  password); it must never depend on interactive sudo.
- The existing `configs/vpntunnel.sudoers` already grants `github_aide` NOPASSWD
  for `systemctl restart vpntunnel`, `systemctl is-active --quiet vpntunnel`, and
  `journalctl -u vpntunnel -n 200 --no-pager`.
- `REMOTE_DIR` is `/opt/vpntunnel`; `bin/release` is the live channel symlink and
  `ExecStart` points at it (never at a concrete VERSION_ID).

## Implementation status (DONE — verified on host + via CI/CD)

All repo-side changes shipped on `main`; the host was re-provisioned and the full
release pipeline was exercised end-to-end against the now-root service.

Verified on the production host (read-only checks):

- The service runs as `root` (`systemctl show User=root`, MainPID owned by root,
  `active (running)`).
- Ownership/modes match the target table: base dir `root:root 0755`, `configs/`
  `0755`, `configs/auth|tls|tunnels` `0700`, `state/`+`logs/` `0750`, `.env` `0600`
  — all `root:root`; `artifacts/`+`bin/` remain `github_aide:github_aide`.
- A non-root user is denied read on the auth tokens (the `0700` root dirs lock out
  every non-root, non-owner identity, `github_aide` included).

Verified via CI/CD (release run on the re-issued `v0.0.1` tag, all green):

- `lint-and-test` passed.
- `github_aide` (SSH key only) uploaded the binary to a fresh
  `artifacts/<VERSION_ID>/`, verified its SHA256, and atomically flipped
  `bin/release` to it.
- `sudo systemctl restart vpntunnel` via the narrow sudoers restarted the root
  unit, and the post-deploy `/v1/admin/health` returned `status:ok` (tunnel
  handshake up, API on TLS). Retention pruned to the newest 3 version dirs.

Confirms the core goal: the deploy identity lost read access to every secret yet
the deploy + restart path still works unchanged.

- The privileged, idempotent host setup is factored into
  `configs/provision-host.sh` (rather than inlined into the `make init` recipe),
  invoked as `ssh -t <host> 'sudo bash /tmp/provision-host.sh'`. This avoids the
  shell-quoting hazard of nesting a root `sh -c` loop inside the single-quoted ssh
  argument, and the file-path invocation keeps the sudo password prompt (on the
  `-t` TTY) separate from the script stream.
- `make init` no longer runs as `github_aide`; it must be run as a sudo-capable
  operator. The Makefile header documents this.
- `deploy-nginx` and `healthz` were updated too: the staging dir and the admin
  token are now root-owned, so both go through `sudo`.

## Tasks

### Task 1: Flip the systemd unit to root
- Description: In `configs/vpntunnel.service`, set `User=root` / `Group=root`
  (or remove both lines, since root is the default). Rewrite the `de-rooted`
  comment block to state the root rationale. Keep the sandboxing as-is:
  `ProtectSystem=strict`, `NoNewPrivileges=true`, `ProtectHome=true`,
  `PrivateTmp=true`, and the existing `ReadWritePaths=/opt/vpntunnel/state
  /opt/vpntunnel/logs /opt/vpntunnel/configs/tls` (root is still confined by
  `ProtectSystem=strict`, so `ReadWritePaths` is still required for the dirs the
  service writes).
- Acceptance Criteria:
  - After reinstall + `daemon-reload` + restart, `systemctl show vpntunnel -p User`
    reports `User=root` and `ps -o user` on the MainPID shows `root`.
  - The unit still starts cleanly and `/v1/admin/health` is green.
- Pitfalls & edge cases:
  - Do not drop `ProtectSystem=strict`/`ReadWritePaths` "because it's root now" —
    strict mode applies to root too; removing `ReadWritePaths` would make the
    service unable to write `state/`, `logs/`, `configs/tls`.
- Complexity: Easy

### Task 2: Move the secret + runtime tree to root ownership (in make init)
- Description: Update the `init` target so the host tree matches the target
  ownership table. Because `configs/`, `state/`, `logs/` become root-owned and
  `0700/0750`, every operator write into them must go through `sudo install`
  (the operator is `pi5_aide` with password-sudo). Concretely:
  - Generate the two API tokens and the tunnel-id HMAC key under `sudo` so they
    are created `root:root 0600` (never overwrite an existing one).
  - Seed `configs/proxy.json` via `sudo install -o root -g root -m 0644` from the
    repo example only if absent (do not clobber an existing host file).
  - Sync the WireGuard `.conf`s by staging in `/tmp` and
    `sudo install -o root -g root -m 0600` into `configs/tunnels/` (the previous
    direct `scp` no longer works once the dir is `root:root 0700`).
  - Normalise ownership/modes: `sudo chown -R root:root configs state logs`,
    `sudo chmod 0700 configs/auth configs/tls configs/tunnels`,
    `sudo chmod 0600` the token/key/`*.conf` files, `sudo chmod 0750 state logs`,
    `sudo chmod 0755 /opt/vpntunnel` (base dir — see the correction note above;
    `0750` would lock the CI user out of `artifacts/`/`bin/`).
  - Remove the stale comment claiming "daemon runs as github_aide … files are
    already github_aide-owned — no chown needed"; it is no longer true.
- Acceptance Criteria:
  - `stat -c '%U:%G %a' configs/auth` → `root:root 700`; same for `configs/tls`
    and `configs/tunnels`.
  - `sudo -u github_aide cat configs/auth/admin_token` fails with permission
    denied (the CI user can no longer read secrets).
  - The service (root) starts and reads all tunnels/tokens/TLS without error.
- Pitfalls & edge cases:
  - Ordering: reinstall the **root** unit, chown the tree, `daemon-reload`, then
    restart — all in the same `make init` run. If secrets are chowned to root
    while the still-`github_aide` unit is active, the next restart of the old
    unit would fail to read them. Do the unit swap and the chown together.
  - `configs/tls` is in `ReadWritePaths`; the root daemon regenerates the
    self-signed cert there on a cold start — `0700 root` is correct and writable.
  - Token/key generation must stay idempotent (never rotate an existing secret).
- Complexity: Medium

### Task 3: Confirm the CI/CD pipeline needs no change (and verify it)
- Description: `release.yml` deploys by writing the binary into the
  `github_aide`-owned `artifacts/<VERSION_ID>/`, flipping the `bin/release`
  symlink (both `github_aide`-owned — no sudo), and running
  `sudo /bin/systemctl restart vpntunnel`. None of this depends on the service's
  run user; restarting a system unit always required root and is already covered
  by the NOPASSWD grant. So the pipeline is unchanged. Verify end-to-end that a
  tag deploy restarts the now-root service and the post-deploy healthcheck passes.
- Acceptance Criteria:
  - A `v*` tag push deploys, restarts, and the post-deploy `/v1/admin/health`
    check returns success, with the service running as root.
  - No edit to `release.yml` was required (other than, optionally, a comment).
- Pitfalls & edge cases:
  - The binary remains `github_aide`-owned and is executed by root — this is the
    P1 residual (Task 5), intentionally not addressed here.
- Complexity: Easy

### Task 4: Sudoers — keep the narrow NOPASSWD grant, do not broaden
- Description: `configs/vpntunnel.sudoers` already grants `github_aide` the three
  exact commands NOPASSWD. It is correct and sufficient for a root service —
  the only passwordless action CI needs is `systemctl restart`, which it already
  has. Keep the file as-is; `make init` continues to `sudo install -m 0440` it to
  `/etc/sudoers.d/vpntunnel-deploy`. Explicitly do NOT add a passwordless grant
  for anything else (no binary-promote step is in scope).
- Acceptance Criteria:
  - As `github_aide`: `sudo -n /bin/systemctl restart vpntunnel` succeeds without
    a password; `sudo -n true` (any other command) is denied.
  - `sudo visudo -c` reports "parsed OK" after install.
- Pitfalls & edge cases:
  - This addresses the operator's note about "passwordless start rights": that
    right already exists and survives the root migration unchanged — no new
    NOPASSWD entry is created.
- Complexity: Easy

### Task 5: Record residual risks (out of scope, track separately)
- Description: Document, do not fix here:
  - `github_aide` in `docker` and `sudo` groups → leaked key is root-equivalent.
    Host action (`gpasswd -d github_aide docker`, `gpasswd -d github_aide sudo`);
    fleet-wide P0. Not a code/deploy change.
  - Root executes a `github_aide`-owned binary → deploy user can reach root via
    binary swap. Real fix: root-owned binary slot with a privileged promote step;
    fleet-wide P1; pipeline rework.
  - `deploy/` `0777` (also on hive/beacon). Tighten to `0755` (this plan's Task 2
    sets vpntunnel `deploy/` to `0755`; hive/beacon are separate repos).
- Acceptance Criteria:
  - These items are captured in this plan and/or a follow-up so they are not lost.
- Complexity: Easy

## Execution Order

1. Task 1 (unit → root) and Task 2 (make init ownership rewrite) in the repo,
   together — they are interdependent.
2. Keep Task 4 (sudoers unchanged) and confirm Task 3 (pipeline unchanged) by
   reading the diffs.
3. Push the branch; merge.
4. Operator runs `make init` once to re-provision ownership, reinstall the root
   unit, `daemon-reload`, and restart. This performs the github_aide → root
   transition atomically.
5. Push a `v*` tag (or re-run the deploy) to verify CI/CD restarts the root
   service and the healthcheck passes (Task 3).
6. Verify `github_aide` can no longer read the secret tree (Task 2 acceptance).
7. File the Task 5 residual items as their own follow-up.

## Risks

- **Half-applied transition.** Chowning secrets to root while the old
  `github_aide` unit is still installed/active means a restart of the old unit
  cannot read the secrets and crash-loops. Mitigation: reinstall the root unit
  and chown in the same `make init` run; on failure, roll back (revert
  `vpntunnel.service` to `User=github_aide`, `daemon-reload`, restart).
- **Operator write paths break silently.** Once `configs/` is root-owned, any
  remaining direct `scp`/non-sudo write in `make init` fails. Mitigation: route
  every config write through `sudo install` (Task 2) and test a full `make init`
  on the host.
- **Root network daemon.** A remote-code-execution bug in the public proxy now
  yields root rather than `github_aide`. Accepted per the fleet decision;
  partially offset by `ProtectSystem=strict`, `NoNewPrivileges`, `PrivateTmp`.
- **Residual root paths remain (Task 5).** Until `github_aide` is removed from
  `docker`/`sudo` and the executed binary is root-owned, a leaked CI key is still
  root-capable. This plan isolates secrets but does not close those paths.

## Trade-offs

- **Consistency + secret isolation vs. a root network service.** Running as root
  unlocks root-owned secrets (CI key loses secret read access) and matches the
  rest of the fleet, at the cost of a root-privileged public daemon. Chosen.
- **Scope.** This plan isolates secrets from the CI key and automates the
  migration through `make init` + CI/CD. It deliberately does NOT fix the
  binary-swap-to-root path (P1) or the group memberships (P0); those are
  fleet-wide and tracked in Task 5.
