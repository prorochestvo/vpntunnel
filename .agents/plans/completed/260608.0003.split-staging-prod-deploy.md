# Task Breakdown

## Overview

Plan 006 wired a single deploy: a `v*` tag push builds an image, publishes it to
GHCR, SSHes to one VPS, runs `docker compose up -d --wait`. There is no staging.
Every prod tag is also the first time anything from `main` runs in a
container-on-a-real-host shape — which means the first integration-level signal
an operator gets is on the production host itself. That is the bug this plan
closes.

Plan 008 splits the pipeline into two environments without changing the binary
or the Dockerfile:

1. **Staging** — every push to `main` builds the image, publishes it to GHCR as
   `:edge` (floating) and `:main-<short-sha>` (immutable), SSHes to the
   **staging** VPS, and rolls the container forward. No manual step. No tag.
2. **Production** — every push of a `v*` tag publishes `:vX.Y.Z` (immutable) and
   `:latest` (floating), SSHes to the **prod** VPS, and rolls the container
   forward. Tagging stays a deliberate manual act.

The image build is identical for both environments — same `Dockerfile`, same
`make test`, same `linux/amd64`, same GHCR repo. Only the image tags applied
and the SSH target differ. That cross-cutting invariant ("the image both
environments deploy is bit-identical when built from the same SHA") is what
justifies extracting the build into a **reusable workflow** (Decision A
below). This is the exception to CLAUDE.md's "dedup is not a goal" rule:
duplicating the build steps across two top-level workflows would create a
real divergence risk — the moment one workflow gets a `--platform` flag and
the other doesn't, "the same image" stops being true and staging stops being
load-bearing.

Eight concrete deliverables:

1. **`.github/workflows/build-image.yml`** — new reusable workflow
   (`on: workflow_call`). Inputs: image-tag list (newline-joined string).
   Outputs: `image_tag` (the primary immutable tag — the one the deploy job
   should pull). Runs `make test`, builds with Buildx, pushes to GHCR.
2. **`.github/workflows/staging.yml`** — new top-level workflow on
   `push: branches: [main]`. Calls `build-image.yml` with tags
   `edge` and `main-<short-sha>`. Then deploys to staging via SSH using
   per-environment GH secrets/variables. `environment: staging` for deployment
   history and scoped secrets.
3. **`.github/workflows/release.yml`** — rewrite. Keep the `on: push: tags:
   ['v*']` trigger. Replace the inline `test`+`publish` jobs with a single
   `uses: ./.github/workflows/build-image.yml` call passing semver tags +
   `latest`. Keep the deploy job, retarget to **prod** GH env/vars, add
   `environment: production` to gate on optional manual approval.
4. **`compose.yml`** — one file, unchanged in shape (`${IMAGE_TAG}` already
   parametrized by Plan 006). Both servers use it as a template.
5. **Smoke test** — after `docker compose up -d --wait` succeeds, the deploy
   script `curl`s `http://127.0.0.1:8081/healthz` from inside the SSH session
   and asserts `"status":"ok"`. Belt-and-braces on top of `--wait`.
6. **README rewrite of `## Deploy`** — split server-side setup into two parallel
   procedures (staging host + prod host), document the full secret/variable
   inventory, document the rollback paths for each environment.
7. **`CLAUDE.md` updates** — Project State (one-line: "two environments, two
   hosts"), Deployment section (image tag list expanded), Constraints (the
   `DEPLOY_SSH_KEY` line becomes `STAGING_SSH_KEY` + `PROD_SSH_KEY`).
8. **`Makefile`** — no functional change required. `IMAGE_TAG ?= dev` still
   does the right thing for `make docker-run`. Noted for completeness, not as
   a task.

What this plan explicitly does NOT ship:

- **Auto-tagging on main**. User said no. Staging deploys ride the branch HEAD;
  tags remain a manual act reserved for prod.
- **Version baked into the binary**. Logging the git SHA at httpproxy startup is
  a separate plan.
- **Multi-arch builds**. Linux/amd64 only, per CLAUDE.md.
- **Auto-promote from staging → prod**. The promotion is "push a `v*` tag at
  the SHA you just validated on staging." Manual, deliberate.
- **Server-side compose divergence between environments**. Both hosts use the
  same `compose.yml` shape (`${IMAGE_TAG}` driven). One image, two tags, one
  template. Justification in Decision H.
- **Blue/green or canary**. Each host gets a hard `docker compose up -d`. ~3s
  of proxy unavailability is acceptable for both environments at personal
  scale.
- **A separate GHCR repo per environment**. One repo,
  `ghcr.io/<owner>/httpproxy`, all tags in one place. Cleaner pull semantics,
  no duplicated visibility settings.

Net diff: ~120 lines in `.github/workflows/build-image.yml` (new), ~70 lines
in `staging.yml` (new), ~80 lines in `release.yml` (rewritten — actually
shrinks), ~200 lines in `README.md`, ~10 lines in `CLAUDE.md`. Zero Go changes.

## Assumptions

### Locked design decisions

#### Decision A — Reusable workflow over per-environment duplication

**Chosen:** option (b) from the user spec — extract `build-image.yml` as
`workflow_call`, both `staging.yml` and `release.yml` `uses:` it with
environment-specific image-tag inputs.

**Rejected:** option (a) — keep `release.yml` as-is for prod, add a parallel
`staging.yml` with copy-pasted build steps.

**Reasoning.** CLAUDE.md's "deduplication is not a goal" rule applies to
coincidental similarity that must be free to diverge. The Docker image build
is the opposite case: divergence here would silently invalidate the whole
point of having a staging environment. If staging built with `--platform
linux/amd64,linux/arm64` and prod with `linux/amd64`, "we tested this on
staging" would be a lie at the layer-list level even though both deploys
appear green. A reusable workflow names the invariant ("one image build, two
deploys") and makes accidental divergence a code-review concern instead of a
silent risk. The cost is one extra file and a `with:` block at each call site
— cheap. The cost of (a) is that the day someone tweaks the build, they
either remember to tweak both files or they don't. We will not remember.

#### Decision B — GH secret/variable naming convention

**Chosen scheme** (suffix-by-environment, all SCREAMING_SNAKE_CASE):

| Name | Type | Scope | Purpose |
|------|------|-------|---------|
| `STAGING_SSH_KEY` | Secret | `staging` env | ed25519 private key for staging host |
| `STAGING_HOST` | Variable | `staging` env | Hostname or IP of staging VPS |
| `STAGING_USER` | Variable | `staging` env | SSH user on staging VPS |
| `STAGING_FINGERPRINT` | Variable | `staging` env | `SHA256:...` of staging host |
| `PROD_SSH_KEY` | Secret | `production` env | ed25519 private key for prod host |
| `PROD_HOST` | Variable | `production` env | Hostname or IP of prod VPS |
| `PROD_USER` | Variable | `production` env | SSH user on prod VPS |
| `PROD_FINGERPRINT` | Variable | `production` env | `SHA256:...` of prod host |

**Rejected:** `SSH_KEY_STAGING` / `SSH_KEY_PROD` (prefix-by-purpose) — reads
less naturally and groups by "kind of secret" instead of by "which host this
talks to". When debugging a deploy, "which environment's stuff am I looking
at?" is the question that gets asked first; environment-as-prefix optimises
for that.

**Rejected:** keeping `DEPLOY_SSH_KEY` and `SERVER_*` as the staging-side
names and adding `PROD_*` alongside. Confusing — the existing names imply
"the one and only server" which is no longer true. Rename both sides for
symmetry.

**Rejected:** GitHub Environments' "deployment branch policies" alone, with
shared secret names. Tempting (the secret store does the routing for you)
but it makes local reasoning harder: a workflow file that reads
`secrets.DEPLOY_SSH_KEY` no longer tells you which key it gets. Explicit
naming wins for grep-ability.

#### Decision C — GitHub Environments yes for both, manual approval only on prod

**Chosen:**
- `staging` GH Environment, no protection rules. Auto-deploy on every main push.
- `production` GH Environment with a "required reviewers" rule (default: the
  repo owner). Every tag push pauses at the deploy step until the owner
  clicks "Approve and deploy" in the Actions UI.

**Reasoning.** GH Environments give us three things that are otherwise
clunky: (1) secrets scoped to "only the production deploy job can read
`PROD_SSH_KEY`" — a leaked CI log from a different job can't echo it because
it isn't in the same scope; (2) deployment history in the Actions UI keyed
by environment ("when was prod last deployed?"); (3) an optional approval
gate. (3) is the killer feature for prod: a `v*` tag push is the operator
saying "I want this in prod", but the approval click is a five-second
re-confirmation that catches the "oops, that tag was meant for testing"
case. Staging gets none of the gates because the whole point of staging is
that pushing to main is allowed to deploy unsupervised. The "approve own
deploys" pattern looks silly on a one-person project but costs five seconds
per deploy and creates a clean audit trail.

#### Decision D — Image tag strategy

**Staging build (on push to `main`):** `:edge` + `:main-<short-sha>`.

- `:edge` floats. Always points at the latest main. Useful for ad-hoc `docker
  pull` and for the staging server's `${IMAGE_TAG}=edge` default.
- `:main-<short-sha>` is immutable. Re-running a previous staging workflow
  from the GH UI pulls the exact image that was built then, not whatever
  `:edge` currently is. Critical for rollback (Decision F).

**Production build (on tag `vX.Y.Z` push):** `:vX.Y.Z` + `:X.Y.Z` + `:latest`.

- `:vX.Y.Z` and `:X.Y.Z` are both immutable per-tag. `metadata-action`
  already emits both shapes; keep them.
- `:latest` floats to the most recent tag. Standard.

**Hard rule:** main-branch builds NEVER touch `:latest`. The
`metadata-action` config in `build-image.yml` is driven entirely by the
caller's `with: tags:` input, and `staging.yml` passes only `edge` and
`main-<short-sha>`. There is no path by which a main push could overwrite
`:latest`. This is the property that lets a prod operator type
`docker pull ghcr.io/<owner>/httpproxy:latest` and trust the result.

#### Decision E — Concurrency

Each top-level workflow gets two concurrency groups:

- **Per-ref `build-image-${{ github.ref }}`** on the reusable workflow's
  build job (or on each caller's job that calls it) — `cancel-in-progress:
  true` for main builds (a second push supersedes the first), `false` for
  tag builds (let each tag build to completion; tags should never be
  superseded).
- **Constant per-environment** on the deploy job:
  - `deploy-staging` for `staging.yml`, `cancel-in-progress: false`. Two
    rapid main pushes queue their deploys rather than cancelling
    mid-flight. Cancelling halfway leaves a half-rolled host.
  - `deploy-production` for `release.yml`, `cancel-in-progress: false`.
    Same reasoning.

The two `deploy-*` groups are deliberately separate — a staging deploy must
not block a prod deploy. Different hosts, different concurrency budgets.

#### Decision F — Rollback

**Staging:**

- **Primary path:** push a fix commit to main. Next staging deploy
  supersedes the broken one.
- **Fallback (image was published but the new code is bad):** re-run an
  older `staging.yml` workflow run from the GH UI. Because the previous run
  also published a `:main-<short-sha>` tag, the deploy step re-pulls that
  specific tag and the host rolls back to the known-good image.
- **Why this works:** `:edge` alone wouldn't help — GHCR has overwritten
  it. The immutable `:main-<short-sha>` is the only durable handle on "this
  specific commit's image".

**Production:**

- **Primary path:** push a new tag at an older commit (e.g. `git tag
  v1.2.4-rollback <oldsha> && git push origin v1.2.4-rollback`). Full
  pipeline re-runs end-to-end against the old code.
- **Fallback (no time to wait for a rebuild, image already on GHCR):**
  SSH manually and `IMAGE_TAG=v1.2.2 docker compose up -d --wait`. Bypasses
  the workflow but rolls instantly to a known-published image.
- **Discouraged:** `git tag --force` to move an existing tag. Documented
  for completeness in the README but not endorsed — confuses GHCR
  immutability expectations and breaks anyone who pulled the original
  `:vX.Y.Z`.

#### Decision G — Server-side `compose.yml` template

**Chosen:** option (a) — one `compose.yml` in the repo. Both servers use
the same template, hand-authored on each server once during setup. Image
tag is parametrised via `${IMAGE_TAG}` (already shipped by Plan 006), passed
inline by the SSH deploy step on every roll.

**Rejected:** option (b) — `compose.yml` + `compose.staging.yml`. Adds a
second file to maintain. The actual content difference between the two
would be exactly one line (the default `${IMAGE_TAG}` value) — not worth a
separate file. CLAUDE.md's "by concern, not by launcher" guidance applies:
the staging-vs-prod split is a deployment concern, not a code-shape concern.

**Rejected:** option (c) — no compose file in the repo. Removes the
template the operator copies during setup; the existing v5 v4→v5 cutover
note relies on having a canonical shape to point at. Keeping the repo
compose as a reference template costs ~15 lines and saves a lot of
documentation.

**The staging server defaults `${IMAGE_TAG}` to `edge`** in its local
shell env or `.env` file (not in the compose file itself — `${IMAGE_TAG}`
in compose stays bare with no `:-` default, so a missing env still fails
loud). The deploy step always passes `IMAGE_TAG=...` inline, so the local
default only matters for manual `docker compose ...` invocations on the
host.

#### Decision H — Post-deploy smoke test

**Chosen:** add a `curl` step inside the SSH deploy script, after `docker
compose up -d --wait`, that hits `http://127.0.0.1:8081/healthz` and
asserts `"status":"ok"`. Belt-and-braces.

**Reasoning.** `docker compose up -d --wait` already blocks on the
Dockerfile HEALTHCHECK (`/httpproxy -healthcheck`, which TCP-dials
`127.0.0.1:8081`). If the admin listener binds but the WireGuard tunnel
never handshakes, the TCP probe says "healthy" while `/healthz` says 503.
A `curl` from inside the SSH session catches that gap at near-zero cost.
The curl runs *on the server*, not from the GHA runner — no firewall
holes, no public exposure of the admin port.

```bash
# inside the SSH script, after `docker compose up -d --wait`
body=$(curl -fsS http://127.0.0.1:8081/healthz)
echo "$body" | grep -q '"status":"ok"' \
  || { echo "ERROR: /healthz did not return status=ok: $body"; exit 1; }
```

`curl -f` makes 503 a non-zero exit on its own; the `grep` is redundant
defence in case the body shape ever changes.

### Cross-plan contract

- **Plan 006 contract preserved.** Server-side state at `/opt/httpproxy/`,
  `httpproxy` user, `compose.yml` accepts `${IMAGE_TAG}` from env. The
  staging host follows the exact same setup; no new server-side shape.
- **Plan 005 `/healthz` contract preserved.** Smoke test reads the same
  endpoint the Dockerfile HEALTHCHECK probes, just with the JSON body
  asserted instead of just the TCP-dial. Body schema (`{status, reason,
  handshake_age_seconds}`) is unchanged.
- **CLAUDE.md "Never log WireGuard key material" preserved.** Neither
  workflow emits anything from `proxy.json` or the `.conf` files — both
  servers' configs are operator-owned and never touched by CI.

## Tasks

### Task 1: Author the reusable build workflow

- **Description:** Create `.github/workflows/build-image.yml`. Define it as
  a `workflow_call` workflow. Move the existing `test` + `publish` job
  bodies from `release.yml` into this file as a single composite shape:
  job 1 runs `make test`, job 2 builds and pushes the image. Expose the
  primary immutable image tag as a workflow output so callers can pass it
  to their deploy job. Accept the image-tag-list as an input (newline-
  joined string, since `metadata-action`'s `tags:` input is newline-
  joined; passing through is simpler than reformatting). Do NOT include a
  deploy job here — this workflow is build-only.

- **Acceptance Criteria:**
  - [ ] File exists at `.github/workflows/build-image.yml`.
  - [ ] Trigger is `on: workflow_call:` only (no `push:` or other triggers).
  - [x] Inputs declared: `image_tags` (string, required). The `ref` input
        originally planned here was dropped: both callers always build from
        the triggering SHA, and `actions/checkout@v4`'s default behavior is
        correct. Flexibility adds surface with no current consumer.
  - [ ] Outputs declared: `image_tag` (the immutable primary tag — the
        value of `steps.meta.outputs.version`).
  - [ ] Job `test` runs `make test` after `setup-go` against `go.mod`.
  - [ ] Job `publish` `needs: test`, uses `docker/setup-buildx-action@v3`,
        `docker/login-action@v3` against GHCR, `docker/metadata-action@v5`
        with the input tag list, `docker/build-push-action@v6` with
        `platforms: linux/amd64`, `cache-from: type=gha`, `cache-to:
        type=gha,mode=max`.
  - [ ] `permissions:` block on the publish job sets `packages: write` and
        `contents: read`. No other scopes.
  - [ ] `make test` still runs with the same `-race` flag (whatever
        `make test` already does); do not regress the existing test command.
  - [ ] Concurrency: `group: build-image-${{ github.ref }}`,
        `cancel-in-progress: ${{ github.ref != 'refs/heads/main' && false || true }}`
        — main pushes supersede, tag pushes don't. (See Pitfalls — the
        ternary in YAML is a known sharp edge.)
  - [ ] Workflow file passes `actionlint` (or at minimum, doesn't emit
        syntax errors when pushed to a throwaway branch).

- **Pitfalls:**
  - GitHub's expression language does NOT have a real ternary — the
    `condition && trueval || falseval` trick works only when `trueval`
    is truthy. For boolean `false`, this idiom breaks. Use a separate
    `if:`-gated job or precompute the boolean as a workflow-level env var
    if the ternary misbehaves. Alternative: just hardcode
    `cancel-in-progress: false` for safety; the cost of an extra build
    on a rapid main push is a few minutes, well worth avoiding
    half-cancelled builds.
  - The `metadata-action`'s `tags:` input expects newlines, not commas.
    If a caller passes `"edge,main-abc1234"` instead of `"edge\nmain-abc1234"`,
    `metadata-action` will treat it as one literal tag with a comma in
    it and the push will fail with a cryptic registry error. Document
    in the file header.
  - `steps.meta.outputs.version` is the **primary** tag — when multiple
    tags are emitted, it's the first one. For staging, the caller MUST
    pass `main-<sha>` as the first tag (immutable, useful for rollback);
    `edge` second. For prod, `vX.Y.Z` first.
  - Do NOT enable `provenance: true` or `sbom: true` on
    `build-push-action` without a separate plan — they add manifest
    entries that distroless tooling sometimes chokes on.

- **Complexity:** Medium

- **Code Example:**

```yaml
# .github/workflows/build-image.yml
name: build-image
on:
  workflow_call:
    inputs:
      image_tags:
        description: "Newline-joined list of tags to publish. First tag is the primary (immutable) one returned as image_tag output."
        type: string
        required: true
      ref:
        description: "Git ref to build. Defaults to the calling workflow's SHA."
        type: string
        required: false
        default: ${{ github.sha }}
    outputs:
      image_tag:
        description: "Primary immutable image tag (e.g. 1.2.3 for v1.2.3, or main-abc1234 for a main push)."
        value: ${{ jobs.publish.outputs.image_tag }}

# Per-ref concurrency. Main pushes supersede each other (cancel-in-progress
# true); tag pushes don't (caller decides). Constant for safety; callers
# that want supersession set it at their level.
concurrency:
  group: build-image-${{ github.ref }}
  cancel-in-progress: false

jobs:
  test:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
        with: { ref: ${{ inputs.ref }} }
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true
      - run: make test

  publish:
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      image_tag: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4
        with: { ref: ${{ inputs.ref }} }
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository_owner }}/httpproxy
          # tags input is newline-joined; pass through verbatim from caller.
          tags: ${{ inputs.image_tags }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

### Task 2: Author the staging workflow

- **Description:** Create `.github/workflows/staging.yml`. Triggers on
  `push: branches: [main]`. Two jobs: `build` (calls `build-image.yml`
  with `image_tags: "main-<sha>\nedge"`) and `deploy` (SSH to staging
  host, roll the container forward, smoke-test `/healthz`). Uses
  `environment: staging`.

- **Acceptance Criteria:**
  - [ ] File exists at `.github/workflows/staging.yml`.
  - [ ] Trigger is exactly `on: push: branches: [main]`.
  - [ ] `build` job calls `uses: ./.github/workflows/build-image.yml`
        with `image_tags` set to the two tags joined by `\n` (in YAML:
        a literal block scalar `|`).
  - [ ] First tag in the list is `main-<7-char-sha>` (the immutable
        one). Compute via `${{ github.sha }}` truncated. See Code Example.
  - [ ] Second tag is `edge`.
  - [ ] `deploy` job `needs: build`, `runs-on: ubuntu-latest`,
        `environment: staging`.
  - [ ] Concurrency on the deploy job: `group: deploy-staging`,
        `cancel-in-progress: false`.
  - [ ] Deploy job has a pre-flight step asserting the four staging
        repo/env vars (`STAGING_HOST`, `STAGING_USER`,
        `STAGING_FINGERPRINT`) are set, mirroring the existing assertion
        block in `release.yml`. Secret cannot be pre-asserted (GH masks
        secrets, see Plan 006's comment); rely on the SSH step's own
        failure.
  - [ ] Deploy step uses `appleboy/ssh-action@v1` against `vars.STAGING_HOST`
        / `vars.STAGING_USER` / `vars.STAGING_FINGERPRINT` /
        `secrets.STAGING_SSH_KEY`, with `command_timeout: 5m`.
  - [ ] Deploy script (inside the SSH session):
        - `set -euo pipefail`
        - `cd /opt/httpproxy`
        - Exports `IMAGE_TAG="${{ needs.build.outputs.image_tag }}"` and
          guards against empty.
        - `docker compose pull`
        - `docker compose up -d --wait --wait-timeout 120`
        - `curl -fsS http://127.0.0.1:8081/healthz` and assert
          `"status":"ok"`.
  - [ ] `$GITHUB_STEP_SUMMARY` line on success and failure, including the
        image tag and the host name.
  - [ ] No `continue-on-error: true` on the SSH step.

- **Pitfalls:**
  - `github.sha` is 40 chars. Truncate to 7 in a `run:` step that exports
    a job-output (or use the `${{ github.sha }}:0:7` expression — verify
    GH expression slicing actually works). Safer: compute in a shell step.
  - The tag list MUST be in the right order. `main-<sha>` first so it
    becomes `steps.meta.outputs.version` and gets surfaced through the
    workflow output as `image_tag`. Reversing the order makes the deploy
    pull `:edge` (which usually works, but defeats the rollback story
    when re-running an older workflow run).
  - GH Environments scope secrets at the **job** level, not the workflow
    level. The `build` job does NOT have `environment:` set (it doesn't
    need the staging SSH key); only the `deploy` job does. Setting it on
    the wrong job either leaks too much access or denies legitimate access.
  - The `environment: staging` line will fail until the operator has
    actually created the Environment in the GH UI. Document this in the
    setup task (Task 6).

- **Complexity:** Medium

- **Code Example:**

```yaml
# .github/workflows/staging.yml
name: staging
on:
  push:
    branches: [main]

jobs:
  resolve-tags:
    runs-on: ubuntu-latest
    outputs:
      tag_list: ${{ steps.tags.outputs.tag_list }}
    steps:
      - id: tags
        run: |
          set -euo pipefail
          short="${GITHUB_SHA:0:7}"
          # newline-joined tag list; first tag is the immutable one.
          {
            echo "tag_list<<EOF"
            echo "main-${short}"
            echo "edge"
            echo "EOF"
          } >> "$GITHUB_OUTPUT"

  build:
    needs: resolve-tags
    uses: ./.github/workflows/build-image.yml
    with:
      image_tags: ${{ needs.resolve-tags.outputs.tag_list }}
    # inherit secrets? No — build-image.yml only needs GITHUB_TOKEN,
    # which is implicit; the SSH key lives in the deploy job's environment.

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    concurrency:
      group: deploy-staging
      cancel-in-progress: false
    steps:
      - name: Assert required env-scoped variables are set
        run: |
          missing=0
          for v in STAGING_HOST STAGING_USER STAGING_FINGERPRINT; do
            val_var="vars_${v}"
            if [ -z "${!val_var:-}" ]; then
              echo "Required variable '$v' is not set in the staging environment"
              missing=1
            fi
          done
          [ "$missing" -eq 0 ] || exit 1
        env:
          vars_STAGING_HOST: ${{ vars.STAGING_HOST }}
          vars_STAGING_USER: ${{ vars.STAGING_USER }}
          vars_STAGING_FINGERPRINT: ${{ vars.STAGING_FINGERPRINT }}

      - name: SSH and roll the container
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ vars.STAGING_HOST }}
```

```yaml
name: release
on:
  push:
    tags: ['v*']

jobs:
  resolve-tags:
    runs-on: ubuntu-latest
    outputs:
      tag_list: ${{ steps.tags.outputs.tag_list }}
    steps:
      - id: tags
        run: |
          set -euo pipefail
          # github.ref_name is e.g. "v1.2.3"; strip the leading v.
          version="${GITHUB_REF_NAME#v}"
          # validate semver shape so a malformed tag fails fast.
          [[ "$version" =~ ^[0-9]+\.[0-9]+\.[0-9]+(-[A-Za-z0-9.-]+)?$ ]] \
            || { echo "ERROR: tag ${GITHUB_REF_NAME} is not semver"; exit 1; }
          major_minor="${version%.*}"
          {
            echo "tag_list<<EOF"
            echo "$version"
            echo "$major_minor"
            echo "latest"
            echo "EOF"
          } >> "$GITHUB_OUTPUT"

    needs: resolve-tags
    uses: ./.github/workflows/build-image.yml
    with:
      image_tags: ${{ needs.resolve-tags.outputs.tag_list }}

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production

      group: deploy-production
      cancel-in-progress: false
    steps:
      - name: Assert required env-scoped variables are set

          missing=0
          for v in PROD_HOST PROD_USER PROD_FINGERPRINT; do
            val_var="vars_${v}"
            if [ -z "${!val_var:-}" ]; then
              echo "Required variable '$v' is not set in the production environment"
              missing=1
            fi
          done
          [ "$missing" -eq 0 ] || exit 1
        env:
          vars_PROD_HOST: ${{ vars.PROD_HOST }}
          vars_PROD_USER: ${{ vars.PROD_USER }}
          vars_PROD_FINGERPRINT: ${{ vars.PROD_FINGERPRINT }}

      - name: SSH and roll the container
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ vars.PROD_HOST }}
          username: ${{ vars.PROD_USER }}
          key: ${{ secrets.PROD_SSH_KEY }}
          fingerprint: ${{ vars.PROD_FINGERPRINT }}
          command_timeout: 5m
          script: |
            set -euo pipefail
            cd /opt/httpproxy
            export IMAGE_TAG="${{ needs.build.outputs.image_tag }}"
            [ -n "$IMAGE_TAG" ] || { echo "ERROR: IMAGE_TAG empty"; exit 1; }
            docker compose pull
            docker compose up -d --wait --wait-timeout 120

            echo "$body" | grep -q '"status":"ok"' \
              || { echo "ERROR: /healthz did not return status=ok: $body"; exit 1; }

      - name: Workflow summary
        if: always()
        run: |
          STATUS="${{ job.status }}"
          TAG="${{ needs.build.outputs.image_tag }}"
          HOST="${{ vars.PROD_HOST }}"
          if [ "$STATUS" = "success" ]; then
            echo "production: ${TAG} deployed to ${HOST}, /healthz OK" >> "$GITHUB_STEP_SUMMARY"
          else
            echo "production: ${TAG} deploy to ${HOST} failed (status=${STATUS})" >> "$GITHUB_STEP_SUMMARY"
          fi
```

## Risks

### (a) Reusable workflow contract drift between staging and prod

`build-image.yml` is the single source of truth for "how we build the
image". If a future plan tweaks the build (e.g. adds a build arg, changes
the base image, enables BuildKit cache mode) and the reusable workflow's
input/output contract changes, both callers must be updated in lockstep.
Mitigation: name the inputs and outputs explicitly, document each in the
workflow's header, and treat a `build-image.yml` change as requiring a
fresh end-to-end run of both `staging.yml` and `release.yml` before
merging.

### (b) `metadata-action` semver patterns vs raw tag inputs

The current `release.yml` uses `metadata-action`'s `type=semver` patterns,
which generate tags by reading the triggering ref directly. Moving the
tag computation to the caller (Task 3) and passing literal strings via
`type=raw` means the called workflow's `metadata-action` no longer knows
the ref is a semver tag. This is a real behavioural change — the OCI
labels emitted by `metadata-action` (`org.opencontainers.image.version`
etc.) may differ. Mitigation: compare `docker inspect` output on the
image built by the new pipeline against an image built by the current
pipeline; add any missing labels as explicit `with: labels:` entries on
the `build-push-action` step.

### (c) GH Environments approval gate is a SPOF on the operator

A `v*` tag push now requires the operator to click "Approve and deploy"
in the GH UI. If the operator is unavailable (asleep, on a plane, phone
dead), prod sits on the old version even though the tag is pushed.
Mitigation: the approval gate's "required reviewers" list can include
multiple GH usernames; add a secondary reviewer if continuity matters.
For the single-operator personal-project case, this is an acceptable
trade — the deliberate gate is the entire point.

### (d) Concurrency group rename window

The deploy job concurrency group is renamed from `release-deploy` to
`deploy-production` in Task 3. During the workflow run that ships THIS
change, a concurrent tag push from the OLD `release.yml` (group:
`release-deploy`) would not be serialized against a job from the new
`release.yml` (group: `deploy-production`). In practice this is a
non-issue because tag pushes are deliberate and rare, but documented
for completeness.

### (e) First-run GHCR package visibility on the new tag shapes

`:edge` and `:main-<sha>` are new tag shapes on the existing GHCR package.
GitHub's package-visibility model is per-package, not per-tag — since the
package is already public (flipped after Plan 006's first deploy), the
new tags are immediately pullable. Confirm in Task 7's validation that a
logged-out `docker pull` of `:edge` works.

### (f) SSH key inventory grows linearly with environments

Two environments → two keys. Three environments → three keys. Plus a
rotation key set per environment in flight. Inventory creep. Mitigation:
the key-rotation procedure in the README is the same shape per
environment; no new mechanism needed. Long-term mitigation (out of scope
here): adopt an SSH CA or short-lived OIDC-issued certs. Not yet
warranted at this scale.

### (g) Smoke test masks a real signal

`docker compose up -d --wait` ALREADY blocks on the Dockerfile
HEALTHCHECK. Adding a separate `curl` step after it catches the
narrow case of "TCP probe says yes but `/healthz` body says no" — but if
the operator ever weakens the smoke test (e.g. drops the
`'"status":"ok"'` grep), the deploy can falsely succeed. Mitigation:
the grep is the actual assertion; document inline in the script that
removing it removes the only post-`--wait` check.

### (h) "Staging" implies "this catches bugs" — it doesn't catch them all

Staging runs on its own VPS with its own WireGuard config, its own
upstream `.conf` files, and its own bearer token (if auth is configured).
A bug that only manifests with the **production** `.conf` (e.g. a
provider-specific MTU quirk) will not be caught on staging. Mitigation:
none — staging is a *signal-strength multiplier*, not a *bug-free
guarantee*. State this expectation explicitly in the README.

### (i) Cost: an extra always-on VPS

A staging VPS that exists only to deploy main-branch images is a real
recurring cost. Mitigation: the staging host can be smaller (1 vCPU,
512MB RAM is enough for httpproxy); use the cheapest tier the chosen
provider offers. Justify against the cost of catching one bad deploy in
prod by hand.

## Trade-offs

- **Decision A (reusable workflow) over per-environment duplication:**
  chose reuse because the build is a genuine cross-cutting invariant
  ("staging deploys the same image prod will get"). Cost: one extra file,
  slightly more indirect for someone reading the workflows for the first
  time. Benefit: drift between staging and prod build configs becomes a
  code-review concern instead of a silent footgun.

- **Decision B (env-prefixed secret names) over `DEPLOY_SSH_KEY_STAGING`
  / `DEPLOY_SSH_KEY_PROD` (suffix scheme):** chose prefix because
  "which environment is this for?" is the question asked first when
  debugging; suffix scheme groups by "kind of secret" which is less
  useful day-to-day. Cost: longer secret names. Benefit: at-a-glance
  grouping in the GH Settings UI.

- **Decision C (GH Environments for both, approval gate only on prod)
  over no-environments / both-gated / staging-only:** chose this because
  (1) scoped secrets are a real security win even without approval gates,
  (2) prod approval is the perfect "are you sure" for a manual tag push,
  (3) staging approval would defeat the entire point of auto-deploy on
  main. Cost: extra GH UI configuration during initial setup. Benefit:
  audit trail + accidental-tag protection on prod.

- **Decision D (`:edge` + `:main-<sha>` dual tag) over `:edge` alone:**
  chose dual-tag because immutable per-commit tags are required for
  re-running an older workflow run (the rollback story). Cost: more tags
  in GHCR (will accumulate forever unless a retention policy is set).
  Benefit: rollback works without rebuilding.

- **Decision E (constant per-environment concurrency, never cancel) over
  ref-keyed or cancellable groups:** chose constant + queue because
  cancellation mid-`docker compose up -d` leaves the host in an
  undefined state. Cost: a rapid sequence of main pushes will queue
  deploys rather than parallel them, slowing perceived feedback. Benefit:
  no half-rolled hosts.

- **Decision G (one repo `compose.yml`, both servers use it) over two
  compose files or none:** chose one because the structural difference
  between staging and prod compose is exactly the `${IMAGE_TAG}` value,
  which is already a runtime env var. Two files would duplicate ~15
  lines for zero functional gain. Zero files would force every operator
  to author their own from scratch — bad onboarding. Cost: the
  template-vs-server-copy distinction needs to stay clear in the README.
  Benefit: minimum surface to maintain.

- **Decision H (post-`--wait` `/healthz` curl):** chose to add it because
  the cost is one line of shell and the catch is the real-life case of
  "TCP probe says yes, handshake never completed, `/healthz` returns
  503". Cost: deploy script is two lines longer. Benefit: catches a
  silent-failure mode that `--wait` alone misses.

- **Single `ghcr.io/<owner>/httpproxy` package for both environments over
  separate `httpproxy-staging` / `httpproxy-prod` packages:** chose
  shared because the image IS the same artifact; only the tag-and-host
  routing differs. Two packages would mean two visibility settings to
  maintain, two retention policies, two pull URLs in the README. Cost:
  staging and prod tags coexist in one tag listing, which can look
  noisy. Benefit: simpler everything else.

- **No auto-tagging on main (manual `v*` tags only):** confirmed user
  decision. The cost is the operator has to remember to tag; the
  benefit is that "what's in prod" is always a deliberate act, not a
  side effect of merging. Auto-tagging belongs in a future plan if it
  ever lands.

- **`@main` omitted from local reusable workflow calls:** GitHub Actions requires no
  `@ref` on local-path `uses:` references. Initial implementation added `@main`;
  review caught it and removed it. The reusable workflow always runs from the same
  ref as the calling workflow run.

- **`secrets: inherit` omitted from the `build` job:** `build-image.yml` only needs
  `GITHUB_TOKEN` (implicit in `workflow_call`) to push to GHCR. No environment
  secrets need forwarding, so `secrets: inherit` is intentionally absent.

- **Concurrency group lives in `build-image.yml`, not in the callers:** GHA does
  not propagate a caller's concurrency group into a called workflow. The per-ref
  `build-image-${{ github.ref }}` group is therefore declared inside the reusable
  workflow. Callers own only their deploy-job concurrency.

- **OCI label `org.opencontainers.image.version` is set from the first raw tag
  value:** Moving tag computation out of `metadata-action` into a `resolve-tags`
  shell step means `metadata-action` sees pre-computed strings (`type=raw`), and
  the version label is derived from the first raw entry. The value is identical
  to what `type=semver,pattern={{version}}` would produce; only the mechanism
  differs. Nothing downstream reads this label.

- **Pre-release semver tags skip `:latest` and `:X.Y`:** Review caught that the
  initial `resolve-tags` step would publish `v1.0.0-rc1` to `:latest`, overwriting
  the stable image. Fixed: only stable `X.Y.Z` tags push `:X.Y` and `:latest`;
  pre-release tags push only their literal immutable version.
