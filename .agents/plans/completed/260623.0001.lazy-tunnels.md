# Task Breakdown

## Overview

`vpntunnel` currently builds **every** tunnel listed in `upstream.configs` eagerly at
startup (`internal/tunnel/pool/pool.go` `NewPool` loops all configs → one
`wireguard.NewDialer` per entry → one gVisor netstack device each). The operator wants
to load Mullvad's full ~700-server `.conf` set into `./configs/tunnels/`. At ~10–50 MB
RSS per netstack device that is tens of GB of resident memory at boot = guaranteed OOM.
Mullvad also caps concurrent WireGuard sessions for one account at 5; the operator
reserves 3 for personal devices, leaving **exactly 2 live devices for this host**.

This plan replaces the eager single-active model with a **lazy, two-role tunnel
manager** bounded by a hard global invariant: **never more than 2 live WireGuard
devices at any instant.**

The two roles map cleanly onto the two ingress paths the binary already exposes:

- **Role 1 — streaming (persistent):** served by the forward-proxy listener
  (`:8080`, `internal/service.ProxyService`, which holds exactly one `tunnel.Dialer`).
  Exactly one tunnel, always up, randomly picked from a country-filtered pool, with
  failure-driven reconnect on a long backoff. This is the "always-on exit" for normal
  browsing.
- **Role 2 — on-demand:** served by the async `/v1/proxy/{scheme}/{rest...}` endpoint
  (`internal/asyncjob` + `handlers/proxy.go`). Time-multiplexed: at most one on-demand
  tunnel live, selected per request by an exact config basename ("zone"), torn down and
  rebuilt on zone switch, kept warm by an idle TTL.

1 streaming + 0..1 on-demand = the 2-device ceiling, enforced structurally (each role
owns at most one device, and they are independent owners).

**Key discovery that shapes the design:** the async proxy handler **already** selects
its tunnel per-request via the `X-Tunnel-Id` header
(`internal/transport/apiserver/handlers/proxy.go` step 2, `r.Header.Get("X-Tunnel-Id")`),
validating it against the pool through `DialerFor`/`ResolverFor`. The value is the exact
config basename. So the "zone-naming mechanism" the spec asks us to invent **is the
existing `X-Tunnel-Id` header** — we keep it. See OPEN DECISION 1.

The async pool today, however, ignores per-zone routing at the worker level: `main.go`
(~309-313) builds **one** `ForwarderFunc` closure that captures a single pre-resolved
`activeID`/`dialer`/`resolver` and forwards **all** jobs through it. That closure must be
replaced by a scheduler that brings the requested zone's device up on demand and
serializes zones onto the single on-demand slot.

`proxy.json` stays the single config mechanism for this version. We **add** fields; we do
**not** refactor config discovery, do **not** move anything to env/flags, and do **not**
remove `upstream.configs` (all deferred to a later plan).

### Architecture shape (new packages, by concern, not by launcher)

| New package | Responsibility |
|-------------|----------------|
| `internal/tunnel/lazy` (working name) | Lazy per-config dialer factory + the streaming supervisor and the on-demand scheduler, each as its own type. Co-located because all consume the same `wireguard.NewDialer` build path and the same 2-device invariant; split by concern (supervisor vs scheduler), not by listener. |

The existing `internal/tunnel/pool` package's eager-build loop is retired for production
wiring but its `BuilderFn` seam, `countryFromID` helper, and `TunnelInfo`/`TunnelHealth`
value plumbing are reused. See OPEN DECISION 4 for whether `pool` is deleted or kept as a
thin read-model.

NOTE: per CLAUDE.md Code Organization, do **not** introduce a shared `bootstrap`/`wiring`
layer; the supervisor and scheduler are constructed inline in `cmd/vpntunnel/main.go`.

## Assumptions

- **[OPERATOR TO VERIFY — design is non-viable if false]** All ~700 `.conf` files share
  ONE `[Interface] PrivateKey` (= one Mullvad device/key); only the `[Peer] PublicKey`
  and `Endpoint` differ per server. If private keys differ per config, each config is a
  *distinct* Mullvad device and the 5-session cap is consumed per *config*, not per
  *concurrent tunnel* — the whole 2-live-device scheme collapses. **Do not start
  implementation until this is confirmed.** A cheap guard task (Task 0) detects the
  violation at startup and fails loudly rather than silently burning sessions.
- The streaming role and the on-demand role hold **independent** device owners; the
  2-device ceiling is `1 (streaming) + max 1 (on-demand)`. Nothing else in the process
  opens a WireGuard device.
- "Eligible pool" for the streaming role = `upstream.configs` filtered by
  `allowed_countries`. For the on-demand role the eligible set is the **same**
  country-filtered pool (a zone request for a config outside the eligible pool is a
  client error). OPEN DECISION 2 asks whether on-demand should be filtered too or allow
  any configured config.
- Country code is the **2nd** hyphen segment of `mullvad-<cc>-<city>-wg-NNN`, always
  exactly two lowercase ASCII letters. Matching rule: a country `cc` matches a config
  iff the config basename contains the substring `-<cc>-`. (This also fixes the
  `countryFromID` bug, Task 7.)
- A listed country with zero matching configs is silently ignored. If the *whole*
  filtered pool is empty, startup fails with a `publicerror` (misconfiguration).
- Mullvad frees an old session only after the peer's keepalive/handshake timeout
  (~tens of seconds). Bringing a new on-demand device up before the old one's session
  has expired would transiently present 2 sessions for the *same* device — within the
  per-account total but risky. Hence the **settle-delay** between teardown and bring-up
  on the on-demand slot. The exact default is OPEN DECISION 3.
- `health.handshake_max_age` (already in config, default 180s) is the staleness
  threshold used by both the streaming supervisor's failure detector and the existing
  per-request health gate.
- The existing `asyncjob` bbolt store + worker pool + GC + recovery are reused as-is for
  persistence and stuck-job bounding. No new database.
- Starvation of non-active zones is acceptable and intended (the on-demand role is a
  personal tunnel); jobs for starved zones expire via the existing
  `api.async.pending_timeout` GC path and return an error.
- Branch `v2-squashed` is off-main; commit autonomously when work is ready (per user
  memory). This plan touches neither `Makefile` nor `cmd/generatevpnconfig/*` (operator
  editing those in parallel).

### Task 3: Streaming supervisor (persistent role, one device, backoff)

- **Description:** Add a `StreamingSupervisor` type to `internal/tunnel/lazy` that owns
  **exactly one** live streaming device for the process lifetime. On `Start(ctx)` it
  picks a random eligible config (Task 2), builds it (Task 1), and exposes the current
  live `tunnel.Dialer` (and `tunnel.Resolver`) to `ProxyService` via an accessor that is
  safe under concurrent reconnect. A background goroutine polls the device's
  `HealthReporter.LastHandshake()`; when the handshake age exceeds
  `health.handshake_max_age` (or `LastHandshake` errors), it tears the device down and
  reconnects after a backoff that starts at `streaming.reconnect_min` (~10m) and grows
  to `streaming.reconnect_max` (~3h). **Every (re)connect picks a NEW random eligible
  config** (not the same server). The supervisor honors `ctx` cancellation for clean
  shutdown and closes the live device on stop.
- **Acceptance Criteria:**
   - [ ] At most ONE streaming device is ever live (enforced: build new only after old is
         `Close()`d, except the very first build).
   - [ ] `Dialer()` / `Resolver()` accessors return the current live device and are safe
         to call concurrently with a reconnect (RWMutex or atomic pointer swap).
   - [ ] Health poll uses `health.handshake_max_age`; a stale or errored handshake
         triggers teardown+reconnect.
   - [ ] Backoff starts at `reconnect_min`, multiplies up to `reconnect_max`, and **resets
         to min after a successful healthy reconnect**.
   - [ ] Each reconnect re-rolls the random config; with a pool > 1 the new pick is
         allowed to differ (do not force "must differ" if pool size is 1).
   - [ ] On `ctx.Done()` the supervisor stops the poll loop and closes the live device
         exactly once.
   - [ ] `ProxyService` integration: `service.NewProxyService` receives a dialer source
         that reflects the *current* supervised device, not a snapshot taken at startup
         (see OPEN DECISION 5 — accessor indirection vs swap-in-place).
   - [ ] Tests with a fake builder and a controllable fake clock / handshake source:
         `TestStreamingSupervisor_Start` (builds one, exposes dialer),
         `TestStreamingSupervisor_reconnect` (stale handshake → rebuild, old closed first),
         `TestStreamingSupervisor_backoff` (min→grow→cap→reset), `..._Stop` (idempotent
         close, no leak), each as subtests of the relevant method test per CLAUDE.md.
- **Pitfalls:**
  - **Race on dialer swap:** `ProxyService` may be mid-`DialContext` on the old device
    while the supervisor closes it. Decide the contract: either (a) accessor returns the
    device and the caller's in-flight conn survives until its own read/write fails, or
    (b) drain before close. Document which; prefer (a) (atomic pointer swap, let in-flight
    conns die naturally) for simplicity — closing a WG device kills its conns anyway.
  - **First-connect failure:** if the very first build fails, decide retry-vs-fail-startup.
    Recommend: retry on backoff (operator tolerates long outages) rather than failing
    startup, but surface a loud WARN. Flag as a sub-decision.
  - Never log the picked config's key material; log `tunnel_id` + `selected_via:random`.
  - Backoff goroutine must not leak on shutdown — select on `ctx.Done()` in every sleep.
- **Complexity:** Hard

### Task 4: On-demand zone scheduler (single slot, FIFO grace-timer switching)

- **Description:** Add an `OnDemandScheduler` type to `internal/tunnel/lazy` that owns
  **at most one** on-demand device, time-multiplexed across zones. It is the new routing
  brain that replaces the single fixed-`activeID` closure in `main.go`. Public surface:
  a method the async worker calls to obtain a forwarding context for a given zone, e.g.
  `Route(ctx, zoneID) (dialer tunnel.Dialer, resolver tunnel.Resolver, release func(), err error)`,
  plus a `Run(ctx)` loop that owns device lifecycle. Behaviour:
  - **Validation:** zone must be in the eligible set (Task 2); otherwise return a
    `publicerror` ("unknown_zone") so the job fails with a client error.
  - **Single slot:** only one zone's device is live at a time. Switching zones tears the
    old device down FULLY, waits `ondemand.settle_delay`, then builds the new one.
  - **Grace-timer scheduling:** serve all queued jobs for the current zone. Each NEW
    request for the **current** zone RESETS a grace timer (`ondemand.grace`). While
    same-zone traffic keeps arriving the scheduler stays on the current zone
    (intentional starvation of others). When the grace window elapses with no new
    same-zone request, switch to the zone with the **oldest** pending job (FIFO across
    zones).
  - **Idle TTL:** after the last request, keep the current device up until either another
    zone needs the slot (→ tear down immediately) or `ondemand.idle_ttl` elapses
    (may be days). The TTL only avoids churn; it never overrides another zone's demand.
  - **Failure policy (this REVERSES the earlier "retry later" idea):** if bringing the
    zone's device **up** fails, fail **all** of that zone's currently-queued jobs with a
    client error and move on to the next zone. **No deferral, no retry loop.** A single
    request failing while the device is up fails only that request; other same-zone jobs
    continue.
- **Acceptance Criteria:**
   - [ ] At most ONE on-demand device is ever live; on zone switch the old device is
         `Close()`d, then the code waits `settle_delay`, then builds the new device
         (assert ordering in a test with a fake builder recording call order + timestamps).
   - [ ] Unknown/ineligible zone → `publicerror` ("unknown_zone"); the async worker maps
         it to a client-error response (Task 5).
   - [ ] Same-zone request resets the grace timer; switch happens only after `grace`
         elapses with no new same-zone request.
   - [ ] Cross-zone selection on switch picks the **oldest** pending job (FIFO).
   - [ ] Device-bring-up failure fails ALL currently-queued jobs for that zone with a
         client error and advances to the next zone — no retry of the failed zone.
   - [ ] Idle TTL: with no demand the device stays up until `idle_ttl`; a demand for a
         different zone tears it down immediately regardless of remaining TTL.
   - [ ] `Run(ctx)` exits on cancellation and closes any live device exactly once.
   - [ ] Tests (fake builder + fake clock): `TestOnDemandScheduler_Route` (valid zone
         serves; unknown zone errors), `TestOnDemandScheduler_switch` (grace reset, FIFO
         pick, teardown→settle→buildup order), `TestOnDemandScheduler_bringupFailure`
         (all queued same-zone jobs fail, next zone proceeds), `TestOnDemandScheduler_idleTTL`,
         `..._Run` (clean shutdown), as subtests.
- **Pitfalls:**
  - **Concurrency-within-zone is an OPEN DECISION (6).** The existing `asyncjob.Pool`
    runs `MaxConcurrentJobs` workers in parallel; the single-slot + zone-serialization
    constraint means *cross-zone* concurrency must be 1, but *within* the active zone you
    may still want N parallel requests through the one live device. Decide: (a) strict
    serialization (one job at a time, simplest, slowest), or (b) allow up to
    `MaxConcurrentJobs` concurrent jobs **as long as they target the current zone**, and
    serialize only zone switches. Recommend (b). This decision drives the locking model.
  - **Grace timer + idle TTL interaction:** the grace timer governs *switching away*; the
    idle TTL governs *tearing down when idle*. Keep them as two distinct timers; do not
    fold them. A request arriving during the idle window cancels the idle teardown.
  - **Deadlock risk:** `Route` must not block forever waiting for a switch while holding a
    lock the `Run` loop needs. Use a request queue + a single owner goroutine
    (`Run`) that mutates device state; `Route` enqueues and waits on a per-request
    channel. This is the cleanest serialization model and avoids lock inversion.
  - **`release()`** must signal the scheduler that a job finished so idle/grace timing is
    accurate; never leak a held slot if the worker panics (defer the release).
  - Never log key material; logs use `zone_id` + reason enums only.
- **Complexity:** Hard

  2. Build the eligible set (Task 2) from `upstream.configs` + `allowed_countries`;

  3. Run the single-key guard (Task 0) over the eligible set; fail startup on violation.
  4. Construct `StreamingSupervisor` (Task 3), `Start(ctx)` it; pass its dialer/resolver

  5. Construct `OnDemandScheduler` (Task 4) over the eligible set; run its `Run(ctx)` loop

  6. Build the async forwarder (Task 5) routing through the scheduler; wire into

  7. Pass live read-models into `apiserver.Options` (Task 9) instead of the eager pool.
  8. Preserve the existing shutdown ordering (proxy listener → API listener → job pool
     drain → GC join → store close) and ADD: stop the scheduler `Run` loop and the
     supervisor before closing the store, so all WG devices are torn down on shutdown.
  Delete `resolveActiveTunnel`'s use as the single-active picker (the supervisor owns

- **Acceptance Criteria:**

## Risks

- **VIABILITY RISK (highest):** if the single-key assumption is false, the entire
  2-live-device scheme is invalid. Task 0 fails loudly at startup, but if the operator's
  Mullvad export uses per-server keys the plan must be reconsidered before any work. **Do
  not implement Tasks 1–10 until the operator confirms the single-key assumption.**
- **Session-cap overrun on switch:** if `settle_delay` is too short, a zone switch can
  briefly present two sessions for the same device, and combined with the streaming device
  that is still within the 5-session account budget but flirts with Mullvad's limits. Too
  long, and on-demand latency suffers. This is a tuning risk; `settle_delay` is
  configurable and the operator will tune by experiment (DECISION 3).
- **Visible contract change — `/v1/tunnels` and `/v1/admin/health`:** operators
  previously saw every configured tunnel; now they see only the 1–2 live devices. Body
  *shape* is unchanged (CLAUDE.md invariant honored) but the *set* shrinks. Anything that
  scraped `/v1/tunnels` for the full catalogue breaks. Documented; must be called out to
  the operator.
- **Async admission-time health gate moves:** `proxy.go` currently rejects requests for
  stale tunnels at admission via `DialerFor`+`HealthReporter`. With lazy building the
  device may not exist at admission; the gate moves to "eligibility check at admission +
  health enforced post-bring-up in the scheduler." This changes the *timing and error
  code* a client sees for a bad/stale tunnel (it may now surface as a failed async job
  rather than a synchronous 503). Flag to operator.
- **Starvation is intentional but operator-surprising:** a busy zone can starve others
  indefinitely; starved jobs expire via `pending_timeout`. If the operator later wants
  fairness, the FIFO-on-switch policy is the seam to change.
- **Goroutine/device leak on shutdown:** the supervisor and scheduler each own a long-
  lived loop and a live device; the shutdown join + close must be exact or a WG device /
  UDP port leaks across restarts. The existing `gcWg` join pattern is the template.
- **Reconnect storm on provider outage:** during a Mullvad-side outage every reconnect
  rebuilds a fresh device and immediately fails; the backoff (min 10m → max 3h) bounds
  this, but verify the backoff actually grows and is not reset by transient partial
  handshakes.

## Trade-offs

- **Reuse `X-Tunnel-Id` as the zone key vs invent a new header (DECISION 1):** chose to
  reuse the existing `X-Tunnel-Id` header rather than add `X-Vpntunnel-Zone`, because the
  async proxy path already reads it and validates it against the pool; a new header is
  pure churn and a second name for the same concept. Rejected: path-embedded zone
  (`/v1/proxy/{zone}/{scheme}/{rest}`) — it breaks the existing route shape and the
  CLAUDE.md route table. Confirm at review.
- **One `internal/tunnel/lazy` package holding factory + supervisor + scheduler vs three
  packages:** chose one package split by concern *internally* (separate types/files)
  rather than three packages, because all three share the build path, the eligible set,
  and the 2-device invariant, and CLAUDE.md organizes business logic by concern with a
  flat split. They are genuinely cohesive (one invariant), not coincidentally similar.
- **Concurrency-within-zone (DECISION 6):** recommend allowing up to `MaxConcurrentJobs`
  concurrent jobs *within the current zone* and serializing only zone switches, over
  strict one-at-a-time serialization — it preserves the existing async throughput model
  for the common case (operator hammers one zone) while still honoring the single-device
  invariant. Strict serialization is simpler but throttles the common path to 1 RPS-ish.
- **Atomic pointer swap for the streaming dialer (DECISION 5):** recommend an
  atomic/RWMutex-guarded accessor that `ProxyService` reads per-dial, over swapping the
  dialer *inside* a long-lived `ProxyService` field, because closing a WG device kills its
  conns anyway, so draining is unnecessary complexity. In-flight conns die naturally on
  reconnect; new dials get the new device.
- **Retire eager `pool` for production, keep its value types / helpers (DECISION 4):**
  recommend keeping `internal/tunnel/pool` only if a thin read-model still wants its
  `TunnelInfo`/`TunnelHealth` plumbing; otherwise delete `NewPool` and move the reusable
  helpers (`countryFromID`, the builder mapping) into `internal/tunnel/lazy`. Decide at
  review based on how much of `pool` survives Task 9's read-model.
- **Fail-startup vs retry on first streaming connect (sub-decision in Task 3):** recommend
  retry-on-backoff with a loud WARN rather than failing startup, because the operator
  explicitly tolerates long payment-delay outages and a hard startup failure would make
  the daemon un-bootable during such an outage. Trade-off: the proxy listener is up but
  returns errors until the first device connects.

## RESOLVED DECISIONS (operator-confirmed)

1. **Zone-naming mechanism** → REUSE existing `X-Tunnel-Id` header. No new header, no
   path-embedded zone. (Tasks 4, 5.)
2. **On-demand eligibility scope + empty-filter** → on-demand draws from the SAME
   country-filtered eligible pool as streaming (country is the global startup filter). An
   empty `allowed_countries` means "filter disabled → all configs eligible". Operator's
   intended set: `["us", "gb", "ua", "de"]` (UK is `gb` in Mullvad naming). (Tasks 2, 6.)
3. **`settle_delay` default** → 15s default, validation minimum 5s; operator tunes by
   experiment. Lives in the `ondemand` block of `proxy.json` for format uniformity (the
   args-vs-json migration is the separately-deferred discussion). (Tasks 4, 6.)
4. **Fate of `internal/tunnel/pool`** → DELETE the eager `NewPool` machinery (it is the
   OOM source). Move `countryFromID` + the segment parser + the builder mapping into
   `internal/tunnel/lazy`. `TunnelInfo`/`TunnelHealth` already live in `internal/tunnel`
   and stay there. The `pool` package is removed entirely. (Tasks 1, 7, 9.)
5. **Streaming dialer hand-off** → atomic-pointer / RWMutex-guarded accessor read
   per-dial by `ProxyService`. No drain-before-close (closing a WG device kills its conns
   anyway). (Tasks 3, 8.)
6. **Concurrency within the active on-demand zone** → allow up to `MaxConcurrentJobs`
   concurrent jobs WITHIN the current zone; serialize only zone switches. (Required by the
   operator's batching example: 7 simultaneous same-country requests run together.)
   (Task 4.)
7. **Error codes + proxy-error marker** → unknown/ineligible zone = **400** with
   `X-Proxy-Error: unknown_zone`. Zone bring-up failure ("tunnel is down" — the operator
   considers this OUR fault) = **502** with `X-Proxy-Error: <code>`. In-zone single-request
   failure while the device is up = **502**. The existing `X-Proxy-Error` header is the
   "error originated from the proxy, not upstream" contract (`handlers/envelope.go:14` sets
   it; `handlers/forwarder.go:315` deletes any upstream-set copy). CRITICAL for the async
   path: the marker MUST be persisted into the STORED `UpstreamResponse` (bbolt), so a
   client polling the job result sees `X-Proxy-Error`, not just the synchronous path.
   (Task 5.)
8. **`upstream.active` / `resolveActiveTunnel`** → REMOVE. `active` is meaningless now
   (streaming is always random, on-demand is always per-request). Drop the field from the
   schema and retire `resolveActiveTunnel`'s single-active selection. Keep
   `upstream.configs`. (Tasks 6, 8.)
