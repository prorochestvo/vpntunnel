# Task Breakdown

## Overview

Add asynchronous + retry-safe semantics to the existing `/v1/proxy/` endpoint
shipped in v1. Async opt-in is per-request and driven entirely by a header:
when the client sends `Proxy-Retry-Tag: <tag>` on a standard proxy request,
the daemon takes ownership, returns `202 Accepted` with the discriminator
header `Proxy-Async-Status: pending`, and processes the request
asynchronously. A subsequent retry with the same tag either returns the
upstream response verbatim (once complete) or another
`202 + Proxy-Async-Status: pending` while the job is still in flight. No
separate `/v1/proxy/async/...` URL prefix is introduced; the URL shape is
identical to the v1 sync surface, only the header changes the semantics.

This plan is a **skeleton**: the architectural shape is locked from the v1
plan's "Deferred: async endpoint (v2)" section
(`plans/completed/260614.0001.https-api-listener.md`, lines 1131-1230) and
then revised live during this session to collapse the originally-proposed
two URL prefixes into a single header-switched endpoint (see Trade-offs
entry "Revision 1 — Endpoint topology"). Eight original open questions were
resolved live and recorded in Trade-offs. The next execution stage is for
`gocode-architect` to populate Tasks 9..N (concrete implementation steps),
then proceed to `gocode-engineer` and the three-lens reviewer fan-out.

## Assumptions

These are **locked** from the v1 plan and MUST NOT be reopened without explicit
user authority. The endpoint-topology entry below was revised live during this
session (see Trade-offs "Revision 1 — Endpoint topology") and replaces the v1
plan's two-URL sketch.

- Single endpoint surface — the existing `{METHOD} /v1/proxy/<scheme>/<rest>`
  family from v1 is unchanged in shape. Async-with-retry semantics are
  enabled per-request via the `Proxy-Retry-Tag: <tag>` request header.
  Absence of the header → pure-v1 sync behaviour (unchanged). Presence of
  the header → async-with-tag mode. No `/v1/proxy/async/...` URL prefix
  exists.
- Tag format: `^[a-zA-Z0-9_-]{8,128}$` (UUID v4/v7 string forms satisfy this
  comfortably). The server never generates the tag.
- HTTP status matrix (async-with-tag mode only; sync mode is unchanged
  from v1):
  - **First time seen / in-progress** → `202 Accepted` with response
    header `Proxy-Async-Status: pending` and a JSON envelope body
    `{"status": "pending", "retry_tag": "<tag>"}`. The same response shape
    is returned on the first submit and on any retry while the job has
    not reached a terminal state. Clients MUST check the
    `Proxy-Async-Status: pending` header before treating a 202 as a final
    answer — a completed job whose upstream returned 202 would also use
    status code 202, and only the header distinguishes the two cases.
  - **Completed (terminal: completed / failed / failed_timeout)** →
    upstream response verbatim — exactly the status code, headers, and
    body the upstream returned. The daemon adds `X-Request-Id` and does
    NOT add `Proxy-Async-Status`; absence of that header on a 2xx-5xx
    response means "this is the upstream's answer, not ours".
  - **Tombstoned (eviction window)** → `410 Gone` with code
    `tag_evicted` via the existing `envelope.WriteError`.
  - **Queue saturated** → `503 Service Unavailable` with code
    `queue_full` via `envelope.WriteError`.
  - Pipeline errors (validation, IP deny, body cap, etc.) use the
    existing `envelope.WriteError` helper exactly as in v1.
- Storage: `bbolt` single file at `/opt/vpntunnel/state/async.db`, configurable
  via `api.async.storage_path`. Single bucket `jobs`; key = retry_tag (bytes);
  value = JSON-serialised job record. Job state machine:
  `pending → {completed | failed | failed_timeout} → tombstone → DELETE`.
  Tombstone payload is minimal: `{status: "tombstone", evicted_at}` — the
  response body and headers are dropped at the eviction transition so the
  bucket footprint stays bounded.
  **Request bodies are NOT persisted to bbolt** — only metadata and (on
  completion) the upstream response. This keeps the submit hot path free of
  large bbolt writes and bounds the on-disk footprint.
- Restart recovery: on daemon startup, the recovery routine scans the `jobs`
  bucket and DELETEs every record with `status = pending` in a single
  bbolt transaction (logged at INFO with the dropped count). Completed,
  failed, failed_timeout, and tombstone records are left untouched. A
  client polling for a dropped tag sees `404 Not Found` and is free to
  resubmit with the same tag (which is treated as a fresh first submit) —
  the `Proxy-Retry-Tag` contract remains idempotent across restarts. See
  Trade-offs entry "Q4".
- TTL: `pending_timeout 5m`, `complete_ttl 1h`, `tombstone_ttl 24h`
  (configurable via `api.async.tombstone_ttl`). Background GC goroutine runs
  every 60s and handles three transitions in one pass:
  - `pending` older than `pending_timeout` → `failed_timeout`.
  - `completed`/`failed`/`failed_timeout` older than `complete_ttl` →
    `tombstone` (payload stripped, `evicted_at` stamped).
  - `tombstone` older than `tombstone_ttl` → DELETE.
  Total idempotency window from completion is `complete_ttl + tombstone_ttl`
  (~25h with defaults); after that the tag is reusable and re-execution may
  occur on resubmit.
- Concurrency: worker pool guarded by a semaphore. `max_concurrent_jobs 100`.
  On saturation, submit returns `503 Service Unavailable` with code
  `queue_full`.
- Body cap: `10 MB` uniformly — the same v1 sync cap applies whether or not
  `Proxy-Retry-Tag` is present. Async opt-in is about retry-safety and
  decoupled timing, not about larger payloads. Clients needing larger
  uploads still chunk client-side, exactly as in v1.
- No streaming response bodies in async-with-tag mode. Async always
  materialises the full upstream response before storing. Streaming
  clients submit without `Proxy-Retry-Tag` to get the v1 sync streaming
  path.
- `/v1/admin/health` gains `pending_jobs_count`, `completed_jobs_count`, and
  `tombstone_jobs_count` fields (admin-only response surface — still no
  leakage of tags or payloads).
- URL log sanitisation is applied at log-write time, not at request-parse time.
  Routing inside the daemon is never affected by sanitiser configuration.
  Config shape: `api.log.path_sanitize_patterns` is an array of objects of
  the form `{"pattern": "<go-regex>", "replacement": "<go-replacement>"}`,
  with capture groups supported via `$1`, `${name}` etc. Patterns are
  precompiled at config load; any `regexp.Compile` failure is a config
  error and the daemon refuses to start (the offending index is named in
  the error). No defaults are shipped — the operator docs include a
  copy-paste reference block (Telegram bot tokens, generic API keys). The
  sanitiser applies uniformly to the single `/v1/proxy/<scheme>/<rest>`
  access log call site regardless of whether the request was sync (no
  header) or async-with-tag (Proxy-Retry-Tag present); zero configured
  patterns means zero behavioural change. See Trade-offs entries "Q1"
  and "Q2".
- Shared (no changes): `ipdeny.DefaultDeny()` (immutable, no async-skip
  branch), `tunnel.Pool`, `envelope.WriteError`, the TLS 1.3 config from the
  v1 API server.
- Operational-log host:port redaction is two-layered:
  - **Primary (at source).** `mapDoError` (sync `forwarder.go`) and its
    async equivalent unwrap `*url.Error`, `*net.OpError`, and
    `*tls.RecordHeaderError` via `errors.As` and emit a controlled
    short message (e.g. `"upstream dial timeout"`) instead of the raw
    stdlib `.Error()` string. Client-supplied hostname may stay in the
    message; resolved IP addresses and any `host:port` pair must not.
  - **Defence-in-depth (at write).** A new slog `Handler` wrapper in
    `internal/observability/` (e.g. `scrubhandler`) sits in front of the
    base handler and regex-scrubs known `host:port` patterns
    (`IPv4:port`, `[IPv6]:port`, `hostname.tld:port`) out of string
    attribute values before they are written. Replacement is `<HOST:PORT>`.
  - The two layers are designed together: the wrapper is the primary
    fix, the handler is the safety net that catches new call sites
    that forget the policy. See Trade-offs entry "Q3".

### Task 12: Implement bounded worker pool with `SubmitOrFetch`
- Description: Create `internal/asyncjob/pool.go` implementing the
  semaphore-bounded executor. The pool owns a `chan struct{}` of size
  `max_concurrent_jobs`, a `Store`, and a `Forwarder` callable injected at
  construction (so the pool does not import the HTTP handler package). The
  primary entry point is
  `SubmitOrFetch(ctx context.Context, tag string, req *http.Request) (Outcome, error)`
  returning a discriminated value covering the four cases listed in the
  status matrix: `OutcomePending`, `OutcomeCompleted{UpstreamResponse}`,
  `OutcomeTombstoned`, `OutcomeQueueFull`. The method reads the record;
  if absent it tries to claim a semaphore slot (non-blocking
  `select { case slot <- struct{}{}: default: return OutcomeQueueFull }`),
  writes a `pending` record, dispatches the request on a goroutine that
  invokes the injected forwarder and CAS-transitions the record to
  `completed` / `failed`, and returns `OutcomePending`. If the record exists,
  the method dispatches on status. A separate `Shutdown(ctx) error` drains
  the in-flight goroutines or cancels via the parent ctx.
- Acceptance Criteria:
  - [ ] `Outcome` is a sealed sum implemented via an unexported method or
        type-switchable concrete types; consumers cannot accidentally add a
        new variant.
  - [ ] The semaphore slot is released exactly once per dispatched job
        (defer in the worker goroutine).
  - [ ] On queue saturation the in-memory state and the bbolt store are
        unchanged — no `pending` record is written, no slot is held.
  - [ ] `pool_test.go` covers: first submit creates pending, second submit
        with same tag while in-flight returns pending without dispatching a
        second worker, completion path is observable via the Store, queue
        full at the limit, completion-then-retry returns the upstream
        response, tombstoned-then-retry returns tombstoned, ctx cancellation
        from `Shutdown` stops outstanding workers.
  - [ ] No goroutine leak under the `goleak`-style assertion (or a simple
        runtime.NumGoroutine before/after with a small slack).
- Pitfalls & edge cases: the request body is `io.ReadCloser` and is consumed
  exactly once — the dispatched goroutine must own it (do NOT also use it on
  the synchronous response path). Closing the body twice is a real bug. The
  semaphore-claim-then-record-write sequence has a race window: if `Put`
  fails after the slot is claimed, the slot must be released and the error
  surfaced. The injected forwarder must accept its own `context.Context`
  separate from the inbound request ctx — the inbound ctx is cancelled the
  moment the 202 response is flushed.
- Code Example:
  ```go
  type Outcome interface{ isOutcome() }

  type OutcomePending struct{}
  func (OutcomePending) isOutcome() {}

  type OutcomeCompleted struct{ Response UpstreamResponse }
  func (OutcomeCompleted) isOutcome() {}

  type OutcomeTombstoned struct{}
  func (OutcomeTombstoned) isOutcome() {}

  type OutcomeQueueFull struct{}
  func (OutcomeQueueFull) isOutcome() {}
  ```
- Complexity: Hard

### Task 13: Implement the 60s GC tick
- Description: Create `internal/asyncjob/gc.go` with a `GC` type that owns a
  `Store`, the three TTL durations, and a clock function (injectable for
  tests). `Run(ctx)` ticks every 60s and in each pass executes three batch
  transitions in order: `pending` older than `pending_timeout` →
  `failed_timeout` (timestamp updated, response left absent); any of
  `completed` / `failed` / `failed_timeout` older than `complete_ttl` →
  `tombstone` (response payload stripped, `evicted_at` stamped); `tombstone`
  older than `tombstone_ttl` → batch DELETE. Each pass logs a single INFO
  line with the three counts (`async_gc_pass timed_out=N tombstoned=N
  deleted=N`). Cancellable via `ctx.Done()`.
- Acceptance Criteria:
  - [ ] One `time.NewTicker(60 * time.Second)` per `Run` invocation, stopped
        in `defer`.
  - [ ] Clock is injectable; tests drive deterministic transitions without
        sleeping for 60s.
  - [ ] Pass order is fixed (timeout → tombstone → delete) — assert via a
        test that seeds three records straddling all three transitions in one
        pass and observes the final states.
  - [ ] `gc_test.go` covers: empty bucket no-op, pending-past-timeout
        transition, completed-past-complete_ttl transition strips the
        response payload, tombstone-past-tombstone_ttl deletion, ctx
        cancellation exits the loop within one tick.
- Pitfalls & edge cases: the tombstone transition must strip
  `UpstreamResponse` — failing to do so means the bucket footprint never
  shrinks. The tick-driven goroutine must NOT panic out of `Run`; wrap each
  pass with a deferred recover that logs ERROR and continues, so a corrupt
  record cannot halt eviction forever.
- Complexity: Medium

### Task 14: Implement startup recovery (scan + DELETE pending)
- Description: Create `internal/asyncjob/recovery.go` with a single
  `RunRecovery(store Store, log *slog.Logger) error` that walks the `jobs`
  bucket once, collects every tag with `status = pending`, calls
  `Store.BatchDelete` over the collected set in one transaction, and logs

## Risks

- **Replay semantics ambiguity (Open Question 8).** Without a clear contract,
  clients will assume stronger guarantees than the server provides and lose
  data on long retries.
- **bbolt single-writer.** Multi-node deploys cannot share storage; v3 will
  need a different store or sharded routing.
- ~~**Restart-recovery body persistence (Open Question 4).**~~ Closed:
  Q4 resolved as "delete pending on restart, client retries". Request
  bodies are never persisted to bbolt, so the 5 GB worst-case disk-hit
  scenario does not apply. Replaced by the new "Restart drops in-flight
  jobs" risk below.
- **Restart drops in-flight jobs.** Any pending job at the moment of a
  daemon restart is deleted; the client receives `404` on poll and must
  resubmit. Clients that do not poll (fire-and-forget) lose the result
  silently. Mitigation: the operator docs must state "async = client must
  poll", and we log `restart_pending_dropped count=N` so operators can
  spot mass-loss after a crash.
- **Sanitiser drift.** Operator-supplied regexes can be wrong; a missed
  pattern silently leaks tokens to access logs.
- **Operational error-log leakage.** Even with sanitiser, transport-layer
  `host:port` strings can appear in error logs. Mitigation depends on
  Task 4's resolution.
- **Concurrency under load.** Semaphore-bounded worker pool is simple, but
  long-tail jobs can exhaust the slot pool while fast jobs queue behind
  them. Acceptable for v2; flag for v3 if observed in production.

## Trade-offs

Each entry records: the choice taken, the alternatives rejected, the
rationale, and the operator-visible consequence.

### Revision 1 — Endpoint topology

This entry supersedes the v1 plan's two-URL sketch
(`POST /v1/proxy/async/<scheme>/<rest>` for submit,
`GET /v1/proxy/async/result/<retry_tag>` for poll). After Q1–Q8 were
resolved, the user proposed a cleaner shape and we replanned in place.

- **Choice:** ONE endpoint, the existing `{METHOD} /v1/proxy/<scheme>/<rest>`
  surface from v1. Async-with-tag mode is enabled per-request by sending
  `Proxy-Retry-Tag: <tag>` on a standard proxy request:
  - Without the header → exact v1 sync behaviour (untouched).
  - With the header, tag new or in-progress → `202 Accepted` with
    response header `Proxy-Async-Status: pending`.
  - With the header, tag completed → upstream response verbatim
    (status code, headers, body) and NO `Proxy-Async-Status` header.
  - With the header, tag tombstoned → `410 Gone` (`tag_evicted`).
  - With the header, queue saturated → `503 Service Unavailable`
    (`queue_full`).
- **Rejected alternatives:**
  - *Two URL prefixes (submit at `/v1/proxy/async/<scheme>/...`,
    poll at `/v1/proxy/async/result/<tag>`).* Was the original v1
    sketch. Forces clients to learn two URL shapes for one feature,
    duplicates the client's original URL knowledge into a server-side
    state lookup on the poll path, and bakes a submit/poll asymmetry
    that the header-switched form eliminates entirely.
  - *Non-standard status code for "pending" (425 Too Early, 449
    Retry With).* Avoids the 202-vs-upstream-202 collision by picking
    a code upstream is unlikely to emit, but ties the contract to a
    standard the rest of the ecosystem doesn't speak. A discriminator
    header is cheaper and more honest.
- **Rationale:** the header-switched form matches HTTP convention —
  `Proxy-Authorization` already lives on this listener,
  `Cache-Control`, `If-Match`, `Expect`, etc. are all per-request
  mode switches that don't change the URL. The async-vs-sync
  collision on 202 is resolved by `Proxy-Async-Status: pending`: when
  the header is present the response is ours ("still pending"), when
  it's absent the response is upstream's (whatever they returned).
  Clients that adopt retry-tags add a header, not a new URL family.
- **Operator-visible consequence:**
  - No new routes on the API router; the route table is unchanged
    from v1.
  - No new HTTP handler files; `handlers/proxy.go` grows by one branch
    and one method (`serveAsync`). v1 sync clients see byte-identical
    behaviour.
  - Client-facing contract: "Check `Proxy-Async-Status: pending` on
    every 202. If present, our daemon owns the request and you should
    retry later with the same `Proxy-Retry-Tag`. If absent, the 202
    is the upstream's actual answer — treat it as a final response."
  - Operator docs must include a worked example showing the header
    check, because a casual reader of the status code alone would
    mis-parse pending vs upstream-202.

### Q1: Sanitiser config schema

- **Choice:** `api.log.path_sanitize_patterns` is an array of objects of
  the form `{"pattern": "<go-regex>", "replacement": "<go-replacement>"}`.
  Capture groups (`$1`, `${name}`) are supported in the replacement so the
  structural part of the path (e.g. `/bot`) can be preserved while only
  the secret segment is masked. Patterns are precompiled at config load;
  any `regexp.Compile` failure is a configuration error and the daemon
  refuses to start, naming the offending array index in the error.
- **Defaults shipped:** none. The operator docs include a copy-paste
  reference block with concrete examples (Telegram bot tokens, generic
  `api_key_<...>` segments, Slack webhook tokens) but the binary itself
  ships zero default patterns.
- **Rejected alternatives:**
  - *Single regex string.* Forces operators to combine all token
    families into one big alternation regex, which is error-prone and
    fragile to extend.
  - *Array of plain strings (implicit replacement).* Loses capture
    groups, which means the structural prefix (e.g. `/bot`) disappears
    from the log along with the token, destroying log readability and
    operator context.
  - *Ship a Telegram default.* If the upstream format ever shifts and
    our default no longer matches, we'd silently fail-open while the
    operator believes redaction is in place. Worse than no redaction
    because it removes urgency to verify the setup.
- **Rationale:** the object-with-capture form matches how every mature
  log scrubber (envoy, nginx, fluentbit) describes the same problem;
  precompile + fail-fast at config load means runtime is allocation-free
  on the hot path and a malformed regex can never reach production
  silently.
- **Operator-visible consequence:**
  - Sanitiser is opt-in: empty config = zero behavioural change.
  - Misconfigured regex blocks daemon start; operators learn at config
    deploy time, not after the token has leaked.
  - Adding a new token family is a config-only change (no rebuild, no
    deploy of new binary).

### Q2: Sanitiser scope

> Q2 was originally framed against the two-URL-prefix sketch ("does
> the sanitiser also cover the existing sync `/v1/proxy/` log, or only
> the new async log?"). Under the unified-endpoint topology
> (Revision 1) there is only one `/v1/proxy/` access log call site, so
> Q2 collapses to "the sanitiser runs there, full stop". The original
> framing is preserved below for traceability.

- **Choice:** the sanitiser applies to the single
  `/v1/proxy/<scheme>/<rest>` access log call site. Sync requests
  (no `Proxy-Retry-Tag`) and async-with-tag requests both flow
  through the same access log emission path, so a single precompiled
  `[]*regexp.Regexp` slice covers them both.
- **Rejected alternative:**
  - *Async-only sanitiser (under the old two-prefix sketch).* Would
    have left a known token-in-URL leak class (Telegram bot requests
    etc.) unredacted on the v1 sync path while we redacted the new
    async path. Obsoleted by the unified-endpoint topology — there
    is no "async-only path" to scope against any more.
- **Rationale:** the locked decision to apply sanitisation at log-write
  time (not at parse time) is only architecturally useful if it
  covers the access-log call site uniformly. Under unified topology
  that's one site, so the question is trivial — but the cost of
  asking it explicitly was a guarantee that no v1 sync request can
  leak a token that an async-with-tag request would have redacted.
- **Operator-visible consequence:**
  - One config block governs all `/v1/proxy/` access log lines;
    operators don't have to think about request mode.
  - The access log shape only changes if and when the operator
    configures patterns. Default behaviour is unchanged.

### Q3: Operational error log leakage

- **Choice:** two-layer redaction.
  1. **At source (typed unwrap).** `mapDoError` (sync `forwarder.go`)
     and its async equivalent use `errors.As` against known stdlib
     transport shapes (`*url.Error`, `*net.OpError`,
     `*tls.RecordHeaderError`) and emit a controlled short message
     (e.g. `"upstream dial timeout"`, `"upstream tls handshake failed"`)
     instead of the raw `.Error()` string. Client-supplied hostnames
     may remain in the message; resolved IPs and `host:port` pairs
     must not.
  2. **At write (slog handler safety net).** A new
     `internal/observability/scrubhandler.go` wraps the base slog
     `Handler`. Before each record is emitted, it regex-scrubs known
     `host:port` patterns out of string attribute values:
     - `\b(?:\d{1,3}\.){3}\d{1,3}:\d+\b` (IPv4:port)
     - `\[[0-9a-fA-F:]+\]:\d+` (`[IPv6]:port`)
     - `\b[a-zA-Z][\w.-]*\.[a-zA-Z]{2,}:\d+\b` (`hostname.tld:port`)
     Replacement is the literal string `<HOST:PORT>`.
- **Rejected alternatives:**
  - *Wrapper only.* Doesn't scale — every new `slog.Error("...", "err",
    err)` call site is a fresh chance to leak, and code review can't
    enforce that policy reliably over months.
  - *Scrub handler only.* The operator loses controlled-message
    context (`"dial of WHAT?"`), which costs real debug time. The
    scrub patterns also can't catch every exotic shape (unix sockets,
    raw IPv6 without brackets, etc.) — fine as a backstop but bad as
    the only defence.
  - *Accept the leak as operator-only-log risk.* Survives the current
    journal-only deploy, but the moment we add log shipping (Vector,
    Loki, Promtail) the leak suddenly fans out to a wider audience.
    We do not want this to be the day we re-discover Q3.
- **Rationale:** The wrapper is the disciplined fix at the known
  high-traffic leak point. The handler is the catchall for everything
  the wrapper doesn't see — new transport-error shapes, future code
  paths, code-review misses. Each layer alone is fragile; together
  they cover the same surface from both ends. The performance cost
  (~5 µs per log line for the regex pass) is negligible at the
  operational log volume the daemon produces.
- **Operator-visible consequence:**
  - Operational error messages stay informative — operators still see
    `"upstream tls handshake failed"` with the client-supplied
    hostname, not a useless `"upstream error"`.
  - Any `host:port` that does slip through is uniformly rewritten to
    `<HOST:PORT>` in logs, so operators learn quickly what the
    redaction signature looks like.
  - One new file to maintain (`scrubhandler.go`) and a small unit-test
    matrix; no operator-facing configuration knobs.

### Q4: Job recovery after daemon restart

- **Choice:** On daemon startup, scan the `jobs` bucket and DELETE every
  record with `status = pending` in a single bbolt transaction. Log
  `restart_pending_dropped count=N` at INFO. Completed, failed,
  failed_timeout, and tombstone records survive untouched. Request bodies
  are NEVER persisted to bbolt — only metadata and (on completion) the
  upstream response are stored.
- **Rejected alternatives:**
  - *Recover & continue.* Would require persisting up to 50 MB request
    bodies to bbolt on every submit (100 concurrent × 50 MB = 5 GB
    worst-case active footprint, plus fsync-pressure on the hot submit
    path). It also automatically re-executes every in-flight request on
    restart, which silently doubles non-idempotent upstream side effects
    with no client signal.
  - *Mark failed (`restart_aborted`).* Breaks the `Proxy-Retry-Tag` contract:
    a client retrying with the same tag after a restart would receive
    `409 tag_completed` and be unable to recover idempotently — they'd
    have to invent a new tag, defeating the whole purpose of the header.
- **Rationale:** The async endpoint exists for clients that poll. A
  `404 Not Found` after a restart is a clean signal — "daemon does not
  know this tag" — and the client is free to resubmit with the same tag,
  which is treated as a fresh first submit. The tag stays idempotent
  across restarts, submits remain fast (no body persistence), and the
  double-execute decision is moved from "server, automatically and
  silently" to "client, explicitly and visibly". bbolt is itself
  crash-safe (WAL + COW), so we never see partial-state records — only
  fully-pending or fully-completed.
- **Operator-visible consequence:**
  - `pending_jobs_count` drops to 0 immediately after restart, then
    climbs as new submits arrive. Operators can confirm recovery from
    the count and the `restart_pending_dropped` log line.
  - The "async = client must poll" expectation is now load-bearing — a
    client that submits and never polls will silently lose work on
    daemon restart. This must be called out explicitly in the operator
    docs.
  - bbolt file size is bounded by completed/failed/tombstone records
    only; the worst case is much smaller than the previously feared
    multi-GB footprint.

### Q5: Worker pool package placement

- **Choice:** new package `internal/asyncjob/` owns the entire async-job
  lifecycle:
  - `store.go` — bbolt CRUD + state transitions
    (`pending → completed | failed | failed_timeout → tombstone → DELETE`).
  - `pool.go` — semaphore-bounded worker pool (`max_concurrent_jobs`).
  - `gc.go` — 60s tick goroutine driving the state transitions.
  - `recovery.go` — startup scan-and-DELETE of `pending` records.
  - `record.go` — JSON record types and status enum.
  No new HTTP handler files are introduced — the existing
  `handlers/proxy.go` gains a single branch at the top of `ServeHTTP`:
  if `Proxy-Retry-Tag` is present, dispatch to a new `serveAsync`
  method on the same handler that calls into `asyncjob.SubmitOrFetch`
  (and writes the 202/410/503/passthrough response); otherwise the
  existing v1 sync flow runs unchanged. See Trade-offs entry
  "Revision 1 — Endpoint topology" for the topology decision that
  drives this layout.
- **Rejected alternatives:**
  - *All in `internal/transport/apiserver/handlers/`.* Would smuggle a
    stateful subsystem (bbolt, GC, recovery) into a package whose
    stated role is "HTTP handlers". Violates the "business logic
    organized by concern, not by launcher" rule in CLAUDE.md.
  - *Two thin handlers `handlers/async_submit.go` and
    `handlers/async_poll.go` calling into `asyncjob`.* Was the
    initial sketch in this plan; obsoleted by the unified-endpoint
    revision (the submit/poll asymmetry no longer exists once a single
    `Proxy-Retry-Tag`-bearing request handles both submit and retry).
  - *`internal/async/`.* Functionally identical to `asyncjob/` but the
    bare word `async` is vague ("async what?"). `asyncjob` names the
    actual unit of work being managed.
- **Rationale:** mirrors the established v1 split — `internal/tunnel/`
  owns tunnel lifecycle and `handlers/` owns HTTP handlers that call
  into it. The same shape is correct here. The new package also gives
  us a clean seam to define an `asyncjob.Store` interface for unit
  tests of the HTTP handlers (no bbolt in handler tests).
- **Operator-visible consequence:**
  - One more directory in the tree (`internal/asyncjob/`); composition
    root in `cmd/vpntunnel/main.go` gains a new `asyncjob.New(...)`
    wiring call alongside the existing pool/wgconf/tunnel wiring.
  - No new HTTP handler files. The existing `handlers/proxy.go` grows
    by one branch + one method (`serveAsync`); the v1 sync path
    remains byte-identical for requests without `Proxy-Retry-Tag`.
  - No change to HTTP route table, on-wire URL shape, or operator-facing
    config beyond what other Q-decisions added.

### Q6: Metrics surface

- **Choice:** v2 ships no new metrics transport. The counts already on
  `/v1/admin/health` — `pending_jobs_count`, `completed_jobs_count`,
  `tombstone_jobs_count` — are the v2 metrics surface. Rate, depth, and
  age distributions are deferred to v3.
- **Rejected alternatives:**
  - *Prometheus exporter.* Standard for prod observability, but
    enterprise-grade for a single-host systemd unit. Adds a dependency
    (`prometheus/client_golang`), forces a placement decision (HTTPS API
    listener behind admin token vs separate plaintext port), and
    expands the v2 scope into a new transport-level surface.
  - *expvar at `/debug/vars`.* Built-in stdlib, zero new deps, free
    Go-runtime metrics. The most attractive deferred candidate — when
    operator pain materialises, this is the recommended next step
    (mount behind admin role on the existing HTTPS API listener,
    scrape with `curl /debug/vars | jq`).
  - *OTLP push.* Requires running an OTLP collector somewhere.
    Disproportionate infra for a single-host daemon.
  - *Health-endpoint extension with rate / median-pending-age.* Rate
    computation needs a rolling window in memory; median-pending-age
    is `O(N)` per request. Adding these silently makes `/v1/admin/health`
    more expensive — undesirable for an endpoint a deploy script
    polls during release verification.
- **Rationale:** v1 has zero metrics surface and has not suffered for
  it. Counts are sufficient for sanity checks; operators can derive
  rate by sampling the counts at two points in time. Adding a metrics
  transport now solves a problem nobody has reported. Locking the
  scope keeps v2 shippable.
- **Operator-visible consequence:**
  - No new HTTP endpoint, no new port, no new auth role.
  - Operators inspect async health via the existing
    `curl -k https://127.0.0.1:8888/v1/admin/health` with an admin
    token (already part of the v1 release-verification step).
  - If real time-series visibility becomes necessary, the recommended
    upgrade path is expvar behind admin role — additive, no breaking
    change to the existing surface.

### Q7: Distributed deploy

- **Choice:** v2 is **single-node only**. The bbolt file at
  `/opt/vpntunnel/state/async.db` lives on one host; retry-tag routing
  trivially works because there is exactly one daemon. No tag-aware
  routing, no replication, no shared storage in v2.
- **Rejected alternatives:**
  - *Design for multi-node now.* Would require either (i) tag-aware
    routing to the daemon that holds the bbolt file, or (ii) a shared
    backend (Postgres, Redis, etcd) replacing bbolt. Both are major
    architectural changes for a problem that does not exist today
    (production runs on one host).
- **Rationale:** "design for the deployment you have, not the
  deployment you might one day have" (the same principle that kept
  v1 single-binary single-host). Once a real second-node requirement
  appears, the v3 design starts from observed traffic patterns and
  failure modes instead of architectural speculation.
- **Operator-visible consequence:**
  - No change vs the v1 deploy story: one binary, one host, one
    bbolt file alongside the existing config tree.
  - The v3 boundary is named in this plan's Risks ("bbolt
    single-writer") so the next operator-pain conversation has a
    clear pointer.

### Q8: Replay-safety semantics

- **Choice:** Tombstone-based `410 Gone`. GC transitions records past
  `complete_ttl` from `completed`/`failed`/`failed_timeout` to `tombstone`
  (payload stripped, only `evicted_at` retained). Any request whose
  `Proxy-Retry-Tag` matches a tombstone returns `410 Gone` with code
  `tag_evicted`, regardless of whether it's the first attempt or a
  retry (with the single-endpoint topology those two are
  indistinguishable to the server and to the client contract).
  Tombstones themselves age out after `tombstone_ttl` (default `24h`,
  configurable via `api.async.tombstone_ttl`).
- **Status matrix refinement:** the v1 plan's "404 for unknown/expired"
  text predates both the unified-endpoint revision and this Q8
  resolution. With the revised topology there is **no** `404` in
  async-with-tag mode — an unrecognised tag is treated as a fresh
  first-time submit (which is the whole point of header-driven
  idempotency), and the only "your tag is gone" signal is `410 Gone`
  on a tombstoned tag. The 410 split is therefore not a refinement of
  404 but a replacement of it for the async-with-tag mode.
- **Rejected alternatives:**
  - *Poll extends TTL.* Does not solve the actual footgun — clients that
    retry after long silence are exactly the ones who never poll. Also lets
    a long-lived client pin storage indefinitely.
  - *Pure documentation contract.* Zero implementation cost but real-world
    risk that clients won't read the docs, then discover the duplicate
    side-effect (duplicate payment, duplicate upstream write) in
    production rather than in dev.
- **Rationale:** Tombstones give clients a deterministic, bounded
  idempotency window (~25h with defaults: 1h `complete_ttl` + 24h
  `tombstone_ttl`) with an explicit "result lost, treat as hard failure"
  signal. The storage cost is small: tombstone records are ~80 bytes;
  worst case 100 jobs/min × 60 × 24 ≈ 144k tombstones ≈ ~11 MB on disk.
  Failed jobs go through the same path so the footgun is closed for both
  success and failure outcomes.
- **Operator-visible consequence:**
  - `async.db` carries up to ~11 MB of tombstone records past the
    completed working set (negligible vs the 50 MB body cap × pending
    pool).
  - `/v1/admin/health` gains a `tombstone_jobs_count` field so operators
    can spot eviction-tail growth without opening the file.
  - Operators get a new tunable, `api.async.tombstone_ttl`, with a sane
    default; longer values cost more disk, shorter values shrink the
    idempotency window.
  - Client-facing contract: "Your tag is safe to retry for
    `complete_ttl + tombstone_ttl` after submission. Within
    `complete_ttl` you get the original result; within `tombstone_ttl`
    after that you get `410 Gone` — treat as hard failure, do not retry
    with the same tag. After both windows expire the tag is reusable and
    the request may execute again."
