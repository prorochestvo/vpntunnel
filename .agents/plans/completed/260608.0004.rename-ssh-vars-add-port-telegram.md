# Task Breakdown

## Overview

Align the SSH-related environment variables in `staging.yml` and `release.yml`
with the fx_rate_monitor naming convention, add support for a non-standard SSH
port, and add Telegram success/failure notifications. The two GH Environments
(`staging`, `production`) keep their isolation; only the variable names inside
each environment change, so the same identifier (e.g. `SSH_HOSTNAME`) resolves
to different values in each environment.

The current scheme uses environment-prefixed names (`STAGING_HOST`, `PROD_HOST`,
…) because the workflows were drafted before the GH Environment scoping was
understood as load-bearing. The prefix is now redundant — environments already
isolate the values — and the prefix-less naming reduces drift between the two
workflow files. The fx_rate_monitor project already uses this style; adopting
it here keeps the operator mental model unified across the two projects.

Beyond the rename, the operator's SSH daemon listens on a non-standard port,
so a new `SSH_HOSTPORT` variable must be threaded into `appleboy/ssh-action`'s
`port:` input.

## Assumptions

- `appleboy/ssh-action@v1` honors a numeric `port:` input — confirmed in its
  README.
- GH Environments fully scope `vars.*` and `secrets.*` lookups by environment.
  Two environments with the same variable name resolve to different values; no
  cross-environment leakage.
- The host fingerprint variable is renamed to `SSH_FINGERPRINT` (not removed)
  — `appleboy/ssh-action` still needs it; we are not switching to a `ssh-keyscan`-in-runtime
  approach.
- Telegram notifications use the same env-scoped pattern: `secrets.TELEGRAM_TOKEN`
  + `vars.TELEGRAM_ROOT_CHAT_ID`. Operator will create these in both
  environments before the next deploy.
- The operator will recreate GH variables/secrets under the new names before the
  next deploy. There is **no overlap window** where both schemes are read — old
  names are deleted from the workflow in the same commit that introduces the
  new ones. This is acceptable because the operator controls deploy timing.

## Tasks

### Task 1: Rename SSH variables in `staging.yml`

- Description: Replace every reference to `STAGING_HOST`, `STAGING_USER`,
  `STAGING_FINGERPRINT`, `STAGING_SSH_KEY` with `SSH_HOSTNAME`, `SSH_USERNAME`,
  `SSH_FINGERPRINT`, `SSH_PRIVATEKEY` respectively. Add a new `SSH_HOSTPORT`
  variable and thread it into the `appleboy/ssh-action`'s `port:` input. Update
  the assertion step's variable list to include `SSH_HOSTPORT`.
- Acceptance Criteria:
  - `grep -E 'STAGING_(HOST|USER|FINGERPRINT|SSH_KEY)' staging.yml` returns no
    matches.
  - `port: ${{ vars.SSH_HOSTPORT }}` appears in the ssh-action step.
  - Assertion step iterates `SSH_HOSTNAME SSH_HOSTPORT SSH_USERNAME SSH_FINGERPRINT`.
  - Workflow Summary step uses `vars.SSH_HOSTNAME` for `HOST=…`.
- Pitfalls & edge cases:
  - `appleboy/ssh-action` accepts `port:` as string; bash assertion via `[ -z … ]`
    is sufficient and does not need integer validation.
  - Don't add the secret to the assertion loop — GHA masks empty secrets the
    same as set ones (already documented as a comment in the existing file).
- Complexity: Easy

### Task 2: Rename SSH variables in `release.yml`

- Description: Mirror Task 1 on the production workflow. Replace `PROD_HOST`,
  `PROD_USER`, `PROD_FINGERPRINT`, `PROD_SSH_KEY` with the prefix-less names.
  Add `SSH_HOSTPORT`. Update assertion and Workflow Summary.
- Acceptance Criteria:
  - `grep -E 'PROD_(HOST|USER|FINGERPRINT|SSH_KEY)' release.yml` returns no
    matches.
  - Same shape as Task 1.
- Pitfalls & edge cases:
  - Concurrency group `deploy-production` and required-reviewer rule on the
    `production` environment are unrelated to the rename — leave them alone.
- Complexity: Easy

### Task 3: Add Telegram notify steps to both workflows

- Description: Add `Notify success` (`if: success()`) and `Notify failure`
  (`if: failure()`) steps at the end of the `deploy` job in both workflows,
  modelled on `fx_rate_monitor`'s `stage.yml`/`prime.yml`. Each posts a one-line
  message to Telegram with the environment label, ref name, and (for failure) a
  link to the Actions run.
- Acceptance Criteria:
  - Both steps use `|| true` so a Telegram outage does not flip the job status.
  - Success message in `staging.yml` reads `[STAGING] Deploy succeeded. Ref: …`
    and in `release.yml` reads `[PRODUCTION] Deploy succeeded. Ref: …`.
  - Failure message includes `${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}`.
  - Token never appears in logs — passed via `env:` block, referenced by
    variable expansion in the `curl` body, not interpolated into the URL via
    `${{ … }}` (which would land in the run log on errors).
- Pitfalls & edge cases:
  - `parse_mode=Markdown` is unnecessary for plain text — omit it to avoid
    accidental markdown parsing of branch names with underscores (e.g. `v1.2_rc`).
  - Don't add Telegram as a hard dependency for the existing Workflow Summary
    step — keep both.
- Complexity: Easy

### Task 4: Update `CLAUDE.md` to reflect the new variable names

- Description: Replace `STAGING_SSH_KEY`, `PROD_SSH_KEY`, `STAGING_FINGERPRINT`,
  `PROD_FINGERPRINT` references in the Constraints section with the new names
  and note the addition of `SSH_HOSTPORT`.
- Acceptance Criteria:
  - `grep -E 'STAGING_|PROD_' CLAUDE.md` returns no matches (other than
    historical references in `plans/completed/`, which are out of scope).
  - The Constraints bullet captures the per-host-ed25519, per-environment-scoped
    rule with the new names.
- Pitfalls & edge cases:
  - Do not rewrite the entire Constraints section — narrowly edit the two
    bullets that name the variables.
- Complexity: Easy

### Task 5: Update `SECURITY.md` and `README.md`

- Description: Replace old variable names in `SECURITY.md` (one line) and in
  `README.md`'s deploy-secrets tables (~10 lines plus the surrounding prose
  about creating GH Environments). Add `SSH_HOSTPORT` row to each table.
  Document the Telegram variables.
- Acceptance Criteria:
  - `grep -E 'STAGING_(HOST|USER|FINGERPRINT|SSH_KEY)|PROD_(HOST|USER|FINGERPRINT|SSH_KEY)' README.md SECURITY.md` returns no matches.
  - Both environment tables list: `SSH_HOSTNAME`, `SSH_HOSTPORT`, `SSH_USERNAME`,
    `SSH_FINGERPRINT`, `SSH_PRIVATEKEY`, `TELEGRAM_TOKEN`, `TELEGRAM_ROOT_CHAT_ID`.
- Pitfalls & edge cases:
  - The README has a migration section (`If you previously set up the repo
    with DEPLOY_SSH_KEY…`); add a similar note for the rename so an operator
    upgrading does not get stranded.
- Complexity: Medium

## Execution Order

1. Task 1 — rename in `staging.yml`.
2. Task 2 — rename in `release.yml`.
3. Task 3 — Telegram steps in both.
4. Task 4 — `CLAUDE.md` updates.
5. Task 5 — `SECURITY.md` + `README.md` updates.

No cross-task dependency strictly forces this order; following it keeps each
diff atomic per file group.

## Risks

- **Operator forgets to recreate GH variables under the new names.** First
  deploy after merge fails with the existing "Required variable 'X' is not
  set" assertion — recoverable, not catastrophic.
- **Both environments end up with different variable values under the same
  name and the operator confuses them when reading logs.** Mitigated because
  GH Environments label the run with the environment name in the UI.
- **Telegram token leakage via log echoing.** Mitigated by passing the token
  only via `env:` and never inlining it into a step's `run:` string with `${{ … }}`.

## Trade-offs

- Prefix-less names are tighter but slightly harder to grep across the repo
  when debugging which workflow uses which value. Net win because the workflow
  files diverge less.
- Renaming in-place (without a transition window where both old and new are
  read) means the deploy is broken for the few minutes between merge and the
  operator setting up the new variables. Accepted because deploys are
  operator-initiated for production and trivially recoverable for staging.
