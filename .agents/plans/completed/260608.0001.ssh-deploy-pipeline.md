# Task Breakdown

## Overview

v4 shipped the image to `ghcr.io/<owner>/httpproxy:<version>`. The operator
still has to SSH in themselves to roll the container. Plan 006 closes that
loop: GH Actions SSHes to the server immediately after `publish` succeeds,
points the server's `compose.yml` at the new tag via the `IMAGE_TAG` env
var, runs `docker compose pull && docker compose up -d --wait`, and fails
the workflow loudly if the HEALTHCHECK doesn't go green inside the
timeout. One outcome: operator pushes `v1.2.3`, image is live on the
server within ~3 minutes, workflow run is green.

Seven concrete deliverables:

1. **Repo `compose.yml` adopts `${IMAGE_TAG}`** (no default — fail loud
   if unset). Clean break from the v4 literal `:latest`.
2. **`Makefile` `docker-run` honors `IMAGE_TAG`**, defaulting to `dev`.
   Same template the server uses; consistent operator UX.
3. **`release.yml` `publish` job exposes `image_tag` as a job output**,
   pulled from `docker/metadata-action`'s `version` output (`1.2.3` for
   tag `v1.2.3`). Versioned, deterministic, never `latest`.
4. **`release.yml` `deploy` job**, `needs: publish`, constant-key
   `concurrency` group (Risk (g)), `appleboy/ssh-action@v1` with
   pinned `fingerprint`. Script: `set -euo pipefail`, `cd
   /opt/httpproxy`, `docker compose pull && docker compose up -d --wait
   --wait-timeout 120`. Non-zero exit fails the workflow.
5. **`$GITHUB_STEP_SUMMARY` one-liner** appended on success or failure
   so the workflow run page reads at a glance.
6. **README `## Deploy` section rework**: server-side prerequisites,
   GH secrets/variables setup, rollback, hardening follow-ups, v4 → v5
   cutover note.
7. **`CLAUDE.md` Project State** one-line update; no layer-table or
   route changes.

What v5 explicitly does NOT ship: separate `deploy.yml`, multi-server
matrix, staging environment, blue/green deploy, watchtower / webhook /
Ansible, in-place `sed` of server's compose.

Net diff: ~80 lines in `release.yml`, ~5 lines each in `compose.yml`
and `Makefile`, ~200 lines in `README.md`, ~3 lines in `CLAUDE.md`.
Zero Go changes.

## Assumptions

### Locked decisions (from user spec — do NOT revisit)

- Extend `release.yml` with a `deploy` job that `needs: publish`.
  No separate `deploy.yml`. Failed job is re-run via the Actions UI.
- SSH action: `appleboy/ssh-action@v1` (major float, consistent with the
  rest of `release.yml`). SHA-pinning is on the hardening follow-up
  list, not in scope.
- Image tag delivery: inline env on the same shell line as
  `docker compose ...`. No `.env` file mutation, no in-place `sed`.
- Health verification: `docker compose up -d --wait` (requires Compose
  v2.17+). No curl from GHA, no admin-port exposure beyond loopback.
- Server-side state at `/opt/httpproxy/` (FHS convention), owned by
  dedicated `httpproxy` user in the `docker` group. No sudo at deploy.
- SSH key: ed25519, dedicated per server, stored as `DEPLOY_SSH_KEY`
  GH secret. Public key in `~httpproxy/.ssh/authorized_keys`.
- Strict host key checking: pinned via action's `fingerprint:` input
  (obtained with `ssh-keyscan -t ed25519 <host>`). Never
  `StrictHostKeyChecking=no`.
- `concurrency:` on the deploy job. (Group key: see Risk (g) — the
  user spec said "same as publish", this plan corrects to a constant
  `release-deploy` after analysis.)
- Rollback is manual: re-tag an earlier commit, push, workflow
  re-deploys.
- Single server. `SERVER_HOST` / `SERVER_USER` / `SERVER_FINGERPRINT`
  are scalar variables; multi-server matrix is a future plan.
- No staging environment. No blue/green. ~3s of proxy unavailability
  on `docker compose up -d` is acceptable.

### Open design decisions resolved in this plan

- **Server-side `compose.yml` is operator-owned**, hand-authored once
  during setup. The deploy job NEVER copies the repo's `compose.yml` to
  the server. Server-side may legitimately diverge (sidecars, volume
  paths, env_file pointers) and shouldn't be clobbered on every deploy.
  Repo and server compose share a template, not identity.
- **`IMAGE_TAG` lives inline** on the same shell line as `docker compose
  ...`, NOT in a `.env` file. Stateless; no file goes stale. Cost:
  operator queries `docker inspect <container>` for "what's running"
  rather than `cat .env`. That's the source of truth either way.
- **`${IMAGE_TAG}` bare, no default**. Missing env → Compose fails loud.
  A `:-latest` fallback would silently defeat pinning.
- **Repo `compose.yml` migrates to the same `${IMAGE_TAG}` shape** as
  the server's. One mental model; clean `make docker-run` story. Cost:
  one-line v4 → v5 cutover (Task 9 cutover note).
- **`Makefile` `docker-run` accepts `IMAGE_TAG` from env, defaults to
  `dev`.** `IMAGE_TAG ?= dev` at the file top-level.
- **`cd /opt/httpproxy` is the first script line** after
  `set -euo pipefail`. `appleboy/ssh-action`'s default working directory
  is `~httpproxy/`, which has no `compose.yml`.
- **No auto-rollback on `--wait` timeout.** Workflow goes red; operator
  diagnoses via `docker compose logs httpproxy`. Auto-revert masks the
  underlying bug.
- **`publish.outputs.image_tag = steps.meta.outputs.version`** from
  `docker/metadata-action`. For a `type=semver,pattern={{version}}` tag,
  this is the stripped semver (`1.2.3` for `v1.2.3`). Do NOT use
  `${{ github.ref_name }}` — that keeps the leading `v` and doesn't
  match what got pushed to GHCR.

### Cross-plan contract with v4 (Plan 004 / Plan 005)

- **`/healthz` contract (Plan 005).** Plan 006 relies on the existing
  HEALTHCHECK baked into the Dockerfile by Plan 004. The TCP-dial probe
  becomes "real" once Plan 005's admin listener is bound; since both have
  shipped, `docker compose up -d --wait` blocks on the same probe that
  `docker inspect ... .State.Health.Status` exposes. No new endpoint, no
  new probe path.
- **`Dockerfile` HEALTHCHECK interval = 30s, start-period = 10s,
  timeout = 5s, retries = 3.** That means `--wait` may wait up to
  `10s start-period + 3 * (30s interval + 5s timeout)` = 115s worst case
  before reporting unhealthy. Docker Compose's `--wait` default timeout
  is 60s — TOO SHORT for our HEALTHCHECK shape. Documented as a Pitfall
  and a Risk. Operator must pass `--wait-timeout 120` or longer to the
  `docker compose up` command, OR shorten the HEALTHCHECK interval.
  Locked decision in this plan: bump the deploy script's `--wait-timeout`
  to 120s. Cleaner than touching the Dockerfile.

## Tasks

### Task 1: Repo `compose.yml` — adopt `${IMAGE_TAG}`

- **Description:** Edit `/compose.yml` — replace the literal `:latest`
  on the image line with `${IMAGE_TAG}` (no default). Final shape:

  ```yaml
  services:
    httpproxy:
      image: ghcr.io/<owner>/httpproxy:${IMAGE_TAG}
      # ports / volumes / restart unchanged
  ```

  Do NOT add a `:?error` suffix or a `:-latest` fallback. Bare
  `${IMAGE_TAG}` already fails loud (Compose emits "variable is not
  set" and renders an empty tag).

- **Acceptance Criteria:**
  - [x] `compose.yml` references `${IMAGE_TAG}` rather than a literal tag.
  - [x] `IMAGE_TAG=dev docker compose config` (after substituting
        `<owner>`) renders `image: ghcr.io/<owner>/httpproxy:dev`.
  - [x] `docker compose config` with `IMAGE_TAG` unset warns about the
        unset variable and renders an empty tag.
  - [x] No `:?...` or `:-...` decorator on the variable.
- **Pitfalls & edge cases:**
  - Brace form `${IMAGE_TAG}` is mandatory in Compose; bare
    `$IMAGE_TAG` breaks parsing in some contexts.
  - v4 operators with existing on-server `compose.yml` files must edit
    their copy during cutover (Task 9 note covers this).
  - `docker compose pull` with unset `IMAGE_TAG` tries to pull
    `httpproxy:` and fails — desired in CI, confusing if an operator
    hand-runs Compose without setting the env. README examples must
    set the env on every invocation.
- **Complexity:** Easy.

### Task 4: `release.yml` `deploy` job — SSH + compose up --wait

- **Description:** Add a new `deploy` job to
  `.github/workflows/release.yml`, after `publish`. Job spec:

  ```yaml
    deploy:
      needs: publish
      runs-on: ubuntu-latest
      concurrency:
        group: release-deploy
        cancel-in-progress: false
      steps:
        - name: SSH and roll the container
          uses: appleboy/ssh-action@v1
          with:
            host: ${{ vars.SERVER_HOST }}
            username: ${{ vars.SERVER_USER }}
            key: ${{ secrets.DEPLOY_SSH_KEY }}
            fingerprint: ${{ vars.SERVER_FINGERPRINT }}
            command_timeout: 5m
            script: |
              set -euo pipefail
              cd /opt/httpproxy
              export IMAGE_TAG="${{ needs.publish.outputs.image_tag }}"
              docker compose pull
              docker compose up -d --wait --wait-timeout 120
        - name: Workflow summary
          if: always()
          run: |
            STATUS="${{ job.status }}"
            TAG="${{ needs.publish.outputs.image_tag }}"
            HOST="${{ vars.SERVER_HOST }}"
            if [ "$STATUS" = "success" ]; then
              echo "✅ httpproxy ${TAG} deployed to ${HOST}, /healthz OK" >> "$GITHUB_STEP_SUMMARY"
            else
              echo "❌ httpproxy ${TAG} deploy to ${HOST} failed (status=${STATUS})" >> "$GITHUB_STEP_SUMMARY"
            fi
  ```

  Key design notes:
  - `concurrency.group: release-deploy` (constant, NOT per-`github.ref`)
    serializes deploys across different tags hitting the same server.
    Risk (g) covers why per-ref is wrong here.
  - `vars.*` for `SERVER_HOST` / `SERVER_USER` / `SERVER_FINGERPRINT`
    (not secrets — none of these is sensitive; auditability beats
    pseudo-secrecy). `secrets.DEPLOY_SSH_KEY` for the private key (real
    secret, auto-masked).
  - `fingerprint:` input enforces strict host key checking. Without it
    the action defaults to `StrictHostKeyChecking=no` — rejected.
  - `command_timeout: 5m` overrides the action's default 10min. Sized
    to fit a large image pull (~3 min) plus the 120s `--wait`.
  - `set -euo pipefail`: `-u` catches an empty `IMAGE_TAG` (regression
    in Task 3) at the `export` line.
  - `--wait-timeout 120`: sized against the v4 Dockerfile HEALTHCHECK
    worst case (115s). Document the dependency in the workflow as a
    YAML comment. Risk (b) covers drift.
  - Summary step uses `if: always()` so the failure path also appends.
    Script `exit 1` propagates via the SSH action's exit code; workflow
    goes red regardless.

- **Acceptance Criteria:**
  - [x] New `deploy` job exists in `release.yml`, sequenced after
        `publish` via `needs: publish`.
  - [x] `concurrency` block on the deploy job uses the constant key
        `release-deploy` (NOT per-`github.ref`) with
        `cancel-in-progress: false`.
  - [x] `appleboy/ssh-action@v1` (major float, intentional) used with
        `host`, `username`, `key`, `fingerprint`, `command_timeout`,
        `script` inputs.
  - [x] `host`, `username`, `fingerprint` read from `vars.*`, not
        `secrets.*`.
  - [x] `key` reads from `secrets.DEPLOY_SSH_KEY`.
  - [x] Script starts with `set -euo pipefail`.
  - [x] Script `cd /opt/httpproxy` before any docker command.
  - [x] Script exports `IMAGE_TAG="${{ needs.publish.outputs.image_tag }}"`
        before both `docker compose pull` and `docker compose up`.
  - [x] `docker compose up -d --wait --wait-timeout 120`.
  - [x] Workflow-summary step writes a one-liner to `$GITHUB_STEP_SUMMARY`
        on both success and failure (`if: always()`).
  - [x] YAML validates.
  - [ ] Manual smoke: push a throwaway tag (e.g. `v0.0.0-rc-deploy`); the
        deploy job runs to completion; `ssh httpproxy@<server> 'docker
        inspect --format={{.State.Health.Status}} httpproxy'` reports
        `healthy`; the workflow summary shows the success line.
        (requires live server + GH Actions run; not executable in the engineer's local environment)
- **Pitfalls & edge cases:**
  - **Docker Compose v2.17+ required for `--wait`.** Older versions
    error with `unknown flag: --wait`. Pin documented in README §7.
    Rejected workaround: polling `docker inspect ... Health.Status`
    from the script duplicates `--wait` and hides the version mismatch.
  - **`appleboy/ssh-action`'s `script:` runs in a single non-
    interactive bash shell.** Multi-line YAML scalar is fine; standard
    quoting rules apply. Don't use `command:` (deprecated alias) or
    `commands:` (doesn't exist).
  - **GHCR auth from the server.** Public package = no auth needed for
    `docker compose pull`. If the operator later flips the package to
    private, the server needs `docker login ghcr.io` with a PAT — same
    deploy job would break. Document the implication.
  - **GHCR `docker pull` rate-limit (429).** GHCR doesn't publish a
    limit today but reserves the right. Script exits non-zero on 429;
    workflow goes red; operator retries the job. Risk-acceptable.
  - **GHA `${{ ... }}` interpolation happens BEFORE the script reaches
    the server**, so `set -u` doesn't fire on the `export` line even if
    the substitution produced an empty string. The empty `IMAGE_TAG`
    surfaces downstream as a Compose `image not found` error. Fail-
    loud, just one indirection away.
  - **`vars.*` is case-sensitive.** GH UI normalizes display to upper-
    case but the lookup is not. Match the workflow file exactly.
  - **`needs.publish.outputs.image_tag` empty if `publish` is skipped
    or fails.** `needs: publish` guards both cases (deploy won't run).
    A future `if:` on `publish` could regress this; trust `set -u`
    plus the eventual `image not found` to keep it fail-loud.
  - **`command_timeout: 5m` is wall-clock.** Slow link / large image
    → deploy fails at 5min. Operator tunes per host.
  - **Secrets are auto-masked in logs; variables are not.** Intentional
    — `vars.SERVER_HOST` showing up in `set -x` output is the audit
    trail. `DEPLOY_SSH_KEY` never appears.
- **Complexity:** Medium.

    to fail healthcheck.
  - **Recipe**: `git log --oneline --tags | head` to find the old
    commit; `git tag v1.0.1-rollback <oldsha> && git push origin
    v1.0.1-rollback`. Workflow re-runs end-to-end. Use a fresh tag —
    re-pushing an existing tag is messy (delete + re-create) and
    breaks immutability expectations.
  - **Expected timeline**: ~2-3 minutes from `git push` to served
    traffic on the rolled-back image.
  - **Soft floor caveat**: rollback to a pre-Plan-006 commit re-runs
    that older `release.yml`, which may not have a `deploy` job at
    all. Even if it does, the server's current `compose.yml` uses
    `${IMAGE_TAG}` so the env-var pattern works against any tag the
    pipeline pushed AFTER Plan 006. Realistic floor: tags built after
    Plan 006 ships.
  - **Source of truth for "what's running"**: `docker inspect httpproxy
    --format='{{.Config.Image}}'` on the server. NOT any file, NOT
    `compose.yml`, NOT the workflow run history.
  - **`:latest` semantics post-rollback**: `metadata-action` still
    publishes `:latest` against the most recently pushed tag, so
    pulling `:latest` after a rollback gets the rolled-back image.
    Consistent with "the last `docker push` wins".

## Risks

- **(a) Docker Compose v2.17+ missing on server.** First deploy fails
  with `unknown flag: --wait`. Mitigation: README §7 pins the version
  and provides `docker compose version` verification. Recovery: upgrade
  Compose, re-run the failed job (~5 min).
- **(b) HEALTHCHECK shape drift.** `--wait-timeout 120` is sized
  against the v4 Dockerfile's `start-period=10s + 3*(interval=30s +
  timeout=5s) = 115s` worst case. A future plan loosening the interval
  (e.g. `--interval=60s`) makes 120s too short → false-positive deploy
  failures. Mitigation: comment the dependency in `release.yml`; bump
  in lockstep with any Dockerfile HEALTHCHECK edit.
- **(c) SSH key compromise.** `DEPLOY_SSH_KEY` grants shell access to
  the `httpproxy` server account. Threat: GH org member with workflow-
  edit rights exfiltrates via a malicious workflow step. Mitigation:
  limit org write access; audit workflow PRs; periodic rotation
  (procedure in README §8). Hardening follow-up: `command=` restriction
  shrinks blast radius to "can re-run the deploy script".
- **(d) Server clock skew → GHCR auth TTL rejection.** Clock >5 min off
  UTC → expired tokens. Mitigation: operator runs `chrony` /
  `systemd-timesyncd`. Not documented in plan; implied by modern distro
  baseline.
- **(e) Operator forgot `usermod -aG docker httpproxy`.** Manual deploy
  hits `permission denied ... docker.sock`. Mitigation: README §7
  spells out the step AND the log-out/log-back-in requirement.
- **(f) `--wait-timeout` insufficient for slow WireGuard handshake.**
  Bad/distant peer → handshake takes 15s+; combined with start-period
  + healthcheck interval, can exceed 120s. Mitigation: operator bumps
  `--wait-timeout` to 180s in the workflow. Documented as Task 4
  pitfall.
- **(g) Concurrent tag pushes race the deploy.** Per-ref concurrency
  groups don't serialize across DIFFERENT refs (`v1.2.3` and `v1.2.4`
  have different `github.ref`). Two deploys could SSH the same server
  simultaneously. **Locked decision**: deploy job uses constant key
  `release-deploy` (NOT `release-${{ github.ref }}`). Publish jobs stay
  per-ref (parallel publish, serialized deploy). Update Task 4 spec
  accordingly.
- **(h) Rollback to pre-Plan-006 commit.** Older `release.yml` may not
  have a deploy job at all → re-tagging an ancient commit doesn't roll
  the server. The server's `compose.yml` (Plan 006 sets it to
  `${IMAGE_TAG}`) survives, so a `deploy`-equipped older tag would
  still work. Realistic floor: tags built after Plan 006. Documented
  in README §9.
- **(i) `metadata-action` major bump changes `version` output shape.**
  Task 3 reads `steps.meta.outputs.version`; future `@v6` could rename
  or restructure. Failure mode: empty `${IMAGE_TAG}` on server,
  cryptic error. Mitigation: bump `metadata-action` deliberately and
  re-smoke. Not solvable in this plan.
- **(j) GH Actions usage limit.** ~3 minutes per release (test +
  publish + deploy). Not a real risk at personal scale; mentioned for
  completeness.
- **(k) `appleboy/ssh-action` supply-chain incident.** A compromised
  action could exfiltrate `DEPLOY_SSH_KEY`. Mitigation: SHA-pin
  (hardening follow-up Task 8). Acceptable v5 risk; widely used,
  community-vetted; pinning is the right next step but not in scope.

## Trade-offs

- **(a) SSH-from-GHA vs Watchtower.** Chose SSH-from-GHA. Deploy-time
  control — the workflow run is the single audit log of "what shipped
  and whether it landed". Watchtower polls server-side and loses that
  visibility. Hands-off is fleet hygiene; at one server it just means
  "no idea what's running until I SSH in".
- **(b) Push-based deploy vs server-side webhook receiver.** Chose push.
  Webhook = HTTP listener on the server, signature verification, TLS,
  none of which pay for themselves at one app on one server.
- **(c) `appleboy/ssh-action` vs Ansible from GHA.** Chose the action.
  Ansible is a hammer for a six-line shell nail; inventory + playbook +
  collection install in CI burns budget on orchestration we don't need.
- **(d) Single `release.yml` vs separate `deploy.yml`.** Chose single.
  Build → push → deploy is one atomic outcome; `needs:` gates deploy on
  publish; the operator re-runs the failed job from the Actions UI.
  Two workflows means cross-run output plumbing and the "image pushed
  but server not deployed" partial state the user called out.
- **(e) Inline env var vs `.env` on server.** Chose inline. Stateless;
  the tag travels on the same shell line as the docker command. A
  `.env` file goes stale the moment an operator runs `docker compose
  up` by hand without resetting it. Cost: `docker compose ps` no longer
  shows the "intended" tag from a file — operator queries
  `docker inspect` instead. Acceptable: that's the source of truth
  regardless.
- **(f) `${IMAGE_TAG}` with no default vs `:-latest`.** Chose no default.
  Silent fallback to `latest` defeats pinning. The whole point of
  versioned tags is that "what's running" is deterministic.
- **(g) Repo `compose.yml` migrates to `${IMAGE_TAG}` vs stays
  literal.** Chose migrate. One template, same shape on the server, in
  the repo, and under `make docker-run`. Pre-1.0 allows clean breaks;
  v4 operators do a one-line edit during cutover (Task 9).
- **(h) `vars.*` for host/user/fingerprint vs `secrets.*` everywhere.**
  Chose variables for the non-sensitive three. Host resolves publicly,
  username is by convention, fingerprint is by design public. Logs
  show the variable values — handy for debugging "wrong host hit"
  scenarios. Secrets-for-everything pretends at security without
  adding any (the values aren't sensitive in the first place).
- **(i) `appleboy/ssh-action@v1` floating major vs SHA-pin.** Chose
  float. Whole `release.yml` is on floats; pinning one action mid-file
  sends mixed signals. SHA-pinning the whole file is on the v4
  known-debt list; v5 adds one more entry to that list.
- **(j) Constant deploy concurrency group vs per-tag.** Chose constant
  (Risk (g)). Per-tag groups don't serialize across different tag refs;
  constant does. Cost: queued deploys wait. Correctness over throughput
  at personal scale.
- **(k) `docker compose up --wait` vs `curl /healthz` loop from GHA.**
  Chose `--wait`. Same probe Docker uses, same probe `docker inspect`
  exposes — one source of truth. Curl-from-GHA would need the admin
  port reachable from outside, which means binding to `0.0.0.0` or
  fronting with a reverse proxy. Both worse than `--wait`.
- **(l) Manual rollback vs `if: failure()` auto-rollback step.** Chose
  manual. Auto-rollback masks the bug. The right response to a failed
  healthcheck is "look at logs, fix the underlying issue", not "revert
  and forget". Operator-friendly automation here trains the team to
  ignore failed deploys.
- **(m) No staging environment.** Cost of a second server (config,
  tunnels, ops) outweighs the integration bugs it would catch at
  personal scale. The pre-tag manual smoke is the gate.
- **(n) No blue/green.** ~3s of proxy unavailability on `docker compose
  up -d` is acceptable for a forward proxy used interactively.
  Blue/green needs either two containers + LB or a draining shutdown
  the proxy doesn't speak. Revisit when the proxy serves
  non-interactive workloads.
- **(o) Single server, no matrix.** Matrix expansion is a structural refactor
  (scalar repo Variables can't be iterated by `strategy.matrix`; the existing
  `vars.SERVER_HOST` etc. must be promoted to JSON-array variables and consumed
  via `fromJSON()` — not mechanical) when a second server appears. Building it
  now is premature abstraction.
