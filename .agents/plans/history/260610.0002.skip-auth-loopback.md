# Task Breakdown

## Overview

Bypass Bearer authentication for clients connecting from the loopback interface
(`127.0.0.0/8` or `::1`) while keeping the 407 challenge intact for every other
remote. The operator is moving the proxy listener onto non-loopback addresses
(LAN / `0.0.0.0`); local CLI tools and scripts on the same host must keep
working without a token, while remote clients still need one. On the default
`127.0.0.1:8080` deployment this effectively disables auth — that is the
intended, documented outcome.

The change is a service-layer policy decision and lives entirely inside
`(*ProxyService).checkAuth` at `internal/service/proxy.go:369`. The `auth`
package does NOT change: the `Verifier` interface stays focused on
"does this header carry a valid token", with no knowledge of *who* is exempt.
This preserves layer boundaries and keeps the verifier reusable.

The implementation is small (~5 lines plus a helper) but the behavior change
is operator-visible: the README and CLAUDE.md both need a one-line qualifier.

## Assumptions

- `r.RemoteAddr` is set by `net/http` to `ip:port` for every accepted
  connection in normal operation. Empty / unparseable values are treated as
  **non-loopback** (fail closed). Rationale: an unparseable `RemoteAddr` is an
  abnormal state — usually a synthetic request from a test harness or a
  custom transport. Treating it as loopback would create a path where an
  attacker who could influence `RemoteAddr` (e.g. through a buggy upstream
  middleware in a future change) could skip auth. Failing closed costs us
  nothing (the operator's CLI tools have valid loopback addresses), and the
  alternative — failing open on a malformed value — is a classic auth
  bypass shape. We log the failure path with `reason=missing/wrong_*` as today.
- `net.SplitHostPort` is the correct parser: it handles bracketed IPv6
  (`[::1]:12345`) which a naive `strings.LastIndex(":")` split would mangle.
- The bypass is intentionally unconditional when auth is configured — there
  is no toggle. Operators who want loopback to *also* require a token would
  not deploy this version. This is consistent with the task: "the default
  127.0.0.1:8080 deployment becomes effectively auth-disabled — acceptable
  and expected."
- `net` is already imported in `internal/service/proxy.go` (used by
  `SplitHostPort` in `HandleCONNECT` and `halfClose`). No new dependencies.
- No new exported identifiers are required. The loopback check is a private
  helper inside the service package.

## Tasks

### Task 1: Add loopback bypass to `checkAuth`

- **Description:** Insert a loopback check inside
  `(*ProxyService).checkAuth` at `internal/service/proxy.go:369`. The check
  is the **first branch after** the existing `s.verifier == nil`
  short-circuit, so:
  1. Disabled-auth wins (already returns `true` immediately).
  2. Loopback bypass runs before the header is even read.
  3. Header / token validation runs only for non-loopback, auth-enabled
     requests (unchanged code path).
  Add a private helper `isLoopbackRemote(addr string) bool` declared in the
  unexported-helpers section near the bottom of `proxy.go`, alphabetised
  between `halfClose` and `logTarget`. Parsing rules:
  - `net.SplitHostPort(addr)` — on error, return `false`.
  - `net.ParseIP(host)` — on `nil`, return `false`.
  - return `ip.IsLoopback()` (this covers both `127.0.0.0/8` and `::1`).
  When the bypass fires, emit exactly one op-log line and return `true`
  without touching the access logger — the downstream handler
  (`HandleHTTP` / `HandleCONNECT`) writes the normal access record once
  it finishes, exactly as it does for a successful token verification.
  Op-log line shape:
  ```go
  s.logger().Info("auth bypassed",
      slog.String("reason", "loopback"),
      slog.String("client_addr", r.RemoteAddr),
  )
  ```
  Do NOT log `target` here — that is the access log's job, and emitting it
  in two places doubles log volume on every loopback request.
- **Acceptance Criteria:**
  - [ ] `checkAuth` order is: `verifier == nil` → loopback bypass → header
        parse / verify (unchanged).
  - [ ] `isLoopbackRemote("127.0.0.1:12345") == true`.
  - [ ] `isLoopbackRemote("[::1]:12345") == true`.
  - [ ] `isLoopbackRemote("192.0.2.4:12345") == false`.
  - [ ] `isLoopbackRemote("") == false`.
  - [ ] `isLoopbackRemote("garbage") == false`.
  - [ ] When bypass fires, the verifier's `Verify` method is NOT called.
  - [ ] When bypass fires, op-log emits exactly one line with
        `msg="auth bypassed"`, `reason=loopback`, `client_addr=<RemoteAddr>`.
  - [ ] When bypass fires, `checkAuth` does NOT call `s.logAccess` itself —
        the downstream handler still emits its normal access record.
  - [ ] Existing auth-failure path is byte-for-byte unchanged for
        non-loopback requests (header parse, 407, `Proxy-Authenticate`
        challenge, `classifyAuthFailure` reason, access record).
  - [ ] No new imports added to `proxy.go` (`net` already present).
  - [ ] `make test` passes.
- **Pitfalls:**
  - Placing the loopback check *before* `verifier == nil` is wrong — auth
    disabled means no log line at all; with the wrong order we'd emit
    `auth bypassed reason=loopback` even when auth was never configured.
    Disabled-auth must short-circuit first.
  - `net.SplitHostPort("[::1]:12345")` returns host `"::1"` (no brackets).
    Do not strip brackets manually — `SplitHostPort` already does it.
  - `net.ParseIP("127.0.0.1.")` returns `nil` — trailing-dot DNS forms are
    not IPs; the function correctly classifies them as non-loopback.
  - Do NOT add `loopback` as a possible value to `classifyAuthFailure` — it
    is not a *failure*, it is a bypass. The two log lines are distinct
    (`auth failed` vs `auth bypassed`), which makes log filtering trivial.
  - `r.RemoteAddr` for a hijacked CONNECT is still set at the point
    `checkAuth` runs (before hijack). The bypass logic does not interact
    with the hijack path.
  - The op-log line must NOT contain the request target or the
    `Proxy-Authorization` header value. Loopback clients are still
    untrusted in the sense that we should not amplify whatever they send
    into operational logs beyond what we'd log for a normal authed request.
- **Complexity:** Easy
- **Code Example:**
  ```go
  func (s *ProxyService) checkAuth(w http.ResponseWriter, r *http.Request) bool {
      if s.verifier == nil {
          return true
      }
      if isLoopbackRemote(r.RemoteAddr) {
          s.logger().Info("auth bypassed",
              slog.String("reason", "loopback"),
              slog.String("client_addr", r.RemoteAddr),
          )
          return true
      }
      header := r.Header.Get("Proxy-Authorization")
      if header != "" && s.verifier.Verify(header) {
          return true
      }
      // ... existing 407 path unchanged
  }

  // isLoopbackRemote reports whether addr (an "ip:port" RemoteAddr) belongs
  // to a client connecting over the loopback interface. Empty or unparseable
  // addresses return false (fail closed: an abnormal RemoteAddr must not
  // grant auth bypass).
  func isLoopbackRemote(addr string) bool {
      host, _, err := net.SplitHostPort(addr)
      if err != nil {
          return false
      }
      ip := net.ParseIP(host)
      if ip == nil {
          return false
      }
      return ip.IsLoopback()
  }
  ```

### Task 2: Cover loopback bypass in `proxy_test.go`

- **Description:** Add new `t.Run` subtests inside the existing
  `TestProxyService_HandleHTTP` and `TestProxyService_HandleCONNECT`
  functions in `internal/service/proxy_test.go`. Do NOT create new
  top-level `Test*` functions — CLAUDE.md requires one `Test*` per method
  with scenarios as subtests. Reuse the existing `mockVerifier` whose
  `verifyFn` field is already in the file (see `proxy_test.go:35`).
  For the "must not call verifier" assertions, set
  `verifyFn: func(string) bool { t.Fatal("verifier called on loopback bypass"); return false }`
  — a regression where loopback no longer short-circuits will fail the
  test loudly. To assert the op-log line, build the service with an
  `OpLog: slog.New(slog.NewJSONHandler(&buf, nil))` and grep the buffer
  for `"reason":"loopback"`.
  Scenarios to add to `TestProxyService_HandleHTTP`:
  - `t.Run("auth enabled bypasses loopback IPv4", ...)` — `RemoteAddr =
    "127.0.0.1:12345"`, no `Proxy-Authorization` header, expect 200 from
    the test upstream, expect verifier's `verifyFn` never called, expect
    op-log to contain `reason=loopback`.
  - `t.Run("auth enabled bypasses loopback IPv6", ...)` — `RemoteAddr =
    "[::1]:12345"`, no header, expect 200, verifier not called.
  - `t.Run("auth enabled rejects non-loopback", ...)` — `RemoteAddr =
    "192.0.2.4:12345"` (TEST-NET-1, guaranteed non-loopback), no header,
    expect 407, verifier IS called (or rather: the header-empty short-
    circuit applies; assert classified reason `missing` via the existing
    op-log path).
  - `t.Run("auth enabled fails closed on empty RemoteAddr", ...)` —
    `RemoteAddr = ""`, no header, expect 407. This proves fail-closed
    behavior on malformed addresses.
  Scenarios to add to `TestProxyService_HandleCONNECT`:
  - `t.Run("auth enabled bypasses loopback", ...)` — IPv4 loopback,
    no header, expect 200 `Connection established` and the tunnel to set
    up. Reuse whatever fake upstream the existing CONNECT tests use.
  - `t.Run("auth enabled rejects non-loopback", ...)` — `192.0.2.4:12345`,
    no header, expect 407.
  Both bypass subtests must include a `verifyFn` that calls `t.Fatal` if
  invoked, to guard against regressions where the loopback branch silently
  falls through to the verifier.
  Use `httptest.NewRequest` with a manually-set `RemoteAddr` field (assign
  after construction). Tests run with `t.Parallel()` inside each subtest
  — they share nothing mutable.
- **Acceptance Criteria:**
  - [ ] Six new subtests added (four under `HandleHTTP`, two under
        `HandleCONNECT`), all using `t.Run`.
  - [ ] No new top-level `Test*` functions added to the file.
  - [ ] Each bypass subtest installs a `verifyFn` that calls `t.Fatal`
        if invoked.
  - [ ] Each bypass subtest asserts the op-log buffer contains the
        substring `"reason":"loopback"`.
  - [ ] Each bypass subtest asserts the response is 200 (HTTP) or
        `HTTP/1.1 200 Connection established` (CONNECT).
  - [ ] Each rejection subtest asserts the response is 407 and the
        `Proxy-Authenticate: Bearer realm="httpproxy"` header is set.
  - [ ] The empty-`RemoteAddr` subtest produces 407.
  - [ ] All new subtests call `t.Parallel()`.
  - [ ] `CGO_ENABLED=1 go test -race ./internal/service/...` passes.
- **Pitfalls:**
  - `httptest.NewRequest` sets `RemoteAddr` to `"192.0.2.1:1234"` by
    default — overwrite it explicitly in every new subtest or you'll get
    spurious non-loopback behavior in the "should bypass" cases.
  - When asserting "verifier not called" via `t.Fatal` inside `verifyFn`,
    be aware the goroutine context matters: for `HandleHTTP` the verifier
    runs on the request goroutine, so `t.Fatal` works; for `HandleCONNECT`
    same path (auth runs before hijack). No goroutine-Fatal hazard.
  - Op-log assertion: build the JSON handler with a bytes.Buffer guarded
    by a mutex if any test goroutine writes to the buffer concurrently
    — `slog.JSONHandler` is documented as safe for concurrent use of
    distinct loggers but the underlying writer is the test's
    responsibility. For these synchronous request tests a plain
    `bytes.Buffer` is fine.
  - Do not assert the *exact* JSON shape of the op-log line — substring
    match on `"reason":"loopback"` is the right level of coupling.
- **Complexity:** Easy
- **Code Example:**
  ```go
  t.Run("auth enabled bypasses loopback IPv4", func(t *testing.T) {
      t.Parallel()

      var opLogBuf bytes.Buffer
      svc, upstream := newTestService(t, func(o *ProxyServiceOptions) {
          o.Verifier = &mockVerifier{verifyFn: func(string) bool {
              t.Fatal("verifier must not be called for loopback client")
              return false
          }}
          o.OpLog = slog.New(slog.NewJSONHandler(&opLogBuf, nil))
      })
      defer upstream.Close()

      req := httptest.NewRequest(http.MethodGet, upstream.URL, nil)
      req.RemoteAddr = "127.0.0.1:12345"
      rec := httptest.NewRecorder()

      svc.HandleHTTP(rec, req)

      require.Equal(t, http.StatusOK, rec.Code)
      require.Contains(t, opLogBuf.String(), `"reason":"loopback"`)
  })
  ```

## Execution Order

1. **Task 1** — implement the loopback bypass in `checkAuth` plus the
   `isLoopbackRemote` helper. This is the load-bearing change; everything
   else verifies or documents it.
2. **Task 2** — add the subtests. They must be written against the
   implementation from Task 1 (the op-log assertion depends on the exact
   `msg` / `reason` strings chosen in Task 1).
3. **Task 3** — update `README.md` and `CLAUDE.md`. Pure prose; can be
   done in parallel with Task 2 if convenient, but logically slots after
   Task 1 since the docs describe behavior that must already exist.

Tasks 1 and 2 are strictly sequential. Task 3 has no code dependency on
Task 2 and could be parallelised, but in practice all three are small
enough that a single engineer session covers them in order.

## Risks

- **Operator misunderstands the default-bind consequence.** If the
  operator does not read the updated README, they may assume auth still
  applies on `127.0.0.1:8080` and be surprised that local curl works
  without a token. Mitigation: the README edit must spell out the
  consequence explicitly, not bury it.
- **Future middleware sets `RemoteAddr` to a synthetic value.** If a
  future change inserts a middleware that overwrites `r.RemoteAddr`
  (e.g. a PROXY-protocol parser), the bypass could fire for non-loopback
  clients. Mitigation: this is a known property of using `RemoteAddr` as
  trust input; documented in the fail-closed Assumptions section so a
  future engineer sees the trust boundary explicitly.
- **IPv6-mapped IPv4 (`::ffff:127.0.0.1`).** `net.ParseIP` returns a
  16-byte IP, and `IsLoopback` on that value returns `true` because the
  Go stdlib correctly treats IPv4-mapped IPv6 loopback as loopback. This
  is the desired behavior; no extra handling needed. The test plan does
  not need a dedicated case for it, but a comment in the helper may be
  worth adding.
- **Test flakiness from concurrent op-log buffer access.** Not expected
  for synchronous handler tests, but if a future subtest fires multiple
  goroutines against the same buffer, a sync wrapper would be needed.
  Out of scope here.

## Trade-offs

- **Policy lives in `service`, not `auth`.** Chose to keep `auth`
  pure ("here is a token, is it valid?") and put the "who is exempt"
  policy in `service` where the rest of the request-flow policy lives.
  The alternative — extending the `Verifier` interface or adding a
  second `LoopbackVerifier` — would force every future caller of `auth`
  to reason about loopback, which is not auth's concern. Cost: the
  service package gets one more 5-line helper. Benefit: `auth` stays
  trivially testable and reusable.
- **No config knob to disable the bypass.** Chose unconditional bypass
  over a `auth.allow_loopback: true|false` config field because the
  stated requirement is "local CLI tools must work without a token",
  and the default `127.0.0.1` deployment becoming auth-effectively-off
  is acceptable. A future operator who wants to *enforce* auth on
  loopback would need a config addition; that operator does not exist
  today, and adding the knob now would add config-surface complexity
  for nobody.
- **Fail closed on unparseable `RemoteAddr`.** Chose fail-closed over
  fail-open because an unparseable `RemoteAddr` is abnormal and any
  bypass logic that defaults to "permissive on abnormal input" is the
  shape of an auth bypass bug. Cost: zero in practice — normal clients
  always have a parseable `RemoteAddr`. Benefit: closes a potential
  trust-input bypass without ceremony.
- **One op-log line per bypass.** Chose to log every bypass at `Info`
  rather than `Debug` (or not at all) because the operator needs an
  audit trail: "who was hitting the proxy without a token, and when".
  At Debug, the line would be invisible in production. Cost: log volume
  scales with loopback request volume. For a host where the operator
  runs occasional CLI tools that is negligible; for a host where a
  loopback script hammers the proxy thousands of times per second, the
  operator can drop the rule on the slog side. Worth the cost.
