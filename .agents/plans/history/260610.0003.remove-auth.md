# Task Breakdown

## Overview

Remove Bearer-token authentication from `httpproxy` entirely. In production the
feature is already dead code: `configs/compose.yml` publishes ports as
`127.0.0.1:1701:1701` and `127.0.0.1:8081:8081` (lines 18-19), so the only
reachable surface is host-loopback; and Docker NAT rewrites the source IP to the
bridge gateway (`172.17.0.1`), so the `isLoopbackRemote` bypass added in plan
`260610.0002.skip-auth-loopback.md` always evaluates to `false` inside the
container anyway. The token therefore protects nothing while costing the
operator real friction (token files, rotation, header plumbing).

The new security boundary is the compose `ports:` block. The proxy is reachable
only by processes running on the same host as the Docker daemon. Any operator
who later flips `ports:` to `0.0.0.0:1701:1701` exposes an unauthenticated proxy
to the network — the README and CLAUDE.md must shout this loudly enough that
nobody does it by accident.

Scope of deletion:

- `internal/auth/` package (entire).
- `Verifier` field, `checkAuth`, `classifyAuthFailure`, `isLoopbackRemote`,
  `authLogTarget`, `export_test.go` shim, every auth-related subtest.
- `Auth` config field, `rawAuth` JSON struct, the
  "token / token_file mutually exclusive" validator, `resolveAuthToken` in
  `cmd/httpproxy/main.go`, and the auth-wiring block in `run`.
- `configs/proxy.example.json` `auth` block; `configs/auth/token` file;
  `configs/auth/` directory (gitignore entries included).
- README Auth section, Observability bullets for `auth failed` / `auth bypassed`,
  CLAUDE.md layer-table row, HTTP routes paragraph, example config schema,
  Bearer-token constraint bullet.

What we do **not** touch:

- `internal/publicerror` (still used for config errors).
- `compose.yml` / Dockerfile / release workflow / SSH secrets / Telegram
  notifier — verified consistent with loopback-only intent.
- `SECURITY.md` is out of scope per the task brief (the file mentions auth, but
  the user explicitly listed the docs to edit; flagged in Risks as a follow-up).

## Assumptions

- The proxy will continue to be deployed only via the documented Docker compose
  path. A bare-metal deployment that binds the listener to a non-loopback
  address would now serve an unauthenticated proxy; this is called out in the
  README and CLAUDE.md so an operator who reads the docs cannot deploy it
  unsafely by accident.
- `configs/auth/token` is gitignored (`.gitignore` lines 45-46:
  `/configs/auth/*` with `!/configs/auth/.gitkeep`); the file is local-only and
  not tracked in git, so the deletion does not require git history rewriting.
  `ls` confirms `configs/auth/token` exists on disk but there is no `.gitkeep`
  sibling — the whole directory can be deleted from the working tree.
- The `Verifier` interface has only one consumer (`ProxyService`); no external
  package imports `internal/auth`. A `go vet ./...` after the deletion will
  catch any straggler I missed.
- No backward-compatibility shim for old `proxy.json` files is needed. The
  loader currently accepts `auth` as an unknown-field-tolerant JSON block; once
  the `rawAuth` struct is removed, an `auth` key in an old config file is
  silently ignored by `encoding/json` (it does not error on unknown fields).
  This is acceptable: the operator who rolls forward keeps their old
  `proxy.json`, the `auth` block becomes a no-op, and the proxy starts. We
  document this in the example config commit but do not add any "deprecated
  field" warning — the field is gone, not deprecated.
- Plan numbering: `plans/` is empty, `plans/history/` is empty, completed plans
  use date-based names. Next active sequential index is `001`.

## Execution Order

Order is dictated by build-greenness: code-and-test edits land in one commit,
disk/docs land in a follow-up. Splitting code from tests would leave `main` red
between commits.

1. **Tasks 1, 2, 3, 4, 5 land together** in a single commit. They form an
   atomic "delete the auth feature" change: package, service consumer,
   service tests, composition root, config schema, config tests. Splitting
   them would break the build between commits.
2. **Task 6** (disk artifacts + gitignore) lands in a second commit. No
   compile-time coupling.
3. **Tasks 7 and 8** (README, CLAUDE.md) land in a third commit. Docs only;
   independent of code.
4. **Task 9** is a read-only audit performed before commit #1 — its result
   is summarized in the commit body of commit #1, not its own commit.
5. **Task 10** is the final gate before opening the PR. If anything fails,
   the engineer iterates on commits #1-#3 rather than adding a new commit.

Tasks 1-5 must be done by one engineer in one session. Tasks 6-8 can be
parallelized in principle but are too small to bother. Total: ~3 commits,
one PR.

## Risks

- **Operator flips `ports:` to `0.0.0.0` without re-introducing auth.** The
  proxy becomes an open relay. Mitigation: the README "No application-level
  authentication" paragraph names this explicitly; CLAUDE.md HTTP routes
  section will no longer claim auth exists. A future operator who reads the
  docs cannot deploy unsafely by accident. There is no in-process guardrail
  against the bind change — that is out of scope and would be a separate
  feature (e.g. "refuse to start when listener is non-loopback").
- **Someone shells into a future non-distroless image and uses the proxy
  without credentials.** Today the image is distroless and has no shell, so
  this is a non-issue. If the deployment ever switches to a debug/dev image
  with `sh`, any process inside the container can hit `127.0.0.1:1701` via
  the bound port without challenge. Mitigation: this is a property of the
  loopback-bind model and is acceptable — gaining shell access to the
  container is already a much larger compromise than "can use the proxy".
  Worth documenting if a debug image is ever shipped; not worth a guardrail.
- **`SECURITY.md` is not updated by this plan.** The user's brief scoped the
  doc edits to README and CLAUDE.md. `SECURITY.md` currently makes claims
  about Bearer-token discipline, log scrubbing, and constant-time
  comparison. After this plan ships, those claims are stale. The engineer
  must flag this in the final commit message and open a follow-up issue or
  let the user decide whether to bundle the `SECURITY.md` edit into the
  same PR. Reviewers should not be surprised by the inconsistency.
- **Old `proxy.json` files in the wild contain an `auth` block.** The JSON
  decoder silently ignores unknown fields, so old configs keep working but
  the `auth` block becomes a no-op. An operator who was relying on auth
  will not be warned. Mitigation: this is the documented behavior of
  `encoding/json` and is consistent with how we handle every other config
  evolution; adding a deprecation warning would mean preserving the
  `rawAuth` struct, defeating the point of the deletion.
- **CI relies on auth tests for coverage gates.** Currently CI runs `make
  test` with no explicit coverage threshold. Deletion of the auth subtests
  drops the test count by ~20 but does not cross any threshold. Verified by
  inspecting `.github/workflows/ci.main.yml`.
- **Reviewer agents flag the SECURITY.md inconsistency as P1.** Pre-empted
  by Task 10's commit-message note.

## Trade-offs

- **Delete vs disable.** Could have kept the `auth` package and config
  field, defaulted to disabled, and let operators opt back in. Rejected:
  the user's stated requirement is "rip it out entirely" because the
  feature is dead code in the only supported deployment shape (Docker
  compose with loopback bind). Keeping it as opt-in preserves a maintenance
  burden (test surface, godoc, dependency on `crypto/subtle`) for a
  use case nobody has. The trade-off cost is: an operator who later
  decides they need auth will reintroduce it via a new commit, with the
  benefit of designing it for the actual threat model rather than retrofitting
  the existing Bearer scheme.
- **Loopback bind as the security boundary.** Chose `127.0.0.1:1701:1701`
  in compose as the sole boundary. Alternatives: SSH-only access, Unix
  socket binding, mTLS. SSH and overlay networks are documented as the
  cross-host story (no change). Unix sockets would require non-trivial
  Docker plumbing and would break the existing curl-based usage. mTLS is
  overkill for a same-host proxy that the operator wrote for themselves.
  Loopback bind is the simplest model that delivers the actual security
  property: "only this machine can use this proxy".
- **No `SECURITY.md` edit in this plan.** Following the user's brief
  exactly. Trade-off: leaves a temporarily-inconsistent doc surface. We
  prefer respecting the user's scoping over silently expanding the change.
  The follow-up cost is one short commit later.
- **No `DisallowUnknownFields` on the config decoder.** Old configs with
  `auth` blocks continue to load silently. Trade-off: a forward-compat
  trap (the operator thinks auth is enabled because the field is in their
  file). Mitigation lives in the README delete and CLAUDE.md edit — the
  docs no longer claim the field exists. An operator who reads the docs
  will not be surprised. Adding `DisallowUnknownFields` would refuse to
  start on any old config and would be a worse experience.
- **Keep `Proxy-Authorization` in the hop-by-hop strip list.** Even though
  we no longer enforce auth, `Proxy-Authorization` is hop-by-hop per RFC
  7230 §6.1 and any client that happens to send one must not have it
  forwarded to the upstream origin. Removing it from the strip list would
  create a credential-leak vector for clients that misuse the header.
  Trade-off cost is zero (one entry in a static slice); benefit is correct
  RFC behavior.
