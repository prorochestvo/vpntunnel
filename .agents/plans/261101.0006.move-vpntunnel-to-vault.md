# Task Breakdown

## Overview

Move the vpntunnel daemon from its current production host (`185.121.81.56`, SSH port
`4287`) to `vault` (`31.220.94.204`), the owner's consolidation host for auxiliary
infrastructure (vault owner decision, 2026-10-28: one server loaded to 80-90% of its
memory, a hard `mem_limit` on every container). vpntunnel supports the other projects with
VPN egress and is not a project of its own, so it belongs with the other auxiliary
services. Start is planned for the week of 2026-11-02, after Task 1 confirms that vault
has room for it.

## Assumptions

- Owner decisions from the 2026-11-01 discussion:
  - The deploy is driven from this repository. The vault repository does not describe
    vpntunnel; this repository holds the deploy description and builds a Docker image if
    needed.
  - vpntunnel runs on vault as a Docker container, not as the current systemd unit.
  - Clients reach the proxy over the vault WireGuard network (`10.77.0.1`) with the
    `X-Vpntunnel-Token` token.
  - The old host's tunnels are stopped before vault starts any. Current client count is
    one at most, and that tunnel may already be unused.
- vault host rules this move must respect (from the vault repository's `CLAUDE.md`):
  the vault repository adds no host provisioning; Docker-published ports bypass ufw;
  `aide` (and any CI identity) must never be in the `docker` group, because membership is
  root-equivalent on a host that holds every stage database, the backups and the
  WireGuard peer control.
- vault snapshot on 2026-11-01 (`ssh vault-seil`): 7941 MiB RAM, 1275 MiB used, no swap,
  4 CPUs, load about 1.3, root disk 14% of 96G used. Container limits sum to 6.25 GiB
  (about 81% of RAM): `stage-mongo` 2.5g, `stage-postgres` 1.5g, `mattermost` 1g,
  `stage-rabbitmq` 512m, `stage-redis` 512m, `mattermost-postgres` 256m. The 90% ceiling
  leaves about 0.75 GiB of limits. Listening on the host: SSH `0.0.0.0:4287`, databases
  on `10.77.0.1:17000-17301`, Mattermost `127.0.0.1:8065`, cloudflared metrics
  `127.0.0.1:20241`.

## Tasks

### Task 1: Confirm vault capacity and readiness
- Description: Before any change, measure vpntunnel's real footprint on the current host
  (RSS of the daemon over a day with the streaming tunnel up and one on-demand tunnel,
  CPU under typical load) and re-take the vault snapshot above. Confirm that the proposed
  `mem_limit` fits under the 90% ceiling and that CPU headroom stays comfortable next to
  Mattermost and RabbitMQ, which carry most of the current CPU load.
- Acceptance Criteria:
  - Measured peak RSS and CPU of vpntunnel are written into this plan.
  - A `mem_limit` is chosen (expected 128m-256m) and the new sum of vault limits is
    written here and is at most 90% of vault RAM.
  - A go/no-go line is recorded here. No-go stops the plan.
- Pitfalls & edge cases: wireguard-go plus the gVisor netstack allocates per tunnel;
  measure with both roles up, not the idle streaming tunnel alone.
- Complexity: Easy

### Task 2: Decide the deploy identity on vault
- Description: The deploy runs from this repository, so its CI needs a way to start a
  container on vault without Docker-group membership. Add a narrow forced-command gate
  on vault for a dedicated user (pattern of vault's `bin/vault-aide-gate` and
  `bin/vault-apply`): it accepts only an image reference for the `vpntunnel` compose
  project and runs `docker compose up -d` for it as root. The gate, the user, its sudoers
  line and its key are installed by the owner by hand, like the rest of the vault host.
- Acceptance Criteria:
  - The gate rejects every argument except a pinned image reference for vpntunnel.
  - The CI user is not in the `docker` group and has no other sudo rule.
  - The gate and its install steps are documented in this repository's deployment
    skill and `DEPLOY.md`.
- Pitfalls & edge cases: the gate must not accept a compose file or extra flags from the
  caller; a caller-supplied compose file is root on vault.
- Complexity: Medium

### Task 3: Build and publish a container image
- Description: Add a Dockerfile (static `CGO_ENABLED=0` binary on a minimal base) and a
  workflow that builds and pushes the image to GHCR on each `v*` tag. The image runs as
  a non-root user; userspace WireGuard needs neither root nor `NET_ADMIN`.
- Acceptance Criteria:
  - Image builds in CI, runs as non-root, read-only root filesystem works.
  - Tunnel `.conf` files, auth tokens and TLS material are mounted from vault at runtime
    (mode `0600`/`0400`), never baked into the image.
- Pitfalls & edge cases: the startup permission assertions of the current release
  layout (`/opt/vpntunnel/` secret tree modes) must be adapted to the container paths,
  not removed.
- Complexity: Medium

### Task 4: Define the vault runtime and network exposure
- Description: Write the compose definition this repository deploys through the Task 2
  gate: `mem_limit` from Task 1, `restart: unless-stopped`, no Docker socket, read-only
  root filesystem. Published ports:
  - proxy listener `7788` on `10.77.0.1:17400` only, for WireGuard clients with the token;
  - API listener `8888` on `127.0.0.1` only, for the owner's host `cloudflared`, replacing
    the nginx edge vhost and the Cloudflare Origin Certificate on the old host.
- Acceptance Criteria:
  - No vpntunnel port is reachable from the public interface (verified with a scan from
    outside WireGuard).
  - The owner extends vault's first `DOCKER-USER` rule with container port `7788`; binding
    to `10.77.0.1` alone is not enough, since Linux accepts packets for `10.77.0.1`
    arriving on the public interface.
  - The vault repository's `README` and `CLAUDE.md` record the new port and the
    `DOCKER-USER` change (a vault PR).
- Pitfalls & edge cases: inside a container, client connections arrive from the Docker
  gateway address, not loopback, so the loopback auth bypass no longer applies and every
  client must send the token; check the owner's host guard
  (`vault-docker-guard.service`) does not reject the new published port.
- Complexity: Medium

### Task 5: Cut over with break-before-make
- Description: Migrate under the Mullvad session budget (at most 2 sessions from one
  host, the account at 5 of 5): stop vpntunnel on the old host and confirm its sessions
  are gone, wait for the settle period, then start the container on vault. Point the
  remaining client, if any, at `10.77.0.1:17400` with the token.
- Acceptance Criteria:
  - At no moment do the old host and vault together hold more than 2 sessions.
  - `make healthz` equivalent passes against vault: Mullvad egress confirmed, the
    `/v1/admin/health` body unchanged.
  - The deploy Telegram notification reports the vault host.
- Pitfalls & edge cases: starting vault first evicts one of the owner's personal devices
  silently, provider-side; on-demand `idle_ttl` of 168h means the on-demand device counts
  as live.
- Complexity: Easy

### Task 6: Retire the old host
- Description: After a week of stable operation on vault, remove the old systemd unit,
  nginx vhost and `/opt/vpntunnel/` from the old host, update the `PRIME` environment
  variables (`SSH_HOSTNAME`, `SSH_HOSTPORT`, `SSH_USERNAME`) and the docs. If nothing else
  runs on `185.121.81.56`, the owner decides whether to cancel that VPS.
- Acceptance Criteria:
  - No deploy path targets the old host.
  - The old host carries no vpntunnel secrets.
- Pitfalls & edge cases: the tunnel `.conf` files are private keys; delete them, do not
  leave copies.
- Complexity: Easy

## Execution Order

1. Task 1 (go/no-go)
2. Task 2 and Task 3 in parallel
3. Task 4
4. Task 5
5. Task 6

## Risks

- A compromised vpntunnel container sits next to every stage database on vault. Mitigated
  by non-root, read-only root filesystem, no Docker socket, and a deploy gate without
  Docker-group access.
- The per-repository deploy gate is a second trust path into vault besides
  `vault-apply`; a leaked key of this repository can restart the vpntunnel container.
- vault becomes a single point of failure for the databases, Mattermost and VPN egress.

## Trade-offs

- Deploy from this repository (owner decision) versus a vault-managed service: the
  alternative was a `services/vpntunnel/compose.yml` in the vault repository pinning a
  GHCR image tag built here, deployed by vault's existing `make deploy` through its single
  trust gate. It needs no second gate on vault; the cost is that a vpntunnel release also
  needs a vault release. Reversal: move the Task 4 compose definition into the vault
  repository and drop the Task 2 gate. The vault README currently states that a new
  supporting service joins as a directory under `services/`; this plan deviates from that
  and the README needs a matching note in the Task 4 vault PR.
- cloudflared replaces nginx for the API: one less service on vault and no Origin
  Certificate to manage; the API is no longer reachable without the tunnel.
